# Переход Saruman к модам: архитектурная оценка

Дата: 24 октября 2026. Прочитаны оба новых ТЗ, код персонажа, исходники проектов
модов и публичные интерфейсы установленных JAR. Minecraft, LLM, игровые команды
и запись в Redis/БД для этой проверки не запускались. Выводы о совместном
выполнении, для которых нет игрового теста, обозначены как требующие проверки.

## 1. Вывод

Выбранное направление правильное: персонаж задаёт намерение, автоматизация
выполняет задачу и сообщает наблюдаемый результат. Политика боя/дыхания,
движение, поиск участка, посадка и дозирование муки должны находиться в модах.
LLM не должна получать сообщение после каждого шага ради продолжения.

Требуется единый диспетчер целей с отдельным циклом исполнения. Простая замена
нескольких tool calls на /treegrow start не решает перехват управления,
восстановление после боя, количественные цели и ограничения ресурсов.

Не считать готовым полное переключение, пока не проверены фактические API,
отмена/возврат управления и совместная работа именно этих сборок.

## 3. Новые требования сильнее старого плана

| Вопрос | Новое требование |
|---|---|
| Игроки | Auto Defense не атакует игроков вообще |
| Вода | Плавание/ныряние/погоня разрешены при контроле воздуха |
| Низкое здоровье | Отступление при ≤6 HP; возврат при ≥10 HP |
| Лечение | Имеющиеся лечебные зелья, еда по игровым правилам |
| Снабжение защиты | Мод публикует нехватку, сам ничего не выдаёт/добывает |
| TreeGrow | Один дуб или берёза за запуск; вид выбирается по ресурсам |
| Лимиты дерева | 64 блока от старта, 5 минут, 3 места × до 16 применений |
| Костная мука | Если меньше 48 — один запрос /give bone_meal 64 с проверкой |
| Навигация дерева | Через пользовательскую цепочку UnionClef, без своего pathfinder |
| Восстановление обычной работы | Допустим новый запуск актуальной команды; без восстановления старого пути |

Старые ограничения «только сухая погоня», «4 HP», ответ игрокам и «пять доз»
нельзя незаметно смешивать с этими модами. Операторский более строгий лимит
поддерживается только если исполнитель умеет его соблюдать; иначе запрос
отклоняется с объяснением, без обхода через legacy tool.

## 4. Что есть в коде персонажа сейчас

- Боевой CombatReflex уже работает в bridge без ожидания ChatAgent/LLM.
  Старые Python WaterSafety, NavigationGuard, сборщик ресурсов и подготовка
  оружия тоже могут менять тело/инвентарь.
- Часть деревьев уже обслуживается детерминированными Python-процедурами,
  но LLM по-прежнему видит много мелких инструментов и может вести цепочку сама.
- Autonomy вызывается из ChatAgent._background_step. Когда поток занят ответом
  модели или выполнением tool, этот цикл не является независимым игровым диспетчером.
- Gradio и prompt читают старые tree_task/self_defense/survival структуры;
  одного добавления Java-вызова недостаточно для согласованной диагностики.

Поэтому снижение задержек — это передача навыков модам плюс отделение
автоматизации от цикла генерации реплик, а не только сокращение промпта.

## 5. Обнаруженные ограничения интеграции

### 5.1. API защиты преимущественно наблюдательный

Установленный dev.autodefense.api.AutoDefenseApi имеет getStatus и getStatusJson.
publish является внутренним методом публикации, не командой включения.
Snapshot содержит enabled, inCombat, recovering, owner, error, missingItems.

У runtime есть внутренний toggle, F8 меняет его состояние. Это позволяет написать
адаптер, но не заменяет публичный идемпотентный setEnabled и подтверждённый stop.
В snapshot нет идентификатора мира, sequence или времени обновления. При потере
связи нельзя объявлять старое owner=NONE доказательством освобождения тела.

### 5.2. Бой завершает текущий TreeGrow

UnionClefBridge.stop отменяет user task и выключает runner. GrowTreeTask.onStop
завершает незавершённую задачу с отрицательным результатом. Это отмена, не pause.
У TreeGrow нет публичного resume существующей посадки.

Auto Defense сохраняет только замеченную @чат-команду; задача TreeGrow, запущенная
напрямую через API, может стать unreplayable. Самостоятельное восстановление её
через механизм сохранённой команды не гарантировано. Ещё опаснее восстановление
старой @команды, не относящейся к текущему внешнему заданию.

Один диспетчер должен владеть восстановлением цели. Нельзя одновременно разрешить
авторестарт команды в моде защиты и повторный запуск той же цели в Python.

### 5.3. Количество, вид и режим не являются параметрами TreeGrow

Фактические методы: TreeGrowClient.start(), current(), cancel(reason).
У текущей задачи есть site(), planted(), success(), result(), boneUses(),
plantSends(), isFinished() и другие отдельные getters. Цельного versioned snapshot
с run ID, species и единым состоянием нет. Изменяющие операции должны выполняться
на игровом потоке: прямой Py4J-вызов Java-метода не обеспечивает это автоматически.

«Вырастить два дерева» можно организовать как два последовательных запуска
с уникальными учтёнными результатами. «Два дуба», «только посадить» и произвольный
меньший лимит муки нельзя считать поддержанными только потому, что имеется start().

### 5.4. Повторный участок TreeGrow требует исправления

В прочитанном исходнике ветка получения саженца выполняется при species == null.
После посадки и неуспешного удобрения abandonSite сбрасывает site/stand/nextUse,
но не обеспечивает получение нового израсходованного саженца. На следующем месте
отсутствие саженца снова приводит к abandonSite.

Этот путь также сверён по bytecode установленного GrowTreeTask: abandonSite
не сбрасывает species и не запускает приобретение. Это статически подтверждённая
проблема; живое воспроизведение в рамках данного анализа не выполнялось.
Код персонажа не должен скрывать её многократными бесконечными start().

### 5.5. Потребность в зелье не равна любому minecraft:potion

MissingItem сейчас передаёт ID и количество. Для лечебного зелья требуется
семантика роли/компонентов: обычная выдача minecraft:potion не гарантирует
лечебный предмет. SupplyService должен использовать проверенный каталог
потребностей и фактический инвентарь, не слепо подставлять ID в /give.

## 6. Целевая архитектура

Уточнение владельца: [три канала действий](HYBRID_DISPATCH_POLICY.md).
Просьбы игроков имеют первый приоритет и сохраняют командные возможности LLM
для задач вне модов. Ситуативные моды — второй канал, планировщик — третий
и выбирает только модовые навыки.

```text
Игрок / оператор / редкое высокоуровневое решение LLM
                         ↓
                 GoalService: принять намерение
                         ↓
  AutomationRuntime: очередь, приоритеты, сроки, состояние и повторы
          ↓                    ↓                     ↓
    DefenseAdapter        TreeGrowAdapter        SupplyService
          ↓                    ↓                     ↓
     Auto Defense           TreeGrow         разрешённое снабжение
          ↓                    ↓
  собственный бой          UnionClef task
                         ↓
      События/снимки → Gradio, память, асинхронные реплики
```

AutomationRuntime работает в отдельном от LLM цикле/процессе. Решения и продолжение
задачи не исполняются из callback генерации речи. Он не рулит каждым игровым tick:
атака, дыхание и навыки полностью локальны в JVM.

LLM нужны понимание произвольной просьбы, отношение персонажа и выбор сложного
намерения. Очередь, веса занятий, расход лимитов, состояние, повторы, наблюдение
роста и переход к следующему дереву работают без модели.

Публичные инструменты LLM: submit_goal, get_goal_status, cancel_goal,
get_mod_status, общение, память и командные tools для принятых просьб игроков
вне модов, например goto/follow. Bone_meal/plant/find/attack не дублируют модовые
навыки. Это контекстное ограничение, а не полное удаление команд из возможностей
персонажа. Планировщик не передаёт LLM построение командных цепочек.

## 7. Модель цели и количественные задания

Хранить goal ID, request ID, вид/режим, требуемое количество, приоритет,
world/session, общий deadline и бюджет, отмену и список запусков модов.
Подтверждённый результат привязан к run ID, позиции и миру; учёт однократный.
Для устойчивых целей использовать существующую БД; Redis — оперативные snapshots.
Мод/игра не ждут успешной записи в БД на каждый tick.

Пример количества N: один запуск → наблюдаемый grown result → completed += 1
→ если completed < N, следующий запуск при свободном управлении.
Без LLM между запусками. После боя сохраняются count, completed и потраченные
ресурсы, а не создаётся новая исходная цель N с нулевым прогрессом.

Если посадка уже есть, но исполнение прервано, нужен поддерживаемый resume/reconcile
или явный незавершённый результат с её координатами. Не считать planted успехом
grown и не плодить дополнительные посадки, забыв прежнюю.

Повтор ограничен числом попыток и общим deadline. Отказ /give не запускает
новый start каждые полсекунды. Смерть/смена мира отменяют запуск; устойчивая цель
переходит в соответствующее состояние без самовольного старта после respawn.

## 8. Владение телом и снабжение

Приоритет источников: просьба игрока → ситуативная работа модов → планировщик.
Ручной Stop явный; смерть/аварийное спасение требуют корректной передачи тела.
Приоритет цели не означает одновременно двигать аватар двумя контроллерами.
Разговор и принятие приоритетной просьбы не ждут завершения боя.

Когда native backend владеет телом, Python CombatReflex, WaterSafety и обычные
tools не меняют движение, поворот, предмет и use. NavigationGuard не отменяет
маршрут, принадлежащий модовой задаче. Не начинать TreeGrow при STOPPING,
AUTO_DEFENSE, recovering, неизвестном или устаревшем состоянии владения.

SupplyService читает missingItems, проверяет права/каталог и пополняет недостающее
в спокойном состоянии, с резервированием и подтверждением. Без прав нет спама.
Auto Defense не получает скрытый старый ensure_scepter, навязывающий посох/XP.
Костная мука остаётся ответственностью TreeGrow согласно новому ТЗ; Python не
выдаёт её параллельно. Предпочтение старой магии не добавляется к моду без поддержки.

## 9. Нагрузка LLM и наблюдаемость

- Не вызывать модель на heartbeat, cooldown, шаг маршрута, каждую дозу или отсутствие мобов.
- Выбор фонового навыка — существующие веса и доступность модов, без LLM.
- Нет подходящего мода — фоновый навык недоступен, а не делегируется модели.
- Простые структурированные задания Gradio идут напрямую в GoalService.
- Произвольный текст интерпретируется один раз; персонаж может обсудить/отклонить
  просьбу согласно образу. Модовая цель далее выполняется автоматизацией;
  пользовательская задача вне модов может требовать следующих командных решений
  LLM по реальным результатам, в рамках срока и лимитов принятой цели.
- Голосовые комментарии по значимым событиям идут асинхронно; типовые реплики
  можно брать из существующей БД. Они не блокируют начало действия.
- В Gradio показывать цель/прогресс, фактический owner, версии, состояние мода,
  потребности, отказ, deadline и принятые решения автоматизации.
- Метрики отдельно: вызовы/токены LLM, очередь→dispatch, dispatch→observed result,
  native handoff, число прерываний/повторов и устаревших snapshots.

Нулевая задержка не обещается: останутся игровые ticks, путь, сервер и сеть.
Уменьшается ожидание модели и устраняется конкуренция контроллеров.

## 10. Порядок изменения системы

1. Зафиксировать точные сборки и новый контракт; закрыть критичные пробелы API
   или реализовать проверенный client-thread адаптер к этим сборкам.
2. Проверить TreeGrow retry и совместную отмену/восстановление после защиты.
3. Ввести тонкие клиенты модов и нормализованные snapshots отдельно от LLM.
4. Перенести цели/очередь в независимый AutomationRuntime.
5. Подключить batch trees и управление защитой; убрать дублирующие Python writers
   только после подтверждения native-контракта. Mod-mode не должен незаметно
   переключаться на старую семантику при неизвестном результате.
6. Перестроить LLM tools/prompts и Gradio вокруг целей/модов.
7. Проверить Start/Stop, бой во время TreeGrow, N деревьев, рестарт приложения,
   смерть, смену мира, ограничения, отсутствие прав и отказ/потерю API.

Эта оценка не является завершённой перепиской runtime. Для корректной полной
замены нужен контракт из [MOD_API_REQUIREMENTS.md](MOD_API_REQUIREMENTS.md).
Текущие моды дают хорошую основу, но готовность отдельного навыка не доказывает
совместимость двух владельцев управления и надёжное внешнее планирование.
