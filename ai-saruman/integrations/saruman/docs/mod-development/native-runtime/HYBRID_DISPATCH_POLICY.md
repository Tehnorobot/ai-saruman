# Три канала действий и командные возможности LLM

Уточнение владельца от 24 октября 2026. Дополняет
[архитектурную оценку](ARCHITECTURE_REVIEW_2026_10_24.md).

## 1. Приоритеты источников

| Приоритет | Источник | Маршрут |
|---|---|---|
| 1 | Просьба игрока/оператора | LLM понимает цель; подходящий мод либо командные tools LLM |
| 2 | Игровая ситуация | Локальная логика ситуативных модов, без LLM |
| 3 | Фоновый планировщик | Детерминированный выбор и запуск только модового навыка |

Источник и приоритет присваивает runtime по реальному событию. Модель не может
объявить фоновое действие пользовательским. Общение не требует владения телом.

## 2. Задачи игроков

- «Посади/вырасти дерево» → TreeGrow. LLM не строит цепочку поиска, посадки и муки.
- «Вырасти три дерева» → количественная цель и три подтверждённых модовых результата,
  без LLM между запусками.
- «Подойди ко мне», «Следуй за мной» → разрешённые goto/follow через LLM, если
  отдельного модового навыка нет.
- Другие принятые просьбы вне двух модов могут требовать нескольких командных
  решений LLM по результатам, с ограниченными сроками и числом шагов.

Командные инструменты сохраняются. Они проверяют owner, мир, отмену и допустимость;
команда как озвученный текст не исполняется, queued не является успехом.
Временный busy/ошибка API модового навыка не превращает его в ручную цепочку.
Неподдержанные параметры дерева объясняются явно, без подмены результата.
Новая принятая просьба прерывает фон поддерживаемым способом и сохраняет прогресс.

## 3. Ситуативные моды и передача тела

Защита работает независимо от LLM, реплики по её событиям асинхронны.
Не допускать цикла «LLM отправила goto → мод отменил → LLM повторила goto».
Мод/адаптер согласует уступку приоритетной цели и публикует причину ожидания.

Приоритет назначения отделяется от безопасного момента передачи управления:
просьба принимается первой, но уже идущие всплытие, обработка смерти или корректное
завершение use требуют согласованного перехода. Причина задержки видна в UI.
Фоновая посадка не получает такого защитного статуса. Наличие моба в 32 блоках
не должно бессрочно блокировать просьбы. Ручной Stop прекращает автоматизацию явно.

## 4. Планировщик

Выбор модового навыка по весам → запуск → наблюдение результата → следующий навык.
TreeGrow — фоновая задача; Auto Defense — ситуативный контроллер, не случайное
задание «начни защищаться». Планировщик не вызывает LLM для построения процедур.

Старые фоновые farm/explore/hunt недоступны без соответствующего модового навыка.
Пользовательские веса сохраняются; текущая вероятность недоступного навыка — ноль,
с объяснением в Gradio. Нет модовой работы — наблюдаемый idle и ограниченная
переоценка доступности, без LLM на каждый тайм-аут.
Снабжение по потребностям, диагностика и отмена — служебные функции runtime;
они не разрешают фоновое планирование добычи/цепочек команд через LLM.

## 5. Dispatcher и проверка

Цель хранит source, priority, executor, requester, goal ID и world/session.
Executor: native_mod или llm_commands. Фоновая цель допускает только native_mod.
LLM получает общение/память, инструменты целей и командные tools для принятых
пользовательских задач вне модов. Правила проверяются исполнителем, не одним промптом.
AutomationRuntime независим от ChatAgent; метрики модового и командного маршрутов
считаются раздельно.

Приёмка: дерево игрока → мод; дерево планировщика → мод без LLM; follow игрока →
командный tool; командный executor планировщика → отказ; новая просьба прерывает
фон; нет бесконечного повторения отменённой команды; Stop не вызывает autoreplay.

Это уточнение требований. Новый dispatcher ещё не реализован; готовность API
модов к этим переходам проверяется отдельно.
