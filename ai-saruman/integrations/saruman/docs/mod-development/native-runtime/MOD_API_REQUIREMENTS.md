# Минимальный контракт модов для автономного runtime

Дата: 24 октября 2026. Это требования к интеграции, **не перечень уже существующих
Java-методов**. Фактические интерфейсы описаны в [проверке архитектуры](ARCHITECTURE_REVIEW_2026_10_24.md).

## 1. Общие правила

- API/version, mod/version и instance/world session публикуются явно.
- Mutations исполняются на client thread через очередь или корректный адаптер.
- Read-only snapshot не меняет мир и не инициирует задач.
- У запросов request ID, у запусков run ID; повтор одного запроса не создаёт дубль.
- accepted отделён от running и завершения; stop подтверждается освобождением
  собственных действий. Не использовать неидемпотентный toggle как внешний протокол.
- Snapshot содержит revision/sequence и признак обновления, а клиент хранит время
  его получения. Не считать старый owner=NONE достоверным после потери связи.
- Внешние операции не открывают новый сетевой сервер: можно использовать существующий Py4J.
- Публичная модовая команда и API используют одну задачу и одинаковые ограничения.

## 2. Auto Defense

Нужны операции явного включения/выключения и остановки с идемпотентным результатом.
Существующий getStatusJson остаётся основой наблюдения. Включение может быть
реализовано небольшим адаптером к runtime, но он обязан проверить enabled и
изменить его в одной операции на client thread, без имитации F8 из Windows.

В status нужны enabled, active/handing_over/recovering, owner, reason/error,
мир/сессия и свежесть. Только inCombat недостаточно: мод может владеть телом
во время спасения или восстановления без атакуемой цели.

Для внешних задач должна быть возможность делегировать их восстановление
runtime. Мод защиты не переигрывает произвольную lastLine одновременно с новой
задачей диспетчера. Старые команды не связываются с новым run только по последней
строке чата. Приоритетный Stop/новое намерение инвалидируют восстановление.

Потребность в зелье должна содержать роль/достаточную спецификацию компонентов
или использовать согласованный SupplyService-каталог, отличающий лечение от воды.
Мод по-прежнему не занимается выдачей снаряжения: эту роль выполняет runtime.

Мод/адаптер должен согласовать уступку приоритетной цели игрока и публиковать
ожидание/причину. Автозахват защиты не должен бесконечно отменять пользовательское
goto, а командный tool не может двигать тело параллельно с текущим владельцем.
См. [три канала действий](HYBRID_DISPATCH_POLICY.md).

## 3. TreeGrow

Нужен единый snapshot текущего/последнего запуска:

```json
{
  "api_version": 1,
  "run_id": "unique-run",
  "request_id": "unique-request",
  "world_session": "current-world",
  "sequence": 42,
  "state": "running",
  "stage": "fertilizing",
  "species": "oak",
  "planted": true,
  "grown": false,
  "position": [10, 64, 20],
  "bone_meal_issued": 3,
  "reason_code": null
}
```

Поле bone_meal_issued обозначает отправленные применения. Подтверждённое
потребление и фактический рост должны быть отдельными наблюдениями.

Запуск должен атомарно проверять свободу UnionClef и отсутствие чужого владения
Auto Defense. Проверка в Python перед отправкой полезна, но не исключает гонку
между проверкой и исполнением. Отказы busy/not_ready не создают новый run.

Для количественных заданий достаточно одиночного запуска, если runtime получает
однозначный результат и способен дедуплицировать его. Для строгого дуба/берёзы,
plant-only и уменьшенных бюджетов нужны соответствующие параметры/capabilities.
Пока их нет — они объявляются неподдержанными, не эмулируются скрытым старым кодом.

При смене места после использованного саженца гарантировать получение следующего
саженца. Исправить состояние, при котором species уже выбран, item израсходован,
а ветка приобретения недостижима.

При прерывании боем вернуть явный interrupted результат и сохранить данные
посадки. Нужен один из проверенных вариантов:

1. Приостановка и возобновление той же логической посадки с сохранением лимитов.
2. Отмена с координатами/стадией и последующее модовое reconcile/resume
   существующего саженца, без дублирования новой посадкой.

Без этого диспетчер сохраняет цель как прерванную и не обещает автоматического
продолжения уже посаженного дерева. Новая стартовая задача не доказывает resume.

## 4. Совместная приёмка перед переключением

- Защита включается/выключается из внешнего API без зависания use/движения.
- TreeGrow запускается из Py4J и возвращает однозначный идентификатор/статус.
- Появление моба во время посадки/удобрения: один owner, остановка старых действий,
  после боя восстановление по выбранному контракту, без replay чужой команды.
- Количество N даёт N различных подтверждённых результатов без вызова LLM между ними.
- Потерянный ответ start не вызывает второй запуск; Stop не отменяет чужой run.
- Смерть, смена мира и ручная отмена не оживляют прежнюю команду.
- Отказ /give не вызывает бесконечные запуски и повторную выдачу муки.
- Нет попыток Python-комбатанта/спасателя вмешиваться в native движение.

Проверять на закреплённых JAR, с независимыми assertions и видео для игровых
сценариев. Успешная сборка и чтение метода status сами по себе не закрывают приёмку.
