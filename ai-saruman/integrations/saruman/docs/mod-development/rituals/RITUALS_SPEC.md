# Arcane Rituals 0.1.0 — клиентский мод

## 1. Задача

Создать **строго клиентский Fabric-мод для Minecraft Java 1.21.11, Java 21**.
Он запускает четыре готовых косметических эффекта через стандартные серверные
команды `particle` и `playsound`. Мод устанавливается только у играющего персонажа.
Серверный JAR, датапак, ресурспак и установка мода другими игроками не нужны.
Зависимости клиента — Fabric Loader и Fabric API; версии сборки зафиксировать.
В fabric.mod.json задать environment=client и клиентский entrypoint.

Персонажу нужны права на используемые серверные команды. Наличие `/give` этого
не доказывает. Проверять команды в присланном сервером дереве команд; если нужная
команда недоступна, отказать без отправки. Сервер может дополнительно отказать
через плагин: отправка команды не подтверждает её выполнение.
Без прав не переключаться молча на эффект, видимый только своему клиенту.

## 2. Эффекты первой версии

Один запуск — **один выброс частиц и максимум один звук**, без повторяющихся кадров,
колец из десятков команд и постоянной ауры. Частицы исчезают естественным образом.
Центр фиксируется при отправке; эффект не следует за движущимся игроком.

| ID | Частицы и количество | Разброс X/Y/Z, блоки | Звук |
|---|---|---|---|
| `greeting` | `minecraft:enchant`, 40 | 0.4 / 0.7 / 0.4 | `minecraft:block.amethyst_block.chime` |
| `contemplation` | `minecraft:end_rod`, 16 | 0.6 / 0.2 / 0.6 | Нет |
| `displeasure` | `minecraft:smoke`, 12 | 0.4 / 0.5 / 0.4 | `minecraft:entity.evoker.prepare_attack` |
| `tree_blessing` | `minecraft:happy_villager`, 24 | 1 / 1 / 1 | `minecraft:block.enchantment_table.use` |

Скорость частиц 0.02. Звук: категория ambient, volume 0.4, pitch 1.0.
Первые три эффекта — у корпуса игрока, на 1 блок выше ног. Последний — на 0.5 блока
выше переданной точки. Координаты конечные, абсолютные, в текущем измерении,
не дальше 8 блоков от игрока. Числа форматировать с точкой независимо от языка ОС.
Получатели — игроки того же измерения в пределах 32 блоков от центра эффекта.
Селектор получателей центрировать на эффекте, не на произвольном исполнителе.
Проверить ID и синтаксис команд именно на 1.21.11.

## 3. Вызов человеком и агентом

Клиентские команды, обрабатываемые локально:

```text
/arcane-ritual play greeting
/arcane-ritual play contemplation
/arcane-ritual play displeasure
/arcane-ritual tree <x> <y> <z>
/arcane-ritual status
```

Для внешнего bridge предоставить публичный класс
`dev.arcane.rituals.api.RitualApi` с методами:

```java
public static String play(String preset);                 // первые три эффекта
public static String playAt(double x, double y, double z); // tree_blessing
public static String getStatusJson();
```

Мутации возвращают JSON `{"state":"queued","preset":"greeting","reason":null}`
либо state=rejected и причину. Вызов безопасен из чужого потока: действия с игрой
выполняются на client thread без блокирующего ожидания. Допускается один ожидающий
запрос, второй отклоняется как busy. Перед отправкой повторно проверить живого
игрока, соединение, тот же мир, доступность команд и дистанцию до точки.
После отправки status становится sent; это только передача команд серверу.
Причины отказа: busy, cooldown, not_in_world, command_unavailable, invalid_target,
unknown_preset. Пока запуск ожидает отправки, getStatusJson показывает queued;
до первого запуска — idle. Все ответы содержат state, preset и reason.
Клиентские команды используют ту же реализацию; серверу `/arcane-ritual` не отправлять.
Отказ второго вызова не заменяет уже ожидающий запрос.

Не чаще одного запуска в 5 секунд по монотонному времени, максимум две
vanilla-команды на запуск.
Отправлять их штатным сетевым API клиента, без эмуляции клавиатуры и чата игрока.
При выходе, смерти или смене мира ожидающий запрос отменяется как rejected/not_in_world;
после подключения заново не воспроизводится. Уже отправленные частицы не отменяются.

## 4. Границы реализации

Посох, опыт, определённый ник, другие игровые моды и LLM не нужны.
Не менять движение, взгляд, attack/use, слоты, здоровье, инвентарь или блоки.
`tree_blessing` не сажает дерево и не ускоряет рост.
В 0.1.0 не создавать GUI, редактор, БД, серверный протокол, историю запросов,
планировщик занятий или интеграцию с конкретным проектом персонажа.
Служебный status хранится локально, не рассылается в чат и не озвучивается модом.

## 5. Проверка и поставка

Собрать remapped JAR через Gradle Wrapper. Автотестами проверить выбор команд,
формат координат, дистанцию, cooldown и отказ при отсутствии доступа;
в тестах заменить сетевую отправку записывающим приёмником. Логи тестов — в консоль
или `build/`, без изменения исходников и создания `logs/` в корне проекта.

В отдельном мире проверить: четыре эффекта; запрет без прав без спама; обычную
ходьбу во время вызова; отмену ожидающего запроса при выходе; видимость и звук
со второго клиента без мода. Настройки клиента и расстояние влияют на восприятие.
Моки не подтверждают видимость другим игрокам. Недоступные игровые проверки
отмечать NOT_TESTED, а не PASS. Чужие моды и БД владельца для проверки не нужны.

Собрать готовый JAR, сохранить исходники и краткую инструкцию.

Справка: [клиентские команды Fabric 1.21.11](https://docs.fabricmc.net/1.21.11/develop/commands/basics#client-commands).
