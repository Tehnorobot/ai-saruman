# Auto Defense: правила реализации для Minecraft Fabric 1.21.11

Дата проверки: 20 октября 2026.

Документ для разработчика, включая GPT-6. Здесь описано, **как реализовывать**
мод и доказывать корректность. Требуемые возможности и политика находятся в
[универсальном ТЗ](AUTO_DEFENSE_SPEC.md), особенности окружения персонажа —
в [плане интеграции Saruman](SARUMAN_AUTO_DEFENSE_SPEC.md).

Это инженерный план. Новый мод ещё не написан/собран в рамках этой работы.
«Идеально на любом сервере» не является гарантией: нужны точная версия,
воспроизводимые испытания и опубликованные границы совместимости.
Не считать все пункты ниже уже подтверждёнными игровыми испытаниями.

## 1. Сначала зафиксировать воспроизводимый профиль

Локально прочитаны metadata установленных JAR и профиль запуска:

| Компонент | Наблюдаемый профиль | Как использовать |
|---|---|---|
| Minecraft | 1.21.11 | Целевая версия, без автоматического перехода на 26.x |
| Java | majorVersion 21 в launch profile | toolchain/release 21 для базовой сборки |
| Fabric Loader | 0.19.2 в библиотеках профиля | Начальная тестовая конфигурация |
| Fabric API | 0.141.3+1.21.11 | Начальная тестовая зависимость |
| UnionClef | mod ID altoclef, 1.21.11-0.95.61 | Только дополнительный compatibility-тест |
| Magical Scepter | 1.2.0, JAR для 1.21.11 | Только отдельный адаптер/compatibility-тест |

Присутствие JAR не доказывает, что он реально загрузился: проверять журнал загрузки.
Metadata Fabric API требует Java ≥21; metadata Magical Scepter — Loader ≥0.18.2
и Java ≥21. Это наблюдаемые ограничения зависимостей, не универсальные требования
к будущему standalone-моду. Минимальный Loader для релиза устанавливается тестом.

Для справочных имён в этом документе используется Yarn **1.21.11+build.6**.
Если разработчик выбирает Mojang mappings, нужно перевести все имена согласованно.
Чужой пример с Mojang-именами не является готовым Yarn-кодом.
Loom и Gradle Wrapper закрепить в совместимых точных версиях. Fabric описывает
изменения инструментария и mappings для этой версии в
[release notes 1.21.11](https://www.fabricmc.net/2025/12/05/12111.html).
Указанные там версии на дату публикации не объявлять «последними сегодня».

Создать build-manifest: Minecraft, Java, Loader, API, Loom, mappings, ОС,
commit исходников, SHA-256 production JAR, список активных дополнений.
Не использовать диапазон «все 1.21.x» без отдельной проверки каждой версии.

## 2. Обязательные инварианты

Ни один дополнительный «умный» приём не имеет права нарушать эти правила:

1. В текущем мире один владелец боевого управления и одно поколение lease.
2. Все изменения живого мира/игрока выполняются на client thread.
3. Решения используют согласованный снимок, действия повторно валидируются перед commit.
4. Действие со старым world/session, player UUID или lease generation отклоняется.
5. Отсутствие цели, безопасной позиции или предмета имеет конкретный reason code.
6. Боевой tick не ждёт Python, LLM, лог-файл, HTTP и завершение worker.
7. Известный отказ может вызвать другой план; неизвестный результат не повторяется вслепую.
8. Выстрел/удар не являются доказательством попадания или убийства.
9. Навигационный backoff не запрещает уже доступную дальнюю атаку.
10. Ручной Stop, смерть и смена мира освобождают собственный ввод и инвалидируют планы.
11. Еда, лук, щит и магия согласованы общим владельцем use/inventory.
12. Геометрия, cooldown, компоненты предмета и серверные правила проверяются по игре.

Инварианты оформить как unit/integration assertions и поля диагностики.
Не заменять их одними комментариями в исходниках.

## 3. Структура кода и направления зависимостей

```text
core/            snapshots, policy, state machine, scoring, geometry, timers
fabric-runtime/  lifecycle, InputFrame commit, vanilla interactions, HUD
api/             публичный фасад, версии DTO, очередь запросов, журнал событий
compat-unionclef/ отдельное дополнение: захват/возврат и подавление чужих записей
compat-scepter/   отдельное дополнение: реальные компоненты и вызовы мода
tests/           policy/replay, client-game tests, сценарные миры и отчёты
```

Core не импортирует UnionClef, Py4J, Redis и классы личности персонажа.
Чистая политика работает с DTO и тестируется без поднятого Minecraft.
Fabric adapter переводит DTO в настоящие игровые операции.
Один основной JAR содержит всё необходимое для standalone vanilla-боя.

Optional addon не должен загружать отсутствующие классы через static initializer.
Проверить регистрацию mixin/entrypoint и classloading без обеих optional-зависимостей.
Не копировать боевое ядро в адаптер или Python.

## 4. Снимок мира и разделение времён

Собирать WorldSnapshot на client thread:

```text
session, world identity, dimension, local player UUID, logical tick
health/absorption, hunger, air, pose, velocity, grounded/fluid state
inventory revision, selected/offhand item, components/cooldowns
tracked targets/projectiles: UUID, entity ID, bounds, motion, observed facts
локальная карта коллизий, текущий input owner и revision намерения
```

В worker передаются только неизменяемые данные; не Java Entity, ItemStack и World.
Результат worker содержит исходные session/tick/map revision и конечный срок.
При применении проверить актуальность мира, текущую позицию и ближайший сегмент.
Новый результат старого поиска не может отобрать управление у уже начавшегося боя.

Разделить клиентские logical ticks, наблюдаемые серверные обновления и монотонное
время watchdog. Они не считаются одной шкалой. Лаг сервера не повод искусственно
ускорять атаки; пауза одиночной игры не расходует игровые таймеры.
Не использовать System.currentTimeMillis для измерения интервалов.

## 5. Порядок работы tick и точка применения ввода

Логический цикл контроллера:

```text
приём приоритетных запросов Stop и смены сессии
→ snapshot текущего игрока и подтверждённых событий
→ смерть/вода/критический риск
→ владение управлением
→ цель и одна тактика
→ план движения и взаимодействия
→ финальная проверка
→ один согласованный commit InputFrame/ActionPlan
→ публикация snapshot/events
```

Регистрация START/END_CLIENT_TICK задаёт границы тика, но сама по себе не
гарантирует правильный момент изменения движения. В 1.21.11 KeyboardInput.tick
формирует поля playerInput и movementVector. Запись до их пересчёта может быть
перезаписана, а поздний END_CLIENT_TICK может примениться только в следующем тике.
Источник: [KeyboardInput 1.21.11+build.6](https://maven.fabricmc.net/docs/yarn-1.21.11%2Bbuild.6/net/minecraft/client/input/KeyboardInput.html).

Реализовать InputDriver в проверенной точке до потребления ввода игроком.
Допустим минимальный mixin вокруг фактического вычисления/потребления input;
точную точку выбрать по исходникам целевой версии и подтвердить трассировкой.
Не угадывать injection descriptor по старой версии.

Клавиши F8/меню обрабатываются отдельно; пример регистрации есть в
[официальном образце 1.21.11](https://github.com/FabricMC/fabric-docs/blob/main/reference/1.21.11/src/client/java/com/example/docs/keymapping/ExampleModKeyMappingsClient.java).
Порядок callback разных модов не является механизмом эксклюзивного управления.

## 6. InputFrame и защита от залипания

Сформировать полный кадр намерения, например:

```java
// Собственный DTO проекта; это не класс Minecraft API.
record InputFrame(
    String session, long generation, long tick, long validUntilTick,
    float forward, float sideways, float yaw, float pitch,
    boolean jump, boolean sneak, boolean sprint,
    UseMode useMode, AttackIntent attack
) {}
```

InputFrame живёт один tick, максимум два для явно разрешённого случая.
Значения движения ограничены допустимым диапазоном; диагональ нормализуется
с учётом выбранного ванильного пути ввода. Координаты/скорость игрока напрямую
не изменяются ради движения и уклонения.

Forward, use, jump и щит каждый tick подтверждаются новым кадром. Пропавший план
не оставляет прежнюю кнопку зажатой. Устаревший cleanup не делает releaseAll
после выдачи lease новому владельцу: освобождаются только действия своего поколения.
При возврате ручного управления учитывать актуальные физические клавиши пользователя.

Проверять не только нажатия, но и записи false/reset: старый мод может отпускать
кнопки нового владельца. При полном зависании client thread cleanup возможен
после возобновления тика, а не магически во время остановки JVM.

## 7. Изоляция UnionClef в установленной версии

Наблюдённый JAR: unionclef-1.21.11-0.95.61.jar, mod ID altoclef.
SHA-256 прочитанного файла:

```text
76bbb677d2f8294e6d2de98b554f81818ae15605ef8a82ff7e1d3b9b82555d1b
```

Чтением bytecode подтверждены следующие пути, без вызова управляющих методов:

| Участок | Наблюдение | Следствие |
|---|---|---|
| PauseCommand | Сохраняет задачу, stop UserTaskChain, disable TaskRunner | Есть основа приостановки |
| TaskRunner.disable | Останавливает цепочки, меняет behaviour stack | Нужен проверенный restore |
| AltoClef.stopTasks | Отмена задачи и Nav.cancelAll | Есть остановка навигации |
| InputControls | releaseAll и обработчики pre/post tick | Нужно проверить нажатия и позднюю очистку |
| AltoClef.onClientTick | InputControls и WeaponSelector hooks вне TaskRunner.tick | Пауза runner не доказывает изоляцию |

Во время native combat lease закрыть пути записи movement/rotation, sprint/jump,
selected slot/offhand и attack/use от старого контроллера, включая поздние результаты.
Просто mobDefense=false, @pause или hasActiveTask=false не являются доказательством.
Сохранить необходимые trackers/наблюдения и канал bridge.

Если публичных точек недостаточно, сделать отдельный compatibility addon с
версионными mixin/accessor. Проверять точные targets и поддерживаемую версию;
неизвестная версия не получает capability exclusive_control. При несовместимости
не угадывать имена и не заявлять успешный handoff. Обновление UnionClef требует
повторной проверки; один class name не гарантирует одинаковое поведение.

Записывать тестовую трассу: tick, channel, writer, generation, accepted/rejected.
При native lease не должно быть принятых чужих записей ни true, ни false.
Адаптеры известных модов необходимы: общий API не способен запретить произвольному
стороннему mixin напрямую менять состояние игрока.

## 8. Оружие: локальный слот и серверный порядок

Выбор слота у клиента и использование того же предмета сервером — разные факты.
Операции идти должны в порядке:

```text
проверить инвентарь/слот → выбрать предмет → штатно синхронизировать выбор
→ заново проверить lease/цель → взаимодействовать → наблюдать результат
```

В Yarn interaction manager имеет private syncSelectedSlot и public attackEntity,
interactItem, clickSlot, stopUsingItem. Это не разрешение вызывать private метод
как public. Использовать подходящий штатный путь или проверенный accessor.
Источник: [ClientPlayerInteractionManager 1.21.11](https://maven.fabricmc.net/docs/yarn-1.21.11%2Bbuild.3/net/minecraft/client/network/ClientPlayerInteractionManager.html).

Не посылать выбранный слот каждый tick без изменения. При custom mod callback
проверять, выполняет ли он vanilla-синхронизацию: ранее у Magical Scepter
наблюдался callback с отдельным пакетом атаки, поэтому нужна явная синхронизация.
Сетевой порядок сохранять через один штатный клиентский канал, без обхода протокола.

Не выдумывать обязательный server-selected-slot ACK, если протокол его не даёт.
Различать EQUIPPED_LOCAL, SELECTION_SENT и SERVER_EFFECT_OBSERVED.
При переносе предмета из inventory использовать clickSlot с актуальным handler,
revision и slot mapping. Minecraft inventory index и screen slot ID не одно и то же.
Открытый контейнер и полная сумка обрабатываются явно; чужие предметы не выбрасывать.

## 9. Настоящий melee и современные компоненты

Копировать последовательность **текущего vanilla attack flow**, проверив её
по исходникам 1.21.11: необходимые pre-attack/cooldown bookkeeping, interaction
manager, взмах и сброс локального счётчика. Один attackEntity сам по себе не
доказывает воспроизведение полного поведения обычного клика.

Справочные имена PlayerEntity: getAttackCooldownProgress, getEntityInteractionRange,
canAttackEntityIn. Они присутствуют в
[Yarn 1.21.11+build.6](https://maven.fabricmc.net/docs/yarn-1.21.11%2Bbuild.6/net/minecraft/entity/player/PlayerEntity.html).
Учитывать оружейные компоненты и фактические условия выбранного предмета;
перед вызовом проверить bounding box, препятствия и допустимость цели.
Не подставлять дополнительную reach ради удобства.

Измерять расстояние до подходящей точки hitbox с учётом vanilla-правил,
а не от центра игрока до центра моба с фиксированным порогом «1 блок».
Не hardcode одинаковые damage/attack speed для всех мечей/топоров.
Нужны проверки sweep и посторонних существ. Удар не должен повторяться из двух
источников: либо vanilla interaction flow, либо оружейный adapter, один dispatch.

В 1.21.11 существуют компоненты MINIMUM_ATTACK_CHARGE и BLOCKS_ATTACKS;
не переносить старую модель предметов без проверки:
[DataComponentTypes](https://maven.fabricmc.net/docs/yarn-1.21.11%2Bbuild.6/net/minecraft/component/DataComponentTypes.html).
Порог готовности атаки — параметр политики поверх настоящих игровых ограничений,
не изменение самих cooldown/атрибутов.

## 10. Лук: автомат состояний и отмена без случайного выстрела

Делать явные переходы SELECT → START_USE → DRAW → AIM → CHECK → RELEASE → OBSERVE.
Лук начинает использоваться штатным interactItem. Количество use ticks, наличие
стрел и актуальная рука проверяются по фактическому состоянию игрока.
BowItem.getPullProgress и onStoppedUsing описаны в
[API 1.21.11](https://maven.fabricmc.net/docs/yarn-1.21.11%2Bbuild.1/net/minecraft/item/BowItem.html).

Критический случай: **stopUsingItem не следует считать безопасной отменой** —
для лука прекращение использования связано с выпуском стрелы. Реализовать отдельный
cancelDrawWithoutShot по проверенному vanilla-пути выбранной версии и подтвердить
игровым тестом: нет нового снаряда и нет расхода стрелы. Не утверждать заранее,
что произвольная смена слота или локальный clearActiveItem гарантируют серверную отмену.

Перед выпуском ещё раз проверить цель, поколение, руку, draw state и траекторию.
Мирный игрок вошёл в траекторию — не отправлять release; перейти в проверенную
безопасную отмену либо безопасное ограниченное ожидание. На неизвестной ситуации
не выполнять опасный fallback «просто отпусти use».
До реализации и испытания безопасной отмены bow capability не считается готовой.

Один draw-cycle имеет action ID. RELEASE отправляется один раз; при лаге результата
наблюдать штатное состояние/стрелы, не генерировать повторные release-пакеты.
В частности, emergency Stop во время натяжения обязан пройти этот же проверенный
путь отмены, а не универсальный cleanup, случайно выпускающий стрелу.

## 11. Баллистика и прицеливание

Позиция наведения — точка в текущем hitbox, исходная позиция — реальная точка
выпуска/глаз согласно механике оружия. Вычисления используют один tick snapshot.
Упредить цель по наблюдаемой скорости, оценивая время полёта для данного натяжения.
При резком изменении движения пересчитать решение, а не стрелять в старые координаты.

Модель траектории должна соответствовать порядку интеграции vanilla: скорость,
сопротивление среды, гравитация и collision sweep по фактическому коду версии.
Не вписывать случайные константы из гайда старой версии. Для начала поддержать
обычный лук/стрелы; прочие projectile types объявлять отдельными capabilities.

Проверять каждый отрезок полёта с размером снаряда и запасом неопределённости,
блоки, hitbox цели и возможные пересечения защищённых существ.
Движение других игроков предсказывается неточно: при опасной неопределённости
лучше отменить выстрел/сменить позицию. Это не обещание абсолютного отсутствия
случайного урона при любом сетевом изменении после уже выпущенной стрелы.

Есть конечный срок поиска решения и ограниченный перебор углов/времени.
Нет решения — NO_FIRING_SOLUTION, переход к другой тактике. Нельзя навсегда
зависнуть в AIMING или крутить камеру быстрее, чем исполняется план движения.

## 12. Щит, движение и единый use channel

Щит работает через реальный предмет/руку, начало использования, правильное
направление и игровую готовность. BLOCKS_ATTACKS и условия конкретного предмета
важнее hardcode «зажат use — значит защищён». Учитывать disabled/cooldown состояние.
Решение поднять щит принимает тот же контроллер, который управляет луком и едой.

Приоритет операции use: немедленное спасение → проверенная защита/отмена оружия →
критическое лечение → атака по выбранной тактике. Это часть состояния, а не три
параллельных таймера. Перед передачей use проверить корректное завершение старого действия.

Уклонение рассчитывается по доступному времени до контакта снаряда и безопасному
движению. Если времени недостаточно, показывать best-effort, а не «стрела заблокирована».
Факт блока/урона подтверждать наблюдениями с указанным уровнем уверенности.

Не включать вечный jump или бесконечное использование щита. Любой hold имеет
владельца, срок и условие снятия.

## 13. Собственное боевое движение

Разделить глобальную цель позиции и локальный контроллер следующего шага.
Контроллер управляет vanilla input, не устанавливает координаты или velocity
для обхода физики. UnionClef не нужен для реализации native_combat_movement.

Для melee вычислять желаемую полосу дистанции по оружию/геометрии. Для лука —
позицию с траекторией и возможностью уйти под защиту. Выбор не обязан вести
в точку, где стоят ноги врага.

Стрейф строить в локальном базисе относительно направления к цели. Перед каждым
шагом проверять swept volume аватара, опору, ступень/высоту, воду, край и соседей.
Выбрать лучшую из нескольких доступных комбинаций forward/sideways; сохранять
направление при близких оценках, менять его по препятствию/новой угрозе.

Пример собственной функции оценки, коэффициенты настраиваются испытаниями:

```text
score = качество позиции для текущего оружия + укрытие + сохранённый прогресс
        - риск снаряда - риск падения/воды - столкновения - недавний провал
```

Все кандидаты сначала проходят жёсткие геометрические ограничения, затем scoring.
Не компенсировать опасную яму большим положительным score за близость к врагу.
Sprinting/критические удары/сброс спринта включать после испытания соответствующих
ванильных условий; постоянный прыжковый спам не считать продвинутым PvP.

## 14. Маршрут, тупик и вода

Планирование ограничено бюджетом узлов/времени. Начальный пример бюджета:
не больше 200 expansions и 1 мс за tick, остальное продолжить позже; конкретные
значения подобрать измерениями. Не блокировать реакцию на удар ради A*.

Считать прогресс по реальному перемещению и качеству позиции, а не факту принятого
goto. Server correction/rubber-band инвалидирует предположенный прогресс.
Следить за повторением сегментов A→B→A; после повторного провала менять решение.
История попыток и абсолютный срок не сбрасываются при каждом новом subtask.

Если враг в воде — сухое сближение/выстрел с берега, без погружения вслед.
Если сам игрок под водой — снять мешающий боевой use безопасным способом,
поддержать всплытие и выбрать проверенный выход. Не ждать появления запаса воздуха
самостоятельно и не повторять stopPathing вместо движения.

После берега заново проверить grounded/fluid/позицию и угрозы. Прежний мокрый
маршрут не восстанавливать. При внешнем спасателе действуют те же generation/lease
и запрет двух одновременных владельцев; иначе мод спасается локально.

## 15. Цели, атрибуция и качество знаний

Сущность хранится как session + UUID; entity ID используется только в текущем мире.
Каждая атака заново проверяет защищённость, жизнеспособность и требования профиля.
Неизвестные/неполные сведения не превращаются в разрешение атаковать игрока.

Для ответа игроку использовать реальное событие урона по локальному игроку
и однозначно установленный источник/владельца снаряда. Снижение HP и ближайший
ник не дают такого доказательства. Проверить семантику packet/callback на тестах.

Телеметрия разделяет:

| Наблюдение | Допустимое утверждение |
|---|---|
| Отправлено взаимодействие | ATTACK_SENT |
| Уменьшилось наблюдаемое HP цели | OBSERVED_HEALTH_DROP |
| Есть достоверная собственная атрибуция | OWN_DAMAGE_CONFIRMED |
| Цель исчезла/выгрузилась | TARGET_LOST |
| Достоверно наблюдается смерть | TARGET_DEAD |
| Подтверждена смерть от нашей атаки | OWN_KILL_CONFIRMED |

У неизвестного результата хранить action ID и причину. Не обещать точную
статистику собственных убийств на vanilla-сервере, если источник не даёт атрибуцию.
Защита и следующий допустимый бой не должны ждать LLM-объяснения этих событий.

## 16. API и восстановление после сбоев

Публичный API выдаёт immutable snapshot; мутации кладутся в ограниченную очередь.
Проверять request ID, expected session, revision конфигурации и generation.
При повторе одного ID вернуть тот же результат; другой payload с тем же ID отклонить.
emergencyStop не стоит за обычными запросами и не зависит от старой сессии клиента API.

Локальный бой не требует heartbeat Python. При потере транспорта мод продолжает
свой самостоятельный цикл согласно enabled/профилю. Внешний runtime не запускает
другого бойца, пока release native не подтверждён.
Watchdog, пауза и ошибка не должны сами порождать новый бесконечный цикл отмен.

Изолировать ошибки HUD, логов и optional provider. Ошибка боевого input driver
инвалидирует его frame и включает наблюдаемое безопасное восстановление.
Не ловить исключение молча и продолжать показывать ACTIVE при отсутствии действий.
Неподдерживаемая версия адаптера — capability false и понятная диагностика.

## 17. Доказательство работоспособности и порядок разработки

Внедрять вертикальными срезами, каждый доводить до наблюдаемого результата:

1. Пустой production JAR: чистый клиент 1.21.11, F8, lifecycle, release после Stop.
2. InputDriver и lease: движение/поворот/слот и тесты позднего чужого cleanup.
3. Цель и melee: дальность/cooldown/удар/анимация/достоверный результат.
4. Собственная навигация: сближение, стрейф, дистанция, тупик и вода.
5. Щит, отход при 4 HP, еда с одним use channel.
6. Лук: сначала надёжное начало/отмена/выпуск, затем баллистика и упреждение.
7. Профили, публичный API, события и настройки.
8. Optional UnionClef addon: полная изоляция и восстановление, затем Scepter addon.
9. Полная приёмка универсального ТЗ и интеграционного плана.

Тестировать отдельно чистую политику, работу загруженных mixin и реальный gameplay.
Для client/server game tests использовать примеры именно 1.21.11:
[Fabric automated testing 1.21.11](https://github.com/FabricMC/fabric-docs/blob/main/versions/1.21.11/develop/automatic-testing.md).
Не копировать актуальную страницу для 26.x без проверки. Dev run не заменяет
запуск remapped JAR обычным launcher. После успешной сборки испытать оба варианта.

Минимальные матрицы: clean Fabric; +UnionClef; +Scepter; +оба; без OP/с OP;
singleplayer и отдельный сервер 1.21.11; 0/100/200 мс RTT в контролируемом тесте.
Для тестов новых сценариев менять один фактор за раз и сохранять seed/координаты,
экипировку, difficulty, gamerules, моды, версии, исходное HP и результаты.
Не активировать самостоятельно серверные соглашения/публикацию ради CI.

Для сравнения улучшений повторить заданный сценарий, например 20 раз:
зомби у края, скелет 16 блоков, утопленник с трезубцем за водой, смешанная группа,
мирный игрок в траектории, переход Stop во время натяжения, respawn с оружием.
Публиковать успешность, смерти, полученный урон, расход стрел и причины отказов.
Количество прогонов — инженерная договорённость, не доказательство совершенства.

Снимать p50/p95/p99 для perception→decision→input и отдельно сетевых последствий.
Записывать CPU по стадиям, TPS/RTT, GC и принятые чужие записи ввода при lease.
Не смешивать время решения мода со временем полёта стрелы или ответом сервера.
Числа без названного профиля, сценария и оборудования не считаются результатом.

К выпуску приложить build-manifest, SHA-256, логи/отчёт, таблицу PASS/FAIL/NOT_TESTED
и известные ограничения. Если нет реального теста — так и написать. Качество
«top PvP» не подтверждается одной победой над неподвижным мобом.

## 18. Чеклист перед передачей JAR

- [ ] Production JAR запускается в закреплённом профиле без optional модов.
- [ ] Все обязательные возможности основного ТЗ реализованы, а не только объявлены.
- [ ] Нет Python/LLM в боевом цикле; нет blocking waits на client thread.
- [ ] Один InputFrame/lease; проверены поздние reset и очередь старых запросов.
- [ ] Оружие синхронизируется, cooldown/reach/компоненты соответствуют версии.
- [ ] Отмена лука и Stop не выпускают стрелу в защищённую цель.
- [ ] Собственный контроллер движения работает при остановленном UnionClef.
- [ ] Вода вызывает фактическое всплытие/выход, а не один статус.
- [ ] Смерть/respawn/смена мира не восстанавливают старый ввод и цель.
- [ ] Статусы отражают факты; нет fabricated попаданий, блоков и убийств.
- [ ] Пройдены отдельные испытания совместимости, handoff и restore.
- [ ] Опубликованы измерения и ограничения; Git/publish выполняет владелец.

Применять этот документ вместе с функциональным ТЗ. Не менять требования профиля
втихую ради прохождения теста. Не считать новое руководство уже реализованной
интеграцией с текущей системой Saruman.
