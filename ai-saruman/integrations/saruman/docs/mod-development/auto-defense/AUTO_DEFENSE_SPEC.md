# Auto Defense 0.2.0 — техническое задание для реализации

Дата: 20 октября 2026. Документ описывает требования к будущей реализации,
а не подтверждённые возможности существующего JAR.

Это основное ТЗ универсального публичного мода. Правила персонажа и план
подключения к конкретному проекту находятся отдельно:
[интеграция с Saruman](SARUMAN_AUTO_DEFENSE_SPEC.md). Для обычного пользователя
этот проект, его исходники, Python и интеграционные дополнения не требуются.
Auto Defense — рабочее название; перед публикацией отдельно выбрать окончательные
название, namespace и Java package. После публичного релиза API их не менять молча.

Технические правила реализации и проверки конкретной версии:
[руководство для Minecraft 1.21.11](AUTO_DEFENSE_IMPLEMENTATION_GUIDE_1_21_11.md).
Читать вместе с этим функциональным ТЗ.

## 1. Задание разработчику

Реализуй Minecraft Fabric мод `auto_defense` для **Minecraft Java 1.21.11**.
Он управляет атакой и защитой локального игрока, работает после включения F8
и через публичный Java API. В боевом цикле нет LLM, HTTP, STT/TTS, Python RPC,
ожидания текста модели и имитации нажатий клавиатуры средствами Windows.

После включения мод наблюдает за загруженными существами в радиусе 32 блоков,
выбирает допустимую угрозу, перехватывает управление, использует меч, топор, лук
и щит, целится, сближается, ищет укрытия, уклоняется, преследует и отступает.
При здоровье **не больше 4 HP из 20** приоритет — выжить и восстановиться.
После устранения угроз управление освобождается для игрока или планировщика.

Это мод атаки/защиты. Посадка, сбор ресурсов, социальная память, общение,
обычные задания, управление контейнерами и выбор занятий остаются вне мода.
Еда, снабжение оружием и выход из воды входят только как необходимые функции боя.
Автоматическое возрождение может обслуживаться внешним контроллером;
после смерти этот мод обязан освободить управление и корректно пережить respawn.

Выполни реальную реализацию, сборку и доступные проверки. Не заменяй механику
заглушками и не называй успешную компиляцию подтверждением игрового поведения.
Если игровых испытаний нет, явно перечисли непроверенные сценарии.

## 2. Среда и зависимости

- Зафиксировать совместимые Minecraft, Java toolchain, Fabric Loader, Fabric API,
  Loom, mappings и Gradle Wrapper в проекте. Не использовать динамические `+` версии.
- Проверять имена методов по mappings именно 1.21.11. Выбрать одну систему имён
  внутри исходников; не смешивать Yarn, Mojang и intermediary произвольным образом.
- Клиентская основа работает без Python, Redis, внешней сети и серверного компонента
  этого мода. Сервер остаётся авторитетом для предметов, урона, дистанций и cooldown.
- UnionClef и Magical Scepter — отдельные адаптеры. Отсутствие одного из них не
  должно вызывать ошибку загрузки основного мода.
- Отдельный серверный компонент для расширенной телеметрии допустим в будущем;
  базовая атака/защита не должна требовать его для запуска.
- Сборка должна отдавать remapped production JAR, исходники и README.

Обычная установка: пользователь ставит Fabric Loader, Fabric API и один основной
JAR Auto Defense, запускает игру и включает защиту F8. В JAR включены боевое ядро,
стабильный API, локальная навигация, настройки и HUD. Дефолтная конфигурация не
содержит имён персонажей, абсолютных путей, адресов Redis или секретов.
По умолчанию используются наличные предметы; автоматическая выдача командами —
отдельная явно включаемая настройка, даже если пользователь имеет OP.

Разделение исходников допускается на core, fabric-runtime и api, но не требовать
от обычного пользователя установки трёх дополнительных библиотечных JAR.
UnionClef и Magical Scepter подключаются необязательными дополнениями с явными
зависимостями; базовая сборка и vanilla-бой работают без их JAR.
Дополнения используют публичные extension points, а не копии CombatController.

Официальный пример Fabric для 1.21.11 использует client tick event и регистрацию
клавиши; клиентские команды регистрируются отдельно от серверных:
[клавиши и tick](https://github.com/FabricMC/fabric-docs/blob/main/reference/1.21.11/src/client/java/com/example/docs/keymapping/ExampleModKeyMappingsClient.java),
[клиентские команды](https://github.com/FabricMC/fabric-docs/blob/main/reference/1.21.11/src/client/java/com/example/docs/client/command/ExampleModClientCommands.java).
Систему mappings и совместимость сборки сверять с
[примечаниями Fabric к 1.21.11](https://www.fabricmc.net/2025/12/05/12111.html).

## 3. Архитектура и задержки

Сделать единый CombatController с конечным автоматом состояний. Разделить наблюдения,
политику целей, владение управлением, навигацию, оружие, щит, еду и диагностику.
Подсистемы возвращают рекомендации контроллеру, а не независимо нажимают кнопки.

Рекомендуемые компоненты:

```text
AutoDefenseApi         — стабильная граница для других модов и внешних контроллеров
CombatController       — состояния и выбор следующего действия
ThreatSensor/Policy    — существа, снаряды, доказательства нападения, допустимость
ControlArbiter         — единый владелец движения/поворота/инвентаря/use/attack
EquipmentManager       — наличное оружие, выдача, подтверждение, боеприпасы
Melee/Bow/Shield       — конкретные игровые взаимодействия
CombatNavigation       — сближение, укрытие, уклонение, отступление
Food/WaterSafety       — восстановление и немедленное спасение
CombatTelemetry        — HUD, snapshots, события и показатели задержек
UnionClefAdapter       — приостановка и передача управления навигацией
MagicalScepterAdapter  — необязательная магия через настоящий API установленного мода
```

Подписаться на клиентский tick. Критическое состояние собственного игрока,
проверка владения и применение управляющих действий — каждый tick.
Обновлять ближайшие угрозы минимум раз в два ticks; подтверждённый урон принимать
событием, без ожидания полного сканирования.

Цель по задержке: решение о срочной защите за 1–2 игровых ticks после доступного
наблюдения. При нормальных 20 TPS это около 50–100 мс; это не гарантия сетевого
попадания и не обещание таких сроков при лаге сервера/клиента.

В client/render thread запрещены sleep, ожидание Future, блокирующий сетевой/
дисковый I/O и полный A*
без ограничения работы. Предварительная цель CPU: лёгкий боевой tick p95 ≤ 1 мс,
p99 ≤ 3 мс на указанной в отчёте машине. Измерить фактически, а не декларировать.
Дорогой поиск пути разбивать на ограниченные порции либо считать по неизменяемому
снимку вне client thread; чтение/изменение живого мира из worker запрещено.
Вернувшийся маршрут проверять по world/session, возрасту и актуальным блокам.

Сканировать сущности, а не все блоки куба 65×65×65 каждый tick. Для маршрута
собирать ограниченную локальную карту и расширять её по мере движения.
Перегрузка телеметрии не должна задерживать защиту.

## 4. Включение и жизненный цикл

- F8 переключает enable/disable; клавиша переназначается в настройках Minecraft.
- При запуске игры по умолчанию disabled. Bridge может явно включить мод через API.
- Enabled означает наблюдение, а не постоянное владение телом.
- В меню, без мира/игрока, при отключении, смене измерения и смерти отпустить
  все действия, отменить свои маршруты, очистить ссылки на сущности и боевые намерения.
- Не переносить UUID/entity ID и доказательства нападения между world sessions.
- После возрождения заново проверить игрока и инвентарь; прежнюю цель не атаковать
  автоматически. Новые угрозы наблюдать заново, если enabled сохранился в сессии.
- Любая ошибка подсистемы завершается ограниченным восстановлением либо безопасным
  освобождением её действий. Залипшие forward/use/shield недопустимы.
- Пауза игры не расходует игровые таймеры; watchdog зависшего API измерять
  монотонным временем отдельно. Не измерять интервалы календарными часами.

## 5. Цели и доказательства нападения

Радиус 32 — трёхмерное расстояние от игрока, настройка по умолчанию.
Источники: существа, реально загруженные клиентом, видимость, координаты,
здоровье, движение, тип, состояние воды, доступное оружие и наблюдаемые снаряды.
Не выдавать отсутствие существа в клиентском мире за его смерть.

В стандартном профиле защищены жители, странствующие торговцы, големы, скот, питомцы,
прочие животные и декоративные сущности. Запрет действует даже при нанесённом ими
уроне. При нападении защищённого существа — щит, укрытие, дистанция, но не ответный урон.

Известные враждебные мобы допускаются без ожидания их первого удара.
Нейтральные/условно агрессивные виды не становятся целями только по общей иерархии
Monster: учитывать игровую агрессию и реальные нападения. Неизвестные модовые
виды по умолчанию не атаковать; поддержать явную конфигурацию классификации.
Исключение защищённых существ всегда сильнее классификации hostile.

В стандартном профиле игроку можно отвечать только после достоверного игрового
события урона **по локальному игроку**.
Ущерб от падения, огня, утопления и нахождение игрока рядом этого не доказывают.
Текст чата и просьба «убей игрока» не создают доказательство нападения.
Для стрелы/трезубца учитывать реального владельца, если источник позволяет
однозначно установить его UUID. Не назначать ближайшего игрока виновником.
Если атрибуция недоступна, показывать unknown_attacker и защищаться без ответной атаки игрока.
Использовать настоящий damage packet/callback выбранной версии, проверив его
семантику; отправная точка для исследования —
[mapping EntityDamageS2CPacket 1.21.11](https://github.com/FabricMC/yarn/blob/1.21.11/mappings/net/minecraft/network/packet/s2c/play/EntityDamageS2CPacket.mapping).

Доказательство нападения хранить 20 секунд игрового времени после последнего
подтверждённого удара: victim UUID, attacker UUID, источник, время, world session.
Не продлевать его своими атаками или словами игрока. Смерть/смена мира очищают его.
Для игроков предел ответного преследования в стандартном профиле 12 блоков; общий радиус
обнаружения 32 не отменяет это отдельное ограничение.

Выбор цели: свежий подтверждённый нападающий, опасный стрелок с линией атаки,
близкая непосредственная угроза, затем остальные допустимые цели.
Учитывать достижимость и риск пути; не переключаться между равными целями каждый tick.
Новая более опасная угроза может немедленно прервать текущую атаку.
Пример начального hysteresis: удержание цели 500 мс, кроме смерти/потери допустимости,
спасения или появления существенно более опасного противника.

Моб за стеной обнаружен, но выстрел через стену запрещён. Предпочитать доступную
угрозу вместо бесконечных попыток достать недоступную.

## 6. Владение управлением и независимые интеграции

Очередность: **ручной аварийный Stop → смерть/спасение из воды → критическое
отступление → бой → задачи игрока и обычные занятия**.
При низком здоровье отступление имеет приоритет над продолжением атаки.

Ввести lease/token управления с owner, generation и world session. Движение,
поворот, выбранный слот, attack/use и offhand координируются одним контроллером.
Нельзя одновременно стрелять из лука, есть и держать щит как независимые действия.

В integrated mode ядро продолжает самостоятельно вести бой. Внешний контроллер
подключается к API и адаптеру координации, сохраняя обычные задачи за пределами
ядра. Имена его классов/настроек не должны попадать в универсальный CombatController.
Конкурирующие боевые системы отключаются или согласованно уступают управление.
Нельзя одновременно выполнять один бой двумя контроллерами.

Захват срочной защиты не должен ждать polling внешнего процесса или ответа LLM. Адаптер
приостанавливает/останавливает нативную фоновую задачу и перехватывает ввод.
Низкоприоритетные управляющие запросы при занятом lease отклоняются с busy/owner,
включая устаревшие запросы bridge. Одного информационного owns_controls в JSON
недостаточно, если другие контроллеры фактически продолжают двигать аватар.

ControlArbiter гарантирует координацию запросов, проходящих через его API и
поддерживаемые адаптеры. Он не может автоматически управлять произвольным модом,
который игнорирует этот протокол и напрямую меняет ввод. Для такого сочетания
показывать CONTROL_CONFLICT и не объявлять совместимость без отдельной проверки.
Адаптер UnionClef реализуется отдельно от ядра и не обязателен обычному игроку.

Сохранять checkpoint чужой задачи только поддерживаемым адаптером. Возобновлять
однократно после подтверждённого завершения боя, остановки боевого маршрута,
безопасного состояния и проверки актуальности intent/world. Ручной Stop,
новая задача, смерть и смена мира отменяют checkpoint. Не перезапускать исходное
задание с нуля и не обнулять его лимиты. Если безопасного resume нет, вернуть
управление планировщику со статусом resume_required, не выдумывать восстановление.

В standalone mode после боя просто освободить управление игроку. В integrated
mode обычный ручной ввод не должен случайно останавливать автономного персонажа;
отдельный аварийный Stop работает в обоих режимах.
Для standalone поддержать manual override: осмысленный ввод движения/мыши
приостанавливает автоматический бой до явного продолжения.

Приоритеты, защищённые существа, радиусы и варианты тактики описываются профилем.
Стандартный профиль self_defense работает сразу после установки. Дополнительный
профиль персонажа задаёт ограничения через API/config, не создаёт отдельную
реализацию боя. Обязательные ограничения активного профиля нельзя снять отдельной
низкоприоритетной заявкой на атаку. Чат игры не является источником конфигурации.

## 7. Состояния и переходы

Минимальные состояния:

| Состояние | Смысл и выход |
|---|---|
| DISABLED | Нет наблюдения/управляющих действий; включение переводит в IDLE |
| IDLE | Наблюдение, тело свободно; допустимая угроза запускает захват |
| ACQUIRING_CONTROL | Ограниченный захват/остановка прежнего движения |
| APPROACHING | Короткий безопасный подход; вход в дальность запускает атаку |
| AIMING | Наведение на актуальную цель с проверкой геометрии |
| MELEE_ATTACKING | Один корректный удар, затем наблюдение/cooldown |
| BOW_DRAWING | Удержание натяжения, повторная оценка цели и линии |
| BOW_RELEASING | Выпуск только после финальной проверки |
| BLOCKING | Щит против наблюдаемой угрозы, без постоянного use |
| DODGING | Короткое уклонение только в проверенное место |
| SEEKING_COVER | Ограниченный поиск реально закрывающего укрытия |
| RETREATING | Приоритетный выход из опасной позиции |
| EATING | Безопасное употребление имеющейся еды |
| WATER_ESCAPE | Всплытие/выход, бой не удерживает движение |
| SUSPENDED | Внешняя пауза с причиной и токеном, ввод отпущен |
| DEAD | Управление отпущено, ожидается новый живой игрок |
| RELEASING_CONTROL | Подтверждение остановки и возврат управления |
| ERROR | Причина, освобождение ввода, ограниченная повторная попытка |

Часть действий можно представить вложенными состояниями, но все переходы
должны иметь наблюдаемую причину, условие завершения и дедлайн.
Ни один переход не зависит от получения реплики от LLM.

## 8. Меч, топор и наблюдаемый результат

Оценивать реальный инвентарь: прочность, доступный слот, damage, attack speed,
перезарядку и ситуацию. Меч — основной melee, топор — допустимая альтернатива;
не менять предмет каждый tick. Внешние ограничения ресурсов соблюдать.

Перед действием: подтвердить игрока/цель и их здоровье, допустимость UUID,
дистанцию и препятствия, выбранный слот и синхронизацию с сервером.
Использовать штатное interaction API Minecraft, а не сырые клики по произвольному
прицелу, `/damage`, `/kill` или изменение здоровья сущности.
Показывать поворот и обычный взмах руки.

Использовать фактическую melee reach выбранной версии/атрибутов. Не вводить
искусственное условие «атаковать только в одном блоке». Не подменять дальность
обнаружения дальностью удара. Проверять реальное восстановление атаки.

Не допускать sweep/побочного урона мирным существам и неразрешённым игрокам.
При опасной зоне меча выбрать подходящий топор/другую точную безопасную атаку;
если её нет — блокировать/сменить позицию, а не игнорировать запрет.

ATTACK_SENT не равен DAMAGE_CONFIRMED. Сохранять цель, время, оружие, здоровье
до/после и качество подтверждения. Простое уменьшение HP рядом со своей атакой
не всегда доказывает, что урон нанёс именно локальный игрок: различать observed_health_drop
и подтверждённую атрибуцию. Исчезновение/выгрузка цели — TARGET_LOST, не KILLED.

## 9. Лук, прицеливание и дистанционный бой

Скелет/утопленник-стрелок не должны игнорироваться до контакта. Если есть
исправный лук, разрешённые стрелы и безопасная траектория — использовать лук.
Если лучшая доступная дистанционная атака отсутствует, выбрать сухое сближение,
щит, укрытие либо отступление и показать конкретную причину.

Лук реализовать как настоящий цикл: выбор/синхронизация слота → натяжение →
наведение → финальная проверка → отпускание. Не считать нажатие use выстрелом.
Учитывать текущую силу натяжения, движение цели, время полёта, падение снаряда,
столкновение с блоками и погрешность прогноза. Константы/механику брать из кода
целевой версии, а не переносить без проверки со старых версий Minecraft.

Проверять всю предполагаемую траекторию и hitbox посторонних существ, а не только
прямую линию до текущей позиции. Перед выпуском повторить проверку UUID,
допустимости, мира, стрел и отсутствия защищённых существ в опасной зоне.
Если мирный игрок пересёк траекторию — отменить выстрел безопасным способом,
не выпустить стрелу в него при попытке «отпустить кнопку».

Поддержать хотя бы обычный vanilla bow и обычные arrows. Отсутствие боеприпасов
даёт NO_AMMUNITION и смену тактики, а не вечное AIMING. Особые стрелы/оружие
не объявлять поддержанными без реализации их правил и тестов.

У натяжения/наведения есть конечный срок. При отсутствии решения после нескольких
оценок — сменить позицию/укрыться; не смотреть бесконечно на движущегося скелета.
Не расходовать все стрелы на цель за препятствием. Сохранять причины отмен/промахов.

## 10. Щит, уклонение и укрытие

Наличие щита в инвентаре не означает защиту. Переместить в подходящую руку,
подтвердить экипировку, использовать штатное удержание предмета и повернуться
в сторону угрозы. Учитывать готовность/прочность щита и запрет его одновременного
использования с натяжением лука/едой.

Поднимать щит при вероятном входящем ударе/приближении стрелы или трезубца,
а не держать постоянно, блокируя весь бой. Оценивать направление и время контакта
снаряда по доступным наблюдениям; плохой прогноз не выдавать за гарантированный блок.
Факт анимации щита не доказывает, что сервер заблокировал урон.

Уклонение — короткое боковое перемещение в известную безопасную клетку.
Проверять опору, место для тела, воду/лаву, край, препятствия и отсутствие
значительного ухудшения положения. Не прыгать произвольно к воде или в яму.

Укрытие — достижимая позиция, действительно закрывающая линию огня опасного
стрелка. Не считать ближайший блок укрытием без проверки. Выходить из укрытия
для безопасного выстрела и возвращаться, не зацикливая два одних и тех же шага.
Если подходящего укрытия нет, явно выбирать другую тактику.

## 11. Навигация и отсутствие зацикливания

Нужен работающий navigation backend, а не только интерфейс. Базовые движения
должны работать без Python. Допустим ограниченный локальный поиск маршрутов;
для пользователей UnionClef предусмотреть необязательный отдельный backend.
В каждый момент активен один backend; не одновременно два pathfinder.

Собственный local backend обязателен для самостоятельного боя. Внешняя
навигация — необязательная возможность для пользователей, которые её выбрали;
ядро не должно требовать UnionClef для боевых перемещений.
Публиковать native_combat_movement отдельно от факта поддержки vanilla attack.

Для продвинутого боевого движения реализовать локальное управление дистанцией,
боковой стрейф относительно цели, выбор направления обхода, управление sprint,
короткое уклонение и отход с сохранением наблюдения угрозы. Изменение направления
должно учитывать блоки, воду, край, снаряды и ближайших противников, а не быть
случайным переключением left/right. Критические удары/сброс спринта допустимы
только при подтверждённых механиках 1.21.11 и безопасной геометрии; не вводить
постоянный прыжковый цикл. Дистанция и темп зависят от выбранного оружия.
Использовать штатную физику и ограничения сервера: без изменения reach/скорости
и без подделки игровых условий. Качество «как top PvP» оценивать сценариями
и замерами, а не объявлять достигнутым наличием перечисленных классов.

Маршруты строить к позиции применения оружия, а не обязательно к ногам врага.
Уже имея безопасный выстрел, не бежать вплотную. При входе в дальность и появлении
линии огня остановить своё сближение и начать атаку.

Нельзя строить путь через непроверенную воду, лаву, опасный обрыв, непроходимый
зазор или незагруженные клетки. На земле учитывать высоту ног/головы и коллизии.
В v0.2 не ломать/ставить блоки, не строить мосты и не телепортироваться ради боя.

Начальные настраиваемые пределы: непрерывная попытка сближения 24 секунды,
отсутствие сокращения дистанции/позиционного прогресса 4 секунды,
leash от места начала боя 32 блока для мобов и 12 для игроков.
Это пределы поиска/движения, а не прекращение боя по таймеру при доступной цели.
Сетевой rubber-band тоже считается отсутствием подтверждённого прогресса.

Запоминать недавние неудачные сегменты и позиции на 30 секунд. Повтор той же
ошибки без изменения наблюдений запрещён. При тупике: другой путь/позиция,
другой доступный враг, укрытие или отступление. Не выдавать постоянный STOP
каждый tick и не сбрасывать историю ради повторения неудачного маршрута.

Navigation backoff запрещает повтор пути, **не выстрел**. Доступная безопасная
дальняя атака проверяется независимо; новый подтверждённый удар запускает
немедленную переоценку защиты. Недостижимый стрелок не превращается в «угроз нет».

## 12. Вода и утопленники

Если игрок на суше, враг в воде — можно стрелять с берега или приблизиться
по сухим клеткам до доступной дальности. Нырять и преследовать по воде нельзя.
Сам факт wet у цели не запрещает безопасный выстрел.

Если сам игрок попал в воду — прекратить боевой маршрут, отменить натяжение
и удержание щита, дать всплытие и безопасный выход. Минимальная WaterSafety
работает локально без Python; в integrated mode может передавать управление
проверенному внешнему спасателю по единому lease.
При submerged/падающем воздухе немедленно удерживать нужное плавание и искать
поверхность/берег; спам stopPathing сам по себе спасением не является.

При выходе из воды подтвердить сухую опору и свободное управление, заново оценить
врага и инвентарь. Не восстанавливать маршрут, который снова ведёт в воду.
Сухопутная цель рядом с водой требует такой же проверки каждого шага.
Принимаемый результат — персонаж реально всплывает и выбирается, а не только
пишет WATER_ESCAPE. Если выхода нет, поддерживать дыхание, показывая NO_SAFE_EXIT.

## 13. Низкое здоровье и еда

Порог отступления: health ≤ 4 HP, без ожидания LLM. Под щитом/укрытием искать
достижимое безопасное место. Во время отхода допустима безопасная атака, если
она помогает спастись, но продолжение погони не имеет приоритета над жизнью.
Противник в воде не должен затянуть отступающего игрока обратно в воду.

Использовать уже имеющуюся подходящую еду, когда игровые правила позволяют.
Не обещать, что обычная еда немедленно лечит при полном голоде или запрещённой
регенерации. Не добывать еду убийством мирных животных, не запускать долгий крафт.
Нет еды — NO_FOOD и защитная тактика; нет безопасной позиции — best-effort защита,
без выдуманного SAFE. При низком здоровье нельзя просто отключить мод.

Hysteresis: возобновление активного боя после восстановления минимум до 10 HP
и переоценки угроз; пороги настраиваемые. Еда имеет дедлайн и подтверждение
завершения по наблюдаемым данным, не по истечению фиксированного sleep.

## 14. Снаряжение и разрешённые серверные команды

Подготовка выполняется заранее в спокойном состоянии. Основной комплект:
пригодный melee weapon, щит, лук и стрелы. Хорошие имеющиеся предметы не заменять
на худшие. В бою немедленно использовать доступное и защищаться; не ждать /give.

В standalone режиме проверить реальные доступные серверные команды/права;
только при включённом command_supply и доступном /give запрашивать недостающее себе.
Стартовые конфигурируемые значения: iron_sword ×1, shield ×1, bow ×1, arrow до 64.
Количество стрел трактовать как целевой запас, а не 64 новых при каждой проверке.
Заполнение инвентаря обрабатывать явно, без выбрасывания посторонних предметов.

В integrated режиме **один владелец снабжения**: native или external.
Выбор явный и публикуется в статусе. При external мод только публикует потребность,
сам /give не отправляет. При native внешняя система не дублирует выдачу.
Мод не должен знать, как называется менеджер снаряжения внешнего проекта.

Без прав использовать имеющиеся предметы и честно сообщать об ограничениях.
Автоматическая добыча/крафт оружия и материалов в этот мод не входят.
Доступность команды не равна успешному выполнению: плагины/правила сервера могут
отказать. Проверять фактический инвентарь; bounded confirmation 4 секунды,
повтор неподтверждённого запроса не раньше 60 секунд.
Резервировать запрос до отправки, чтобы неизвестная доставка не вызвала дубль.

Запрещены команды убийства/урона/телепортации, creative, изменение правил мира
и выдача предметов другим игрокам как способ реализовать бой. Команды разрешены
для заранее согласованного собственного снаряжения и, при магии, очков опыта.

Magical Scepter — необязательный отдельный адаптер: проверять наличие мода на
клиенте и поддержку сервером. Если реально реализован, предпочитать безопасное
подходящее заклинание, читать действительные компоненты, XP, дальность и cooldown.
Выбранный слот должен быть синхронизирован с сервером до вызова атаки мода.
XP пополняется заранее только при доступной команде; без мода/прав не блокировать
ванильный бой. Не выдавать все варианты посоха и не имитировать заклинание командой.
Если адаптер не входит в поставку 0.2, capabilities обязано показывать false;
не объявлять поддержку магии только по наличию JAR.

## 15. Публичный API и расширения

Публичный класс со стабильным именем, например
`dev.autodefense.api.AutoDefenseApi`. Реализовать контракт, документировать
точное имя. Ниже проект интерфейса, а не существующие API Minecraft/Fabric.

```java
public final class AutoDefenseApi {
    public static int getApiVersion();                 // 1
    public static String getCapabilitiesJson();
    public static String getStatusJson();              // immutable snapshot
    public static String getConfigJson();
    public static String getEventsSinceJson(long seq, int limit);
    public static String setEnabled(String requestId, String expectedSession, boolean enabled);
    public static String requestSuspend(String requestId, String expectedSession, String owner, String reason);
    public static String releaseSuspend(String requestId, String expectedSession, String token);
    public static String setConfigJson(String requestId, String expectedSession, String json);
    public static String emergencyStop(String requestId);
}
```

Методы безопасны при вызове с произвольного внешнего thread: возвращают cached snapshot либо
кладут запрос в ограниченную очередь, без блокирующего ожидания client thread.
Изменения игры выполняются в client thread. Ответ мутации: accepted/rejected,
request_id, revision; отдельно статус выполнения. requestId обеспечивает
идемпотентность в пределах сессии. Ответ accepted не означает, что тело уже свободно.
expectedSession берётся из snapshot и проверяется при приёме и выполнении запроса.
При смене мира отложенная команда не применяется к новой сессии. Для состояния
без мира snapshot содержит отдельный идентификатор контекста; его запросы не
превращаются в игровые действия после подключения. emergencyStop намеренно
действует на актуальный контекст независимо от устаревшей сессии вызывающего.

Каждая внешняя пауза имеет отдельный токен. Освобождение одной причины не снимает
другую: releaseSuspend не должен отменять активное спасение из воды/ручной Stop.
Устаревшие запросы другой world session отклоняются. Очередь переполнена — явный
queue_full; emergencyStop не должен ждать позади обычных запросов.
Конфигурация выбирает валидированный профиль; проверка целей перед действием
обязательна для любого профиля и не отключается флагом bypass_checks.

API не требует установки Py4J, Python или запуска сетевого сервера. Другой мод
может вызвать его в той же JVM. Python при необходимости подключается через
свой уже установленный bridge; этот транспорт не является зависимостью ядра.
По умолчанию мод не открывает HTTP/WebSocket/TCP порты.

Extension points минимум: WeaponProvider, NavigationProvider, ExternalControlAdapter
и TargetPolicy. Контракт каждой возможности объявляет версию, поддержку, ограничения,
дедлайны и release/cancel. Provider не получает разрешение обходить общий ControlArbiter
или обязательные ограничения целей. Ошибка дополнения не ломает vanilla fallback.
Навигационный provider выполняет локальные шаги, не требует внешнего процесса для боя.
Выбор provider детерминированный; две реализации не владеют телом одновременно.

В capabilities отдельно публиковать autonomous_combat, local_navigation,
native_combat_movement, water_escape, profile_constraints, equipment_supply, event_stream и
external_control_arbitration. Последнее true только при реальном согласованном
контроле подключённого внешнего владельца, а не по наличию поля owner в JSON.
Для каждого provider показывать идентификатор/версию и причину недоступности.

Snapshot как минимум:

## 16. Настройки, HUD и диагностика

Конфигурация JSON с валидацией и атомарным сохранением. F8, enable, standalone/
integrated mode, радиусы, пороги здоровья, тактические пределы, снабжение и HUD
должны быть документированы. Изменение настройки применяется на границе tick.
Добавить понятный локальный экран настроек: enable, профиль, радиусы, пороги,
manual override, command_supply и HUD. Интеграция с Mod Menu необязательна;
отсутствие Mod Menu не препятствует настройке. Некорректный файл не обнуляет
рабочие настройки и не приводит к загрузке полурабочей конфигурации.
Сохранить формат версии config и миграцию настроек между релизами.

Минимальные клиентские команды, не требующие серверного OP:

```text
/autodefense enable
/autodefense disable
/autodefense status
/autodefense stop
/autodefense resume
/autodefense reload
```

disable/stop/resume различаются: disable выключает наблюдение, stop защёлкивает
ручную паузу с освобождением тела, resume снимает только эту ручную паузу.

Локальный HUD: enabled, состояние, цель, расстояние, оружие, щит, HP, причина
неатакования и текущий владелец управления. ATTACK_SENT отображать отдельно от
наблюдаемого/атрибутированного урона. Настраиваемый маркер выбранной видимой цели
рисовать локально, без /effect/glowing и изменения сервера; не показывать его
сквозь стены по умолчанию. Обновлять HUD независимо от LLM и озвучки.

Логировать смены состояний и значимые результаты, не каждый tick одинаковую строку.
Снимать время обнаружение→решение→первое действие, задержку владения, стоимость
tick/pathfinding, число отмен выстрела, причины неудач и задержку остановки.
Логи ограничены по размеру; файлы пишутся вне критического боевого tick.

Reason codes минимум: NO_WEAPON, NO_AMMUNITION, NO_FOOD, OUT_OF_RANGE,
NO_LINE_OF_SIGHT, PROTECTED_ENTITY_IN_PATH, TARGET_FORBIDDEN, TARGET_LOST,
UNKNOWN_ATTACKER, NO_SAFE_ROUTE, NO_SAFE_COVER, NO_SAFE_EXIT,
CONTROL_BUSY, WATER_ESCAPE, RETREAT_LOW_HEALTH, COOLDOWN,
COMMAND_NOT_AVAILABLE, EQUIPMENT_UNCONFIRMED, DISCONNECTED, DEAD.

## 17. Приёмка

Сначала unit-тесты чистой политики, конечного автомата, сроков, очереди API,
lease, навигационной памяти и геометрии. Затем сборка production JAR и испытания
в отдельном тестовом мире. Игровой тест и его результат документировать отдельно.

Обязательные сценарии:

1. F8 и API включают один контроллер; повтор enable не создаёт второй.
2. Зомби обнаруживается до контакта, выполняются настоящие удары и взмахи.
3. Скелет на 12–24 блоках вызывает дальнюю тактику либо подход/укрытие с причиной,
   а не ожидание расстояния в один блок. Лук реально выпускает стрелу.
4. Стрела/трезубец вызывают щит/уклонение; эффект блока проверяется в игре.
5. Мирный игрок проходит между лучником и целью — опасный выстрел отменяется.
6. Жители, животные, голем и мирный игрок не получают намеренного/побочного урона;
   нападение защищённого существа не отменяет запрет.
7. Игрок ударил или попал стрелой — атрибуция по реальному источнику, ограниченный
   ответ; чат, падение и неизвестный источник не вызывают атаку случайного игрока.
8. Враг за стеной/на другой стороне воды не вызывает бесконечное AIMING/прыжки.
9. Цель в воде доступна для выстрела с берега; персонаж не идёт за ней вплавь.
10. Игрок столкнут в воду — всплывает и выбирается; нет цикла stop→вода→stop.
11. При 4 HP начинается наблюдаемое отступление; еда используется по правилам игры.
12. Без еды/стрел/щита/прав/места в инвентаре есть понятная смена тактики без зависания.
13. /give отказан/ответ потерян — нет дублей и спама, факт успеха требует инвентаря.
14. Оружие из другого слота действительно видит сервер; melee/magic не происходят
    с прежним предметом из-за отсутствующей синхронизации.
15. Блокировка пути/отбрасывание не вызывают бесконечного повторения двух точек.
16. В бою несколько мобов: приоритеты устойчивы, опасный новый враг не игнорируется.
17. Смерть, respawn, смена мира, disconnect и Stop не оставляют зажатых действий.
18. При поддерживаемом внешнем контроллере бой перехватывает тело без ожидания
    внешнего процесса; актуальная задача возвращается владельцу через адаптер.
19. Устаревший внешний запрос не отбирает движение у боя/спасения. Два бойца одновременно
    не работают. Пропажа внешнего процесса не останавливает локальную самозащиту.
20. При 32 мобах и активной навигации опубликованы измерения задержек и CPU;
    проверена реакция при лаге сервера без спама пакетами/командами.
21. Чистая установка только с Fabric API: без UnionClef, Magical Scepter, Python,
    сети и файлов чужого проекта работают F8, все vanilla-действия и навигация.
22. Default command_supply выключен: наличие OP само по себе не выдаёт предметы.
23. Отсутствующее/несовместимое дополнение отмечается в capabilities; основной
    мод загружается и продолжает vanilla-бой. Совместимость не определяется одним ID.
24. Профиль и настройки меняются без переноса алгоритма боя в отдельный проект;
    пользовательский профиль не содержит захардкоженных путей или имён персонажей.
25. При полностью приостановленном внешнем pathfinder сохраняются самостоятельные
    стрейф, выбор дистанции, уклонение, сближение и отступление новым модом.
26. После захвата управления поздние записи/очистка ввода старого контроллера
    не меняют поворот, выбранный слот и удержания нового владельца.

Критерий готовности: успешная сборка + тесты + заполненная таблица игровых
сценариев PASS/FAIL/NOT_TESTED. Непроверенные возможности остаются явно непроверенными.
Без backend навигации, реального bow release, щита или арбитража версия не считается
полной реализацией этого ТЗ, даже если UI и классы успешно компилируются.
