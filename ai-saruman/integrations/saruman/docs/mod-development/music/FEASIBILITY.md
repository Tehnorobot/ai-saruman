# Музыкальный навык персонажа: исследование и проект

Дата: 2 ноября 2026. Цель — Fabric / Minecraft Java 1.21.11, текущий Saruman runtime.
Ничего не установлено и не запущено в игре. API ниже — предложение для разработки,
не существующие методы проверенных сторонних модов. Оценки сложности инженерные,
без обещаний сроков или гарантии успешной реализации конкретной LLM.

## Рекомендуемое решение

Отдельный универсальный клиентский мод с небольшим адаптером к персонажу.
Первая версия играет на заранее подготовленных note blocks, не строит сцену,
не добывает материалы и не меняет gamemode. Музыкальный цикл работает локально
в Java без LLM/Python/HTTP между нотами. Saruman выбирает song_id, затем наблюдает
начало, завершение, отмену или причину недоступности.

Сначала проверить готовый NoteBot на тестовом профиле. Если его управление и
передача тела подходят, достаточно внешнего адаптера; наличие стабильного API
не подтверждено. Если нет — небольшой собственный исполнитель предпочтительнее
копирования чужих внутренних полей и обязательных SHA-пинов для всей системы.

## Кто услышит музыку

1. **Настоящие note blocks:** сервер обрабатывает реальные взаимодействия и создаёт
   игровые звуки. Это путь для слышимого окружающими исполнения без обязательного
   музыкального мода у каждого слушателя; права, дальность и серверные правила
   всё равно действуют. Официальная [статья Mojang](https://www.minecraft.net/en-us/article/block-week-note-block)
   описывает настройку, инструменты под блоком и слышимость; это историческая
   статья, не источник новых mappings или современного протокола 1.21.11.
2. **Локальный preview/playSound на клиенте:** слышит клиент Сарумана, но сам по
   себе такой вызов не рассылает звук остальным игрокам. Проверять реальным вторым клиентом.
3. **AudioPlayer/SVC:** серверное воспроизведение аудио; слушателям нужен рабочий
   Simple Voice Chat. Не нужны клавиши PTT Сарумана или его виртуальный микрофон.
4. **Виртуальный кабель:** можно синтезировать MIDI в аудио и направить его в тот
   же CABLE, что и TTS. Это передача музыки микрофоном, а не игра на блоках.
   Она наследует ограничения SVC, шумоподавления, соединения и аудиомаршрутизации.

Нельзя выдавать успешный локальный preview за подтверждение слышимости на сервере.

## Хранение и преобразование нот

Сохранять оригинал отдельно от подготовленного исполнения:

```text
music/sources/       .nbs, .mid, сведения об авторе/источнике
music/compiled/      versioned JSON с событиями для конкретного backend
music/reports/       потери, транспозиции, неподдержанные инструменты и темп
music/stages/        привязка сцены к миру, позиции инструмента и исполнительской точки
```

- **NBS** — лучший первый импорт для Minecraft. Есть [описанная спецификация](https://noteblock.studio/nbs).
  Явно выбрать поддерживаемые версии, не обещать «все NBS» без тестов. Начать с v4/v5;
  v6 импортировать только с проверкой совместимости каждого инструмента.
- **MIDI** — удобный исходник для редакторов и последующего импорта. Java 21 имеет
  [javax.sound.midi](https://docs.oracle.com/en/java/javase/21/docs/api/java.desktop/javax/sound/midi/package-summary.html).
  Это даёт чтение MIDI, но не готовую Minecraft-аранжировку.
- **JSON** — удобный небольшой формат для собственных коротких мелодий и runtime.
- PDF/фотография нот — не MIDI: сначала распознавание или ручной перенос, отдельная
  проверка ошибок. MP3/WAV также не партитура; точное извлечение многоголосных нот
  из готового трека — отдельная сложная задача, не базовый импорт.

Предложение внутреннего формата подготовленной песни:

```json
{
  "schema_version": 1,
  "song_id": "short_study",
  "backend": "physical_note_blocks",
  "ticks_per_second": 20,
  "loop": false,
  "events": [
    {"tick": 0, "instrument": "harp", "note": 6},
    {"tick": 10, "instrument": "harp", "note": 8},
    {"tick": 20, "instrument": "harp", "note": 10}
  ]
}
```

Здесь note — Minecraft-индекс 0–24, не номер MIDI. Для harp без изменения
настройки строя: MIDI 54 → индекс 0, MIDI 60 → индекс 6, MIDI 78 → индекс 24.
Формула `index = midi_note - 54`. У других инструментов учитывать высоту исходного
семпла; нельзя слепо применять эту формулу к басу или колокольчику.
В NBS диапазон стандартной клавиатуры для note blocks — key 33–57;
`index = nbs_key - 33`. Не смешивать NBS-key, MIDI-note и block-state note.

Конвейер без LLM:

```text
NBS/MIDI → разбор и единая временная шкала → выбор дорожек → карта инструментов
→ транспозиция/проверка диапазона → квантование времени → лимит плотности
→ JSON + отчёт изменений → проверка сцены → локальное исполнение
```

MIDI: учитывать все смены темпа и порядок событий дорожек, NOTE_ON с velocity=0,
NOTE_OFF и формат временной шкалы. Неподдержанный SMPTE/MIDI type явно отклонять.
Время сначала считать от начала песни, затем квантовать в абсолютные ticks,
а не округлять длительность каждого шага с накоплением ошибки.
Для постоянного BPM `ticks_per_quarter = 1200 / BPM` при 20 TPS.
NBS tempo измеряется в собственных ticks/sec, а не BPM и не всегда 20.

Ноты вне диапазона не обрезать к ближайшей границе молча. Выбрать политику:
перенос всей партии по октавам, упрощение партии или отказ. Показать количество
затронутых нот и потерянных голосов до начала исполнения.

## Ограничения физического исполнения

- У блока 25 настроек высоты. Это два октавных интервала, не фортепианная клавиатура.
  Инструмент зависит от основания; нужно подходящее пространство и доступ к блокам.
- NBS v6 добавляет четыре трубы из Minecraft **26.1**. Наш профиль **1.21.11**:
  нельзя автоматически объявить эти инструменты ванильными для него только потому,
  что импортёр прочитал новый файл. Проверять instrument registry целевой версии.
- Во время песни нельзя перенастраивать один блок под каждую ноту без последствий:
  настройка сама издаёт звук и требует взаимодействий. Нужна предварительная
  настройка/карта `(instrument, note) → block position`.
- Для первой версии: готовая сцена из 25 настроенных блоков одного инструмента,
  либо минимальный набор реально нужных высот. Вся сцена должна быть доступна с
  безопасной исполнительской точки; число уникальных нот не равно длине песни.
- Reach, линия доступа, защита региона, режим игры и лимиты взаимодействий
  определяются сервером. Не включать reach-bypass, gamemode или телепортирование.
- Обычные ноты — затухающие звуки; MIDI sustain, NOTE_OFF, динамика и панорама
  не воспроизводятся физическими блоками как на синтезаторе. Длительность между
  ударами можно сохранить, но удержание одного звука требует иной аранжировки/backend.
- Нормальная цель сетки — 20 ticks/sec (50 мс при нормальном tick rate).
  В tick можно планировать аккорд, но сервер может ограничить количество действий;
  одинаковые события одного блока могут схлопываться. Не обещать любую полифонию.
- При лаге не выпускать накопившиеся ноты пачкой. Пропускать/останавливать по
  объявленной политике. Измерять фактический джиттер, а не обещать идеальные 50 мс.
- Режим игры ударами должен реально звучать на сервере и не ломать блоки.
  Локальный звук, взмах руки и отправленный пакет — разные результаты.

## Архитектура и интеграция

```text
SongLibrary → Importer/Compiler → StageValidator → PlaybackController
                                             ↘ Status / events / HUD
```

Состояния: IDLE, LOADING, VALIDATING, TUNING, READY, PLAYING, PAUSED, STOPPED,
COMPLETED, FAILED. У каждой подготовки есть дедлайн; у песни конечная длительность.
Повтор по умолчанию выключен, очередь ограничена одной выбранной композицией.

Публичный API новой реализации: version/capabilities, listSongs, validateStage,
play(requestId, songId), pause, resume, stop, snapshot и ограниченный журнал событий.
Принимать запросы с любого потока через ограниченную очередь; работать с миром
только на client thread. Парсинг/диск вне критического игрового цикла. Управление
из Python — выбор композиции и чтение событий, не отдельный RPC на каждую ноту.

Один владелец поворота/движения/рук. Существующий бой/спасение немедленно прерывает
музыку локально, без ожидания LLM; не отключать Auto Defense ради исполнения.
На бой отменять use/attack/свои маршруты. Возобновлять только после проверки мира,
сцены и актуальности поручения. После Stop/смерти/выхода не возобновлять самостоятельно.
Следить за изменёнными/сломавшимися блоками, чужой настройкой и выгрузкой сцены.

Одна просьба «сыграй X» → одна музыкальная цель. «Хватит играть» отменяет намерение,
все его pending-вызовы и текущую песню; LLM не создаёт замену из старого запроса.
При запрете самостоятельной музыки отключается и фоновый выбор. Наличие аддона
проверять как optional capability: отсутствие музыки не блокирует follow/TreeGrow/бой.

В Gradio: список композиций, backend, подготовленность сцены, Play/Pause/Stop,
текущий такт/длительность, отчёт преобразования и понятная причина остановки.
Речь PersonaAgent редкая и асинхронная; не комментировать каждый удар.
Для аудиобэкенда отдельно согласовать приоритет TTS и приглушение музыки.

## Сложность и работа MiniMax

В локальном каталоге Lab на дату исследования указан MiniMax-M3.1-Flash.
Его [официальная страница](https://agent.minimax.io/tools/m3.1-flash) описывает задачи
программирования; это не тест Fabric и не гарантия корректного Minecraft-кода.
Не нужен отдельный MiniMax-запрос на исполнение каждой ноты или музыкального шага.

| Этап | Относительная сложность | Где LLM-разработчик потребует проверки |
|---|---|---|
| JSON-партитура + валидатор + детерминированный проигрыватель | Низкая/средняя | Порядок нот, пауза/Stop, отсутствие дрейфа |
| Импорт выбранных NBS v4/v5, MIDI PPQ | Средняя | Заголовки/ошибочные файлы, tempo map, транспозиция |
| Одна подготовленная сцена, 1–2 голоса | Средняя | Серверные взаимодействия, настройка/игра, дальность |
| Надёжное соседство с Auto Defense/UnionClef | Высокая | Владение телом, прерывания и отмена старых намерений |
| Универсальная автоматическая стройка сцены в survival | Высокая | Материалы, навигация, приваты, восстановление окружения |
| Автоматическая точная аранжировка любого MIDI/MP3 | Очень высокая / не цель MVP | Музыкальная структура и неизбежные потери |

Давать MiniMax этапы с точной версией mappings и небольшим проверяемым результатом,
не всё сразу. Сначала чистые тесты импортёра/планировщика, затем remapped JAR,
потом тестовая сцена с записью слышимого результата вторым клиентом. Сборка не
доказывает ни правильность ритма, ни слышимость другим игрокам.

Минимальная приёмка: короткая гамма, мелодия с паузами, простой аккорд, нота вне
диапазона, смена темпа, Stop между нотами, прерывание боем, смерть/перезаход,
неизвестный song_id, занятый контроллер, сломанный блок, отключённый аддон.
До запуска разработки можно проверить готовый NoteBot на той же сцене и сравнить,
нужна ли собственная реализация исполнительной части.
