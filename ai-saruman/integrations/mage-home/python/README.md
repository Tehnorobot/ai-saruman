# Mage Home v5 — автономный Python-модуль

Python 3.10+, нет runtime-зависимостей и зависимости от персонажа, Minecraft, Jev или настроек Java. Runtime Java потребляет готовый `mage_home.blueprint/1` и исполняет его самостоятельно; Python не выдаёт игровые действия и не подтверждает серверное исполнение.

## CLI

Из этой папки (или через `PYTHONPATH` / после установки wheel):

```text
python -m mage_home design --profile profiles/replay.json
python -m mage_home expert --profile profiles/replay.json
python -m unittest discover -s tests -v
python -m pip wheel --no-deps . --wheel-dir dist
```

На stdin передать **один объект JSON UTF-8** и закрыть поток. На stdout будет одна строка JSON UTF-8; не смешивать её с журналом. Процесс возвращает 0 и для доменных ошибок: проверяйте `ok`. `design` принимает `{description, context, projectId}`, возвращает `{ok:true, blueprint:{…}}`. `expert` принимает `expertRequest` из общей схемы, возвращает `{ok:true, proposal:{…}}`; `ok:false` означает `{error:{code,message}}`, не готовый план. Пример текстового входа: `replay/request-courtyard.json`; примеры инцидентов: `replay/request-expert-access.json`, `replay/request-expert-mismatch.json`.

Replay поиска дома совпадает по точному описанию, экспертного сценария — по виду инцидента. В `designs.json` записано **архитектурное намерение**, а не финальный blueprint. Компилятор выводит детерминированные клетки, обязательный воздух, пары, зависимости, вход и ведомость. Зафиксированные экспертные тактики привязываются только к наблюдаемой текущей цели и проходят те же проверки, что и ответы модели. `delayMillis` в отдельной replay-записи позволяет воспроизвести таймаут; `response` позволяет записать статический ответ, в т. ч. для негативного теста.

## Самостоятельный профиль

Скопируйте `profiles/live.example.json` в локальный файл и явно задайте OpenAI-compatible endpoint `/v1/chat/completions`, модель (опционально `expertModel`), предельное время и переменную окружения с ключом. Стандартно HTTPS; HTTP только loopback и только при `allowLoopbackHttp:true`. Для локального провайдера без авторизации уберите `apiKeyEnv`. Если совместимый сервер не поддерживает `response_format`, задайте `jsonResponseFormat:false`; ответ всё равно должен быть строгим JSON. Пакет не печатает заголовки, сырые HTTP-ответы или ключи. Дизайнеру не передаются адрес сервера, seed или имя игрока; эксперт получает только строительный инцидент, локальный мир, операции и выбранную историю. С отредактированным профилем отдельно проверьте `design` и `expert`. Replay и loopback-конформанс — не результат реальной модели.

Необязательный `projectDirectory` (относительно профиля или абсолютный) включает атомарное сохранение проверенного blueprint под именем, полученным из хеша `projectId`. Идентичность мира, журнал попыток и долговечные исполнительные обязательства принадлежат Java.

Необязательный `designCacheDirectory` сохраняет чертёж после успешной компиляции. Следующий запрос с тем же описанием, миром, углом пола и возможностями клиента повторно валидирует этот чертёж и выдаёт его с новым `projectId` без вызова провайдера. Подготовка площадки всегда проверяет текущее состояние мира.

## Границы валидации

Проектировщик проверяет маршрут от входа к проходным зонам каждого этажа, к комнатам, мебели и открытым площадкам. В чертёж записываются `accessAreas` и `accessLevels`. Двери учитываются по направлению прохода. Java сверяет в мире пол, лестницы, двери, мебель и требуемый просвет, на которых основан расчёт.

Уровень плана принимает `decorations` с полями `room`, `at: [x, localY, z]`, `block` и необязательным `state`. Ноль по высоте означает акцент в полу, единица подходит для ковра, горшка и напольного света. Для подвесных и настенных светильников выбирается высота крепления. При наличии `context.resources` проектировщик получает количества доступных блоков. Если `canSupplyBlocks` выключен, компилятор сверяет весь расход с `inventory`.

- Ось Y, геометрия дверей/кроватей/двойных сундуков, граф зависимостей, двухблочная высота проходов, опора, лестничные посадки, доступ к мебели, комнаты и прикладные требования проверяются локально, без запроса к модели. DSL поддерживает объединения прямоугольников, стены с проёмами и остеклением, плоскую и ступенчатую двускатную крышу, внутренние лестницы, палубы/дворики. Обязательные факты поставляются LLM как типизированные предикаты с дословными цитатами. Валидатор проверяет эти предикаты; он не является универсальным интерпретатором естественного языка.
- Поддерживается ограниченный набор состояний vanilla Java 1.21.11; прочие идентификаторы с наблюдаемого сервера можно передавать как данные, но они не становятся разрешёнными целями установки. Вместо неизвестного свойства, формы или конфликтного требования возвращается ошибка. Варианты маршрутов консервативны, не эмулируют физику или UnionClef.
- `plan_site(blueprint, context, observations)` — чистый планировщик снимка: явные абсолютные наблюдения, расчистка препятствий и жидкости, проверяемая опора под пятном, засыпка снизу вверх до заданной глубины, опора и просвет у входа. `UNKNOWN` и `BLOCKED` не несут мутаций. CLI-дизайн не получает снимок и не заменяет обязательный Java-этап подготовки.
- Expert: координаты абсолютные, `worldSnapshot.cells` — явные состояния (воздух обозначается `minecraft:air`); `worldSnapshot.known` при наличии перечисляет **ненаблюдённые** точки согласно описанию общей схемы. Возвращённые токены `requestId`, `runId`, `generation`, `schemaRevision`, `permitGeneration`, `worldSnapshotRevision` нужно повторно проверить **на клиентском тике перед исполнением**. `same_token` — чистый аналог этой проверки, не диспетчер игровых действий. Model output не может переопределить токены.
- Точные поля `repair.steps[].cells` — `{x,y,z,block?,state?}`; для `break_block` state описывает наблюдаемое исходное состояние, для `place_block` — целевое. Эксперт предлагает физические действия. Исполнитель может снабжать персонажа предметами через `/give`. `move` использует полностью наблюдаемый маршрут с опорами. Смена неизменяемой схемы и удаление исходных шагов через патч запрещены; добавляются проверяемые зависимости. Временный пролом вне цели требует объявленного долга и точного восстановления в том же патче. Java всё равно проверяет преусловия, права, мир, токены и наблюдаемый эффект.
- `select_attempts` различает рабочие, неудачные и прерванные записи. Отсутствующая опора или ненаблюдаемая точка не позволяет переиспользовать успешную трассу; полностью наблюдённая расчистка позволяет заново рассмотреть блокированный проход. Без явной мировой/проектной привязки в expertRequest, другой `runId` намеренно не выбирается внутри Python.
