# Подключение Telegram к персонажу

Текстовый шлюз уже проверен пользователем на VPS. Новая интеграция добавляет
события игры, подготовку постов выбранной моделью Telegram, постоянную очередь,
получение новых постов канала, управление SSH-туннелем и окно в Character Lab.
Minecraft, авторизация моделей и сама игра остаются на компьютере.
Строительство домов в эту интеграцию не включено.

## Что нужно сделать один раз

### 1. Обновить gateway.py на VPS

В PowerShell **на компьютере**:

```powershell
cd C:\Users\aimihail\Desktop\projects\ai-saruman\integrations\telegram-gateway
scp gateway.py root@152.234.255.232:/opt/saruman-telegram/
ssh root@152.234.255.232
```

После входа **на VPS**, между отправками:

```bash
systemctl restart saruman-telegram
systemctl status saruman-telegram --no-pager
curl -s http://127.0.0.1:8787/healthz
```

Ожидаем `active (running)` и `api_version: 2`. `.env` и существующую базу не заменяй.
API v2 добавляет получение новых постов только настроенного канала и явный повтор
отклонённого запроса с тем же ID. `sent` и `unknown` не отправляются повторно.

### 2. Настроить автоматический туннель

Можно оставить ручной туннель. Чтобы окно SSH больше не требовалось, выполни
**на компьютере** из папки шлюза:

```powershell
uv run --no-project --python 3.12 python setup_tunnel.py --server 152.234.255.232
```

Скрипт создаёт отдельный SSH-ключ в `%USERPROFILE%\.ssh\saruman-telegram`, если его
ещё нет. Если предыдущий запуск завершился `sh: 1: set: Illegal option -`,
используй исправленный локальный `setup_tunnel.py` и повтори ту же команду:
это ошибка преобразования строк Windows, исправленная передачей UTF-8 байтов
без CRLF. Удалять существующий ключ или повторно настраивать бота не нужно.

Существующий ключ не перезаписывается. Ты один раз вводишь пароль VPS
в запрос OpenSSH; программа не сохраняет и не выводит пароль. На VPS создаётся
пользователь `telegram-tunnel` без права выполнять произвольные команды. Публичный
ключ разрешает локальное перенаправление только к `127.0.0.1:8787`; глобальные
настройки SSH и вход root не меняются. Ограничения ключа описаны в
[документации OpenSSH](https://man.openbsd.org/sshd.8#AUTHORIZED_KEYS_FILE_FORMAT).

Приватный ключ не передаётся на VPS и не включается в запросы LLM. Отпечаток VPS
должен быть уже проверен и сохранён первым ручным SSH-входом. Скрипт не принимает
незнакомые/изменённые ключи сервера автоматически. После выполнения он добавит
четыре `GATEWAY_SSH_*` настройки в существующий `.env.client`, сохранив API-ключ.

Закрой старое окно **ручного туннеля** через Ctrl+C, чтобы оно освободило порт 8787.
Шлюз-службу на VPS не останавливай. Новый туннель создаст окно лаборатории либо
игровой runtime после включения Telegram.

### 3. Запустить окно Character Lab

В PowerShell **на компьютере**:

```powershell
cd C:\Users\aimihail\Desktop\projects\ai-saruman
uv run --python 3.14 saruman
```

Открой `http://127.0.0.1:8765/#telegram`. Python-окружение лаборатории и окружение
игрового runtime остаются раздельными. Если лаборатория уже работала, перезапусти
только её процесс для загрузки нового сервера и обнови страницу.

В окне Telegram:

1. Включи **«Включить Telegram»**, сохрани и нажми **«Проверить связь»**.
2. Сначала оставь автопубликацию выключенной. После игрового события текст появится
   как **«На просмотре»**. Кнопка **«В очередь»** разрешает отправку этого текста.
3. Для самостоятельных публикаций включи **«Публиковать подготовленные посты
   автоматически»**. Интервал по умолчанию — 1800 секунд; его можно изменить.

Открытие страницы само по себе не вызывает LLM и не отправляет посты. Включение
Telegram разрешает обработку очереди и подготовку черновиков активным игровым
персонажем. Автопубликация отдельно разрешает отправку новых текстов без просмотра.
Она расходует лимиты/токены выбранной роли Telegram. Модель
в шапке лаборатории относится к тестовому чату, не к этим публикациям.

### 4. Перезапустить игровой Python runtime

Используй прежний способ запуска персонажа из `integrations/saruman`. Нужен полный
перезапуск Python-процесса для загрузки нового адаптера, затем обычный Start.
Minecraft перезапускать для этого обновления Python не требуется.

Текст готовит профиль **Telegram**, выбранный в Saruman Lab → Настройки.
Он независим от PersonaAgent и чата Lab; провайдеры могут отличаться.
Отдельный процесс LLM на VPS не нужен. Расход записывается в общий RoleStore
как `telegram`, сессия заканчивается на `:telegram`. При обновлении сохранённый
выбор PersonaAgent копируется в Telegram один раз. Дальше модели меняются отдельно.
[Роли и подключение MiniMax](../../docs/MODEL_SETTINGS_RU.md).

## Как проверить

1. В новом окне Telegram создай свой черновик и отправь его через «В очередь».
   Проверь статус «Опубликовано» и message_id. Это ручная отправка через реальную очередь.
2. При активном персонаже дай ему вырастить дерево. После подтверждённого завершения
   TreeGrow появится одно событие `tree_grown`, затем черновик/пост согласно режиму.
   Повторные снимки того же запуска не создают новые события.
3. Временно разорви доступ ПК к VPS. Очередь должна сохраниться; после восстановления
   соединения используется прежний publication_id, новый ID автоматически не создаётся.
4. Отключи Telegram в окне: последующие отправки и генерация останавливаются, история
   сохраняется. Уже принятый Telegram запрос невозможно отозвать этим переключателем.
5. Проверь историю: события → ID поста → попытки → message_id. Кнопки страниц открывают
   старые записи. Раскрытая диагностика и редактируемый текст не перерисовываются таймером.

Локальные автотесты подменяют Telegram/LLM. Они проверяют HTTP и SQLite целиком, но
не подтверждают физическое выполнение игрового события или права нового SSH-пользователя
на реальном VPS. Эти проверки выполняются после установки на твоей машине/сервере.

## Источники, память и ошибки

- Игра: подтверждённое завершение TreeGrow, неудача TreeGrow, наблюдаемое окончание
  активности защиты и смерть. Окончание защиты **не считается доказательством убийства**.
  Обещания LLM, команды «принято» и приватные разговоры не становятся достижениями.
- На вход модели поступают выбранные необработанные события и три последних поста
  для защиты от повторов; полный журнал остаётся в `.saruman/telegram.sqlite3`.
  В окно можно открыть полные данные событий и попыток. Координаты, имена игроков,
  world/run IDs, адреса сервера и ключи в запрос подготовки поста не передаются.
- Неописанные моделью события освобождаются для следующего черновика; неизвестные
  event_ids отклоняются. Смысл текста требует проверки на реальном персонаже:
  ссылки на факты и инструкции не гарантируют отсутствие всех галлюцинаций LLM.
- На компьютере сохраняются события, тексты, очередь, попытки и входящие посты.
  На VPS сохраняется журнал доставки. Обе базы нужно сохранять при переносе.
- Временная недоступность шлюза повторяется с задержкой без лимита числа попыток.
  После 429 учитывается `retry_after`. Явные ошибки прав/параметров показываются
  у отдельного поста; после исправления нажми «В очередь» с тем же ID.
- `unknown`: ответ о доставке потерян. Сначала проверь канал. Автоматической отправки
  нового сообщения нет. Это не ошибка всего игрового процесса.
- Новые сообщения канала читаются Bot API и сохраняются с update_id без дублей.
  Это не выгрузка всей старой истории. Другой потребитель getUpdates/webhook для этого
  бота создаст конфликт: используй одного бота для этого шлюза.
- Окно и игровой runtime используют один локальный журнал и lease с обновлением
  владения. Они могут работать одновременно; один запрос не отправляется двумя
  локальными работниками. Шлюз дополнительно проверяет publication_id на VPS.
- Управляемый туннель работает только пока запущена лаборатория или игровой runtime
  и включён Telegram. При новом запуске он создаётся снова. Автозапуск Windows,
  запуск клиента Minecraft и самостоятельный вход в мир этой задачей не добавляются.

Токен бота остаётся в `.env` на VPS. Локально нужен только `.env.client` с ключом
ограниченного API и путём к SSH-ключу. Домен и новая платная услуга не требуются.
