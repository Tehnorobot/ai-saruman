# Разбор частичного запуска Auto Defense от 21 октября 2026

Проверены предоставленные `codex_result.json`, `codex.jsonl.txt` и
`2026-10-21T07-35-42-606144Z-agent_failed.tar.gz`, текущий код лаборатории и
доступные только для чтения показатели контейнера агента. Дополнительно выполнены
два независимых разбора: контроллера и исходников мода. Код системы и мода,
настройки, авторизация и состояния заданий не изменялись; новые модельные запросы,
Gradle и Minecraft не запускались.

Задание: `16c911fc0fbf4d`; проект: `b8fff539803e4d`; модель: `gpt-6-sol`,
reasoning: `medium`.

## Почему остановилось

Последовательность подтверждена журналом:

1. Агент создал начальный Fabric-проект и выполнил несколько сборок и тестов.
2. Первый клиентский запуск Minecraft завершился до игровых assertions:
   `pthread_create failed (EAGAIN)` → `unable to create native thread` →
   ошибка создания `Sound engine` → `runClientGameTest FAILED`.
3. Агент начал повтор через
   `JAVA_TOOL_OPTIONS='-XX:ActiveProcessorCount=4' xvfb-run -a ./gradlew runClientGameTest --no-daemon`.
   В журнале есть только начало этой команды, без результата.
4. Надзорный процесс остановил Codex по общему лимиту:
   **`TIMEOUT`, `duration_seconds: 1500.46` — 25 минут**.
5. Контроллер преобразовал этот результат в `FAILED / agent_error`, создал
   резервную копию и вышел. Независимая проверка лаборатории не началась.

Это сочетание ресурсной ошибки среды и недостаточной обработки прерывания в
лаборатории. Успешные промежуточные команды не означают завершения ТЗ.

## Ограничение потоков контейнера

`compose.yaml:8` задаёт общий `pids_limit: 256`, который наследует `agent`.
Лимиты worker 500 и изолированной сборки не увеличивают лимит агента:
данный клиент был запущен непосредственно командой Codex внутри agent.

Docker inspect работающего agent подтвердил лимит 256 PID, 3 CPU, 6 GiB памяти;
время запуска этого контейнера — `2026-10-20T23:16:06.051380254Z`.
При диагностике получены:

| Показатель cgroup | Значение |
| --- | --- |
| `pids.max` | 256 |
| `pids.current` | 184 |
| `pids.peak` | 256 |
| `pids.events: max` | 24 |
| `memory.events: max / oom / oom_kill` | 0 / 0 / 0 |
| `memory.peak` | 4 799 479 808 байт, около 4,47 GiB |

Достижение лимита процессов/потоков подтверждено. Эти счётчики накоплены за жизнь
контейнера: нельзя приписать все 24 отказа одному конкретному тесту. В сочетании
с `EAGAIN` это наиболее обоснованное объяснение падения клиента. Это **не**
ошибка `Java heap space`; увеличение только `-Xmx` её не устраняет.
В crash report указаны 3 доступных CPU и 32 логических CPU оборудования;
нельзя утверждать, что JVM обязательно использовала все 32 CPU.

После завершения задания Docker top всё ещё показывает четыре процесса Java
(34, 24, 84 и 37 потоков на момент чтения) и Xvfb. В базе только одно задание,
оно FAILED; каталоги requests/running/results пусты. Имеются оставшиеся процессы
после завершения задачи. `agent/daemon.py:66–70` завершает process group Codex,
но это не обеспечивает очистку отдельно отделившихся процессов Java/Xvfb.
Конкретная принадлежность каждого оставшегося процесса этому запуску и его
отделение от исходной process group не установлены: аргументы, окружение и
хранилища авторизации не читались. Наблюдаемый факт — Java/Xvfb остаются при
пустой очереди и единственном задании в FAILED.

## Почему не продолжились остальные раунды

- `agent/daemon.py:11,63–70`: общий лимит 1500 секунд и завершение процесса.
  В лимит входят анализ ТЗ, редактирование, Gradle, загрузка ассетов и игра.
- `worker/engine.py:436–456`: автоматический повтор предусмотрен для `RETRY`,
  отдельные паузы — для quota/auth. `TIMEOUT` попадает в окончательный FAILED.
- `worker/engine.py:460–462`: round обновляется и независимые проверки
  начинаются только после успешного завершения Codex. Поэтому `round=0`
  означает незавершённый первый раунд, а не отсутствие созданных файлов.
- `max_rounds=5` ограничивает цикл успешно завершённых этапов разработки и
  последующей проверки. Это не пять попыток восстановления после TIMEOUT.
- `common/db.py`: существующий resume рассчитан на USER_PAUSED/QUOTA_PAUSED;
  обычное возобновление FAILED не предусмотрено.
- `compose.yaml` не передаёт `AGENT_TIMEOUT_SECONDS` агенту и worker.
  Просто добавить эту переменную в `.env` сейчас недостаточно.

`last_error` сохраняет последние 900 символов журнала. В данном случае туда
попала справка Gradle и начало повторной команды, а структурированная причина
`TIMEOUT` оказалась в отдельном result JSON. Это ухудшает диагностику в UI.

## Что действительно сделано

В архиве два production-класса: `DefenseLifecycle` и `AutoDefenseClient`.
Реализованы:

- Fabric-каркас для Minecraft 1.21.11, закреплённые зависимости и Java 21;
- переназначаемая F8;
- enable/disable, ручной Stop/resume и клиентские команды;
- состояния и поколения сессии при смене мира/игрока, смерти и меню;
- пять unit-тестов и исходник клиентского теста переключения F8.

Боевого ядра, выбора целей, управления вводом, перемещения, настроек, публичного
интеграционного API и адаптера Saruman в сохранённых исходниках нет.
README честно описывает результат как первый этап без боя и движения.

| --- | --- |
| Ранние `./gradlew build` | Успешны, строки журнала 52 и 65 |
| Импорт `ClientCommands` | Ошибка компиляции в строке 69, исправлена на `ClientCommandManager` в 73 |

В исходниках нет собственного серверного теста, а client-only `auto_defense`
не включён в серверный список загруженных модов. Поэтому сообщение
`All 1 required tests passed` не доказывает F8, бой или интеграцию.

Клиентский тест скомпилирован, но его обнаружение средой ещё требует проверки:
в архиве нет `src/gametest/resources/fabric.mod.json`, а основной metadata
объявляет только `entrypoints.client`; в журнале есть
`processGametestResources NO-SOURCE`. Это возможное следующее препятствие,
а не доказанная причина данного падения.

В журнале 84 существует JAR 6,1 KiB с временем 23:47. После этого менялись
production-исходники; успешной финальной remapJar/build не видно. Соответствие
того JAR последним исходникам не подтверждено.

## Что известно об участии субагентов

В JSONL 106 корректных записей: 56 item.completed, 48 item.started,
один thread.started и один turn.started. Среди items: 79 command_execution,
10 file_change, 9 agent_message и 6 web_search. Отдельная строка 80 содержит
диагностику неудачного apply_patch вместо JSON; следующая правка применилась.

Нет экспортированных событий делегирования и идентификаторов отдельных
architect/reviewer/tester. Фразы «I’ll assign independent review» и
«The reviewer found…» — текст основного агента, а не независимое доказательство.
По этому экспорту нельзя подтвердить запуск субагентов или окончательно
исключить его: формат вывода установленной версии CLI может быть неполным.

Лаборатория создаёт роли и просит модель делегировать, но не проверяет получение
независимых ответов. Для надёжной МАС нужны наблюдаемые задания, результаты и
идентификаторы проверяющих, а не только указание в промпте.

Дополнительно необходимо проверять фактически загруженную конфигурацию:
проектные `.codex/config.toml` загружаются только для доверенных проектов.
Статус доверия этого запуска не установлен; глобальное хранилище не читалось.
См. [официальную документацию OpenAI](https://learn.chatgpt.com/docs/config-file/config-basic).
Публичный JSONL описан в [Non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode);
он не заменяет проверку конкретных возможностей установленной версии CLI.

## Ограничения резервной копии

Проверены SHA-256 всех 31 файла, перечисленного в manifest: совпали.
Приложенный внешний JSONL побайтово совпадает с архивным. Архив целостен,
однако текущая политика резервирования делает его неполным для восстановления:

- `backup/daemon.py:32–34` исключает build, все JAR/ZIP и изображения/видео;
- исключён даже `gradle/wrapper/gradle-wrapper.jar`, хотя журнал 91 подтверждает
  его существование: 45 633 байта;
- отсутствуют готовые JAR, XML/HTML результатов build и отдельный crash report;
- отсутствие входного стороннего JAR в таком архиве не доказывает, что его
  никогда не предоставляли: фильтр исключает и такие файлы.

Существующие исходники сохранены; повторять разработку с пустого проекта не нужно.

## Дополнительные замечания по коду

Это статические замечания независимого ревью, не причины TIMEOUT:

- `invalidate()` очищает world/player, сохраняя present/alive/menu. После
  observe → stop → resume state() может сразу вернуть OBSERVING до следующего
  observe, хотя ссылки на сессию очищены. Один тест закрепляет такое поведение.
  Следует определить и согласовать контракт возобновления до добавления InputDriver.
- Сообщение F8 выбирается только по enabled и может говорить «observing», когда
  фактическое состояние PAUSED, DEAD или WAITING_FOR_WORLD.

В базе есть большой временной разрыв: первое занятие задания в 23:41:10 UTC,
повторное в 07:28:00 UTC, ошибка в 07:35:42 UTC. Причина восстановления worker
по этим файлам не установлена. Возможна приостановка хоста/VM либо восстановление
обработчика; считать весь этот интервал активной работой модели нельзя.
