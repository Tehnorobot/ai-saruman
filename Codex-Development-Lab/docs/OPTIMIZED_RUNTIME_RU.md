# Оптимизированная работа агентов

Реализация: `optimized-roles-v1`. Планировщик, кодер и ревьюер сохраняются.
Новые LLM-роли, обязательное число задач и остановки по счётчику не добавлены.

## Что получает агент

В начале — небольшое представление `role_context`: область проекта, цель,
первичная ошибка, незапущенные проверки и ссылки. Полный вход сохранён отдельно
под хешем. Старый длинный отчёт ревью не дублируется в каждом запросе.

- `read_requirements` читает текущие R/C из semantic catalog. `namespace=legacy`
  нужен только для явно исторического реестра.
- `query_memory` фильтрует историю и имеет пагинацию. Публичные заметки текущей
  фазы доступны отдельной страницей `public_notes` и `public_cursor`.
- `read_artifact` читает диапазон строк, JSON pointer или страницу полного
  артефакта. Историческая версия сохраняет свой scope; она не становится текущим PASS.
- `read_diff` и `ReviewRequest.diff_ref` дают реальные изменения исходников.
- `record_note` сохраняет публичную гипотезу, наблюдение, решение и следующий шаг.
  Для новой гипотезы выдаётся ID; следующая оценка повторяет этот `hypothesis_id`.
  Можно явно связать condition/task/incident/finding/observation IDs.
- `read_execution` возвращает полный сохранённый вывод команды постранично.

Эти функции доступны нативным API-агентам и Codex через image-owned CLI:
`python3 -m agent.codex_tools TOOL JSON --context PATH`.
Контекст создаёт контроллер. В production CLI сверяет его с текущим запросом.
Read-only роли пишут заметки в свою существующую очередь, исходники остаются read-only.
После ответа публичные заметки и команды связываются с канонической памятью.

## Ошибки и прогресс

Падение общей сборки сохраняет точную команду, сообщение, полный build log и
ссылки на JUnit. Диагностика существует и тогда, когда игровые сценарии не начались.
Для старых прогонов создаётся производная навигация; оригиналы не переписываются.
Старые JUnit без доказательства свежести помогают диагностике, но не становятся
новыми результатами приёмки.

Незапущенная проверка получает `NOT_EXECUTED`, `attempted=false` и `stopped_by`.
Она не увеличивает число провалов продуктовой гипотезы. Пробелы наблюдений
учитываются отдельно. Реальные unit-наблюдения внутри упавшего build сохраняются,
но не подтверждают общую готовность и не доказывают игровые действия.

Наличие реализации (`unknown/absent/present_claim/buildable`) отделено от
проверенности. Ремонт существующего кода не требует автоматически включать весь
непроверенный граф. Реально отсутствующие зависимости и пользовательские внешние
блокировки сохраняются. `present_claim` — заявление, а не PASS.

## План, код и ревью

`depends_on_action_indexes` содержит только реальные зависимости действий;
адаптер больше не связывает соседние действия автоматически.
`action_outcomes` сообщает по назначенным действиям `implemented_claim`, `partial`,
`not_attempted`, `needs_experiment` или историческое `not_assessed`.
Перечисление action IDs само по себе не означает выполненную работу.

Ревью получает diff, затронутые условия и полный индекс старых замечаний.
`finding_id` сохраняется для той же проблемы. Новое замечание использует пустой
ID; контроллер назначает постоянный. `resolved_finding_ids` закрывает только явно
рассмотренные замечания. Это оценка ревью, не независимый результат теста.
Ревьюер сопоставляет цель действия, ID условия и смысл исполняемого assertion.

При обновлении существующего semantic проекта следующая работа выбирается
заново с текущей диагностикой и доступностью реализации. Принятые ТЗ, каталог,
граф, частичный код и история сохраняются; декомпозиция с нуля не требуется.
Текущий план и его предыдущие результаты остаются в архиве.

## Продолжение после сбоя

Завершённые tool exchanges и публичное состояние фазы сохраняются по устойчивому
ключу. При сетевом retry они восстанавливаются, если вход и протокол совместимы.
Скрытое reasoning и signatures в общую память не записываются; для такого
протокола используется новое продолжение с публичными результатами и полными refs.
Исход команды с неизвестным завершением сначала сверяется, а не выполняется повторно.

`run_command` сохраняет stdout/stderr и метаданные до возврата результата, включая
timeout. Значение timeout команды остаётся явным выбором агента. Мягкая граница
фазы не обрывает процесс. Пауза пользователя и его бюджет имеют приоритет.

## Повторное использование запусков

По умолчанию сценарии исполняются отдельно. Для действительно одинаковых unit
запусков кодер и ревьюер могут явно задать:

```json
"reuse": {
  "group": "unit-suite",
  "profile": "default-test",
  "initial_state": "clean-unit-process"
}
```

Совпасть должны команда, инвентарь, тип, source/spec, окружение и начальное
состояние. Gameplay не объединяется. Один свежий физический запуск даёт несколько
логических проекций с одним `execution_id`. Отчёты по-прежнему проверяются по хешам.
Результат другого source или прошлого запуска не подставляется.
Свежий общий Gradle build может дать ту же unit-suite только при явном согласии
и полном совпадении инвентаря. Компиляционный кэш сохраняется; результаты Test
должны быть свежими.

## Проверки и ограничения доказательств

Полная память не сокращается. Ограничение страницы означает `partial` и cursor,
а не удаление остальных данных. Сводки больше не ограничиваются первыми 64 тестами.
Кэшированные токены показаны как повторно использованный вход; без тарифов нет
утверждения о денежной экономии.

Оригинальные доказательства, изоляция каталогов, проверка хешей и независимый
исполнитель остаются обязательными. Фото/видео не блокируют разработку.
Проектный анализ и причины решений: [аудит](PIPELINE_OPTIMIZATION_RU.md).
