# Прогресс отдельного условия и выбор следующей работы

Прогресс учитывается по ключу `condition_id → scenario_id → checkpoint_id`.
Например: `C26 → survival-retreat → CP2`. Текст ошибки, ревизия исходников и
результат соседнего теста не меняют этот ключ и не обнуляют нерешённую попытку.

## Что считается наблюдением

- Источник — только независимый `VerificationResult` с исполнителем `runner`.
- В историю попадают только сценарии, включённые в этот прогон.
- Пропуск или падение до проверки сохраняет нерешённую историю; это не PASS.
- PASS того же чекпоинта закрывает текущую последовательность неудач.
- Повторное чтение одного результата после восстановления контроллера не создаёт новую попытку.
- Переименование или удаление падающего чекпоинта не закрывает его историю автоматически.
- Другое ТЗ или другой проект не наследует прежние результаты.

Если условие назначено в плане, но результат не содержит ни одного связанного
наблюдения, история явно отмечает отсутствие проверки (`scenario_id` и
`checkpoint_id` равны `null`). Получение реального измерения закрывает этот
пробел как `OBSERVATION_AVAILABLE`, а не PASS условия. Провалы настоящего
чекпоинта при этом остаются открытыми.

Полная история сохраняет ссылки на принятый план и гипотезы, отчёт кодера и
изменённые файлы, независимый результат и последующий анализ планировщика.
Подтверждение или опровержение гипотезы объясняет модель по измерениям. Скрипт
не определяет смысл ошибки по словам и не выдаёт предположение за доказательство.

## Вход агентов

В `PlannerInput` и `CoderAssignment` добавлено необязательное поле
`condition_progress_ref: ArtifactRef`. Старые контрольные точки остаются допустимыми.
Ревьюер получает такую же ссылку внутри документа `ReviewRequest.context_ref`.
Выходные форматы моделей не изменены; новых агентов или дополнительных вызовов нет.

Ссылка ведёт к краткому индексу. Каждое условие имеет `history_ref` на полный
документ. Индекс показывает незакрытые проверки, ранее падавшие проверки,
изменения контракта теста и доступную независимую работу. Массовые успешные
модульные кейсы представлены счётчиком и полной ссылкой, а не копируются в промпт.
У каждой требующей внимания пары сценарий/чекпоинт есть собственная `history_ref`:
для диагностики одного CP не требуется читать историю остальных проверок условия.

Контроллер хранит индекс в `pipeline/condition-progress.json` каталога результатов.
Для агентов актуальная копия находится в `.lab-pipeline/condition-progress.json`.
В запросах используются адресуемые по содержимому снимки индекса и историй:
следующее обновление не уничтожает старую ссылку. Оригиналы событий остаются
в `pipeline-memory`, их доступные зеркала — в `.lab-memory/pipeline`.

Для существующих проектов история восстанавливается из полного архива событий
и сохранённых контроллером манифестов соответствующих прогонов. Новые связи
между условием, чекпоинтом и результатом дополнительно сохраняются неизменяемым
событием `ConditionObservationMapping`. Недоступные старые соответствия перечисляются
в `unmapped_verification_refs`; контроллер их не угадывает.

## Выбор следующей работы

Повтор нерешённого наблюдения — сигнал для рефлексии, не предел числа попыток.
Планировщик читает историю и выбирает новый различающий эксперимент, конкретное
исправление либо независимую функциональность. Общая сигнатура ошибок раунда
больше не скрывает застой отдельного условия.

`selection_advice` перечисляет независимые задачи и задачи, зависящие от
нерешённых условий. Это подсказка по графу, не автоматическая смена назначения.
Количество связанных задач определяет планировщик. При выборе только диагностики
он объясняет, почему независимая работа сейчас менее полезна или недоступна.

Для переноса остаётся прежний формат `deferred`:

```json
{
  "task_id": "T13",
  "reason": "Проверить отличающую причины гипотезу отдельным экспериментом",
  "return_when": "Получен независимый результат этого эксперимента"
}
```

Контроллер сохраняет незакрытые записи возврата между раундами. Полные прежние
решения остаются в памяти даже после закрытия текущего пункта.

## Ревью смысла теста

Ревьюер сопоставляет исходное условие, прежние контракты чекпоинтов и реальный код
новых утверждений. Исправление неправильного оракула или фикстуры допустимо при
сохранении требуемого действия и его эффекта. Удаление утверждения, условный обход,
проверка одного токена состояния или переименование теста сами по себе не доказывают
работоспособность. Эти выводы делает существующий ревьюер; новых скрытых требований
к продукту нет.

Пользовательские бюджеты, пауза и изоляция сохраняются. Счётчики не вводят новых
остановок и не меняют независимые вердикты приёмки.

## Статусы в панели

В «Задачи и условия» показан один короткий текущий статус. «Ещё не проверено»
отличается от «Проверка не завершена». Если проверка раньше проходила, но свежего
подтверждения нет, показано «Нужна перепроверка». Настоящий FAIL остаётся красным,
а прежний PASS не делает текущую версию подтверждённой.

Закрытая по умолчанию «История проверки» показывает общий успешный раунд и
результат последнего прогона. Успехи разных условий в разных прогонах не
представляются как общий успех задачи. Раскрытие сохраняется при обновлении панели.
Это только представление: исходные статусы, доказательства и решения приёмки не меняются.
