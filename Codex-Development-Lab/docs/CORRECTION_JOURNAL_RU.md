# Журнал исправлений формата

Журнал хранит промежуточные ошибки ответа LLM и связанные исправления. Он не заменяет историю разработки и результаты тестов.

1. Адаптер сохраняет полный публичный ответ до исправления, точные ошибки и ID `C-…`.
2. Модель получает короткую сводку. Повторяющиеся ошибки одного поля объединяются. Полный пример контракта не повторяется в каждом сообщении об ошибке.
3. Через `read_correction` модель читает нужное поле, ошибки или связанный исправленный ответ.
4. Контроллер переносит записи в постоянную память после попытки, включая неудачную. Повторный импорт не создаёт дубликаты.
5. Следующая попытка получает ссылку `correction_index_ref`. Сами полные ответы в начальный контекст не вставляются.

Пример вызова инструмента:

```json
{"record_id":"C-0123456789abcdef0123456789abcdef","section":"submission","path":"$.findings[0].code_refs"}
```

Доступные разделы: `index`, `summary`, `issues`, `example`, `submission`, `resolution`. Для индекса допустим пустой `record_id`. Большие ответы читаются по `next_offset`; исходная запись сохраняется полностью. `example` показывает пример именно для ошибочного поля, `read_output_format` — полный доверенный формат.

Постоянные записи находятся в `artifacts/<job-id>/pipeline-memory/`. Агент читает защищённую копию в `.lab-memory/pipeline/`. Навигационный индекс экспортируется в `.lab-pipeline/corrections-index-<контракт>.json`. Codex CLI читает эти файлы своими инструментами; API-агенты также имеют `read_correction`.

Статусы:

| Статус | Значение |
|---|---|
| `rejected` | Ответ отклонён; причины сохранены |
| `accepted_format` | Адаптер принял JSON и схему |
| `accepted_controller` | Контроллер принял ответ и проверил ссылки/область действия |

Ни один из этих статусов не означает PASS игрового теста. Исправление связано с ошибками через `resolves`. Незакрытые ошибки привязаны к конкретной фазе, входным данным и раунду; старые записи остаются доступны для справки. Данные другой версии ТЗ не подмешиваются в текущий индекс.

Журнал начинает собирать новые события после обновления. Он не восстанавливает отсутствующие промежуточные ответы из старых журналов. Приватные рассуждения модели и ключи API не являются содержимым журнала.

## Точечные правки

Для разбираемого JSON с адресуемыми ошибками используется `SubmissionPatch`. Модель указывает хеш сохранённого ответа и операции с путём поля, ожидаемым старым и новым значением. Значения передаются сериализованным JSON в `expected_old_json` и `new_json`. Контроллер применяет операции к копии. Полная замена корня, изменение полей вне ошибок, несовпадающие старые значения и устаревший хеш отклоняются.

Коррекция формата API идёт в отдельной короткой переписке с той же выбранной моделью. В ней доступны только `read_patch_field` и `submit_patch`. Она использует общий бюджет запросов; исходники и история проекта в неё не передаются. Исправления ошибок, обнаруженных контроллером, также запрашиваются через `SubmissionPatch`. Эти попытки выполняются в контейнере с проектом только для чтения, включая исправление отчёта кодера; выбор модели и роль сохраняются.

Планировщик получает `task_index`: реальные ID, названия задач, зависимости, условия и связанные открытые вопросы. Передача задач не может переименовать или разделить существующие задачи. Для изменения графа нужен отдельный контракт графа. Проверка выдаёт точные лишние, отсутствующие и повторные ID и пути ошибочных полей. Независимые ошибки классификации собираются вместе.

После применения правки повторяются проверки полного ответа, scope, связей и цитат. Наблюдения предыдущей попытки сохраняются со ссылкой и проверяемым хешем, пока исходники не изменились. Если JSON вообще не разбирается или ошибка требует нового анализа, остаётся обычная сдача ответа с диагностикой. Точечная коррекция не разрешает угадывать продуктовые решения.

Обновление не повышает бюджет проекта и не возобновляет задания. Исчерпанный лимит запросов остаётся отдельным ограничением, заданным пользователем.
