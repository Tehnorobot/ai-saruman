# Классификация ошибок выполнения

Контроллер принимает решения по структурированным кодам терминальных ошибок и фактическим HTTP-статусам. Текст HTML, результаты инструментов и параметры запроса не определяют повтор, паузу или восстановление контейнера.

## Источники решения

| Источник | Проверяемые данные | Реализация |
| --- | --- | --- |
| API агента | `error.code`, HTTP-статус шлюза и `diagnostic.upstream_status` | `common/provider_failures.py`, `agent/dslab.py` |
| Повтор шага | Терминальный код временного отказа, обрыва потока или ошибки генерации | `worker/pipeline.py` |
| CLI | Код верхнеуровневого события `turn.failed` / `error` | `worker/engine.py` |
| Runner | `RunnerAPIError.status` | `worker/sandbox.py` |
| Docker Engine | `EngineHTTPError.status` | `runner/engine.py`, `runner/broker.py` |

Для старых записей без кода сохранена совместимость с известными сообщениями адаптера. Она проверяет терминальное сообщение, а не произвольные слова во всём журнале. Неизвестный явный код не заменяется догадкой по описанию.

Полная диагностика сохраняется отдельным событием `provider.error`. Краткое терминальное сообщение содержит код и статусы даже при сокращении текста.

## Проверки

- Слова `configuration`, `quota`, `max_tokens` в HTML не меняют классификацию HTTP 503.
- Сообщение инструмента не может имитировать терминальную ошибку авторизации или квоты.
- HTTP-статус внутри имени модели или другого параметра запроса не влияет на повтор.
- Текст `404` в теле HTTP 500 не означает, что контейнер отсутствует. Маркер восстановления и блокировка сохраняются.

Это устраняет ненадёжные решения по тексту. Само по себе обнаружение этих мест не доказывает возможность внешней атаки на хост.
