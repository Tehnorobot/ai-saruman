# Память, достоверный статус и проверки

## Сохранение и восстановление

Полные оригиналы событий остаются в `artifacts/<project>/<job>/pipeline-memory`.
Агент читает копии из `.lab-memory/pipeline` своего проекта.

Синхронизация сравнивает байты обычных файлов. Совпадающая копия не
перезаписывается; отсутствующая или повреждённая восстанавливается из оригинала.
Размер или время изменения сами по себе не подтверждают совпадение.
Индекс записывается один раз за проход и только при изменении. История не
обрезается. Ссылки и выход за разрешённые пути по-прежнему отклоняются.

Контроллер проверяет паузу и продлевает lease во время синхронизации. Событие
фиксируется в оригинальном архиве и в указателях состояния до экспорта копии.
Прерывание экспорта не удаляет оригинал; следующий проход восстанавливает копию.
Журнал исправлений читается по нужной схеме; уже проверенные неизменяемые записи
повторно не загружаются при каждом исправлении. Изменение версии ТЗ разделяет кеши.

## Отображение работы

Получение завершённого ответа фиксируется до архивации и разбора формата.
Окно показывает «Сохраняет результат агента», «Синхронизирует память» с числом
записей или «Ожидает восстановления квоты». Эти операции не обозначаются как
написание кода. Ручная пауза имеет приоритет и не снимается обновлением.

## Реестр тестов

Для проекта Auto Defense классы групп addon/management/delivery выбираются
в одном месте. JUnit Launcher до исполнения обнаруживает тесты и сохраняет
реестр в `build/verification`. Gradle сверяет свежие результаты с этим реестром.
Добавление обычного `@Test` в выбранный класс не требует второго списка методов.

`tools/sync-unit-registry.py` обновляет только предложение кодера по реестру
обнаружения. Он сохраняет существующие связи чекпоинтов; новые тесты не получают
выдуманного покрытия. Пропуск, ошибка, дубликат или отсутствие ожидаемой проверки
не даёт PASS. Успешное обнаружение тестов не заменяет их исполнение.

## Предусловия игрового сценария

Необязательное поле `execution.precondition_tests` содержит точные JUnit-имена
проверок фикстуры. Пример части сценария:

```json
{
  "execution": {
    "expected_tests": [
      {"classname": "example.AirTest", "name": "fixtureReady"},
      {"classname": "example.AirTest", "name": "targetDamaged"}
    ],
    "precondition_tests": [
      {"classname": "example.AirTest", "name": "fixtureReady"}
    ]
  }
}
```

Это фрагмент, а не полный контракт. Предусловие проверяет блоки, сущности и
синхронизацию до действий продукта. Его нельзя одновременно использовать как
доказательство выполнения продуктового условия. Проверку удара, лечения,
выстрела или выбора цели нельзя объявлять предусловием ради обхода FAIL.

В многоэтапном сценарии запись предусловия может содержать `checkpoint_ids`:
список только зависимых чекпоинтов. Отсутствующий или пустой список означает
весь сценарий. Сбой поздней фикстуры не стирает независимый результат раннего
этапа. Уже наблюдавшийся FAIL продукта сохраняется, если поздняя проверка
фикстуры вообще не была исполнена: отсутствие этой проверки не оправдывает
раннюю ошибку.

Независимый исполнитель читает свежие отчёты JUnit с проверкой хешей.
При неверной или неподтверждённой фикстуре зависимые наблюдения получают
`NOT_EXECUTED`, а `fixture_result` хранит причину, проверки и исходные результаты
чекпоинтов. Условия остаются открытыми; прежние ошибки не закрываются.
Остальные сценарии продолжаются. Исходные отчёты и неудачные утверждения
сохраняются полностью. Старые манифесты без поля сохраняют прежнюю семантику.

Пересечение предусловия и продуктовой проверки проверяется до принятия отчёта
кодера. Все конфликты возвращаются ему за один проход: файл, сценарий, тест,
контрольная точка и условие. Для исправления внешнего файла кодер сохраняет
доступ к редактированию; правка одного JSON-отчёта этого не исправит.
Сохранённые результаты повторно проверяются при продолжении. Неверный
`development-ready` архивируется, работа возвращается к прежнему заданию
кодера. План, граф, исходники и история сохраняются. Автоматического удаления
контрольных точек или назначения PASS нет.

## Планирование следующей работы

Планировщик разделяет дефекты аддона, фикстуры, реестра проверок и провайдера.
Для действия описывает гипотезу, изменение и наблюдение, различающее причины.
Связанные изменения объединяются по общему смыслу и удобству проверки;
фиксированного числа задач нет. Исправление общей тестовой обвязки не закрывает
все функции, которые эта обвязка затрагивает. Повторный провал требует нового
эксперимента либо независимой работы с конкретным условием возврата.

Ревьюер проверяет сохранность смысла утверждений. Код, история и результаты
предыдущих раундов сохраняются. Новых агентов, искусственных лимитов попыток
или остановок по счётчику это обновление не добавляет.
