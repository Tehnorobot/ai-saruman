# Компактный обмен между агентами

Модель возвращает машинное решение отдельно от объяснения. Контроллер проверяет допустимость действий. Ревьюер оценивает смысл. Независимый процесс запускает тесты и устанавливает их результат.

## Форматы

| Этап | Машинный JSON | Объяснение |
|---|---|---|
| Разбор ТЗ | `AgentCatalog`: требования, условия, вопросы, диапазоны ТЗ | Markdown |
| Изменение каталога | `AgentCatalogPatch`: только операции над изменёнными записями | Markdown |
| Граф | `AgentGraph`: задачи и зависимости | Markdown |
| План | `AgentPlan`: действия, существующие ID, ожидаемые наблюдения, регрессии, ручные проверки, внешние зависимости | Markdown: причины, гипотезы, эксперименты, отложенные решения |
| Кодер | `AgentReport`: путь сценариев, ответы на замечания, непроверенные утверждения и открытые проблемы | Markdown: изменения, результаты диагностики, риски |
| Ревьюер | `AgentReview`: решение о следующем этапе, проверенные условия, замечания | Markdown: наблюдения, ошибки логики, предложения и неизвестные |
| Тестовые сценарии | `AgentScenarios`: связь с условиями, настоящие тесты, контрольные точки и параметры запуска | Markdown: пояснения сценария |

Для JSON обязательны поля схемы, но структура текста не регламентируется. Объяснение можно выдать обычным видимым Markdown перед финальной машинной сдачей. Оно не считается ошибкой JSON. Поле `notes_md` тогда может быть пустой строкой. API использует `submit_result`; Codex CLI возвращает компактный JSON последним сообщением. Схема и пример передаются для конкретного этапа. Новых фиксированных квот на количество задач нет.

## Что больше не генерирует модель

Контроллер добавляет проект, раунд, версии ТЗ и исходников, хеши, MIME и известные ссылки на входные документы. Для кода он сравнивает реальные файлы с исходным снимком, записывает изменённые и удалённые пути. ID действий и замечаний назначаются по порядку; порядок действий сохраняется. Старые внутренние контракты `PlannerDecision`, `CoderReport`, `ReviewResult` и другие остаются форматом постоянного хранения.

В каталоге необходима проверяемая связь с ТЗ. Модель указывает путь и диапазон строк; контроллер читает настоящий текст и вычисляет хеш. В сценариях модель указывает путь настоящего тестового файла; контроллер вычисляет его метаданные и текущую область действия сценариев. Определения тестов остаются JSON, потому что по ним запускается проверка.

## Где хранится информация

- Полный публичный журнал каждой попытки остаётся в истории агентов.
- Исходное компактное сообщение и все текстовые разделы сохраняются отдельным событием постоянной памяти.
- Markdown сохраняется без пересказа в `.lab-pipeline/report-<этап>-<хеш>.md`; его содержимое и ссылка также находятся в постоянной памяти задания.
- Вложенное описание `AgentScenarios` сохраняется до преобразования, включая весь Markdown. Нормализация не удаляет оригинал.
- Следующие этапы получают `agent_report_refs` для адресного чтения объяснений. Полная история доступна через индекс памяти.
- В окне «Пайплайн и решения» → обзор/ревью есть раскрываемый блок «Полный отчёт · Markdown». Текст показывается безопасно, без исполнения HTML.

Строгое машинное хранение не означает, что модель должна заново составлять этот формат. Совместимость UI, памяти и тестового процесса обеспечивается преобразованием в контроллере.

## Фото и видео — дополнительные материалы

Запись тестового видео, скриншоты, формат, длительность и качество записи не являются задачами кодера и не должны создавать внешние зависимости или запросы к пользователю. Runner и панель прикладывают доступные материалы автоматически. `AgentScenarios` больше не содержит поле `media`; агент описывает реальные игровые проверки, а не оформление записи.

Отсутствие или повреждение записи не меняет результат настоящего JUnit-теста. Небезопасные или повреждённые файлы не прикладываются, а причина сохраняется в диагностике. Реальные падения, пропущенные утверждения, устаревшие исходники и неверные отчёты продолжают препятствовать PASS. Это относится к материалам тестирования, а не к функциям мода, который сам работает с изображениями или видео.

Для существующего проекта деревьев пользователь явно отменил обязательность пункта C60 о приложенном видео. Контроллер хранит это уточнение в `pipeline/evidence-policy.json` с хешем исходного условия и версией ТЗ. C60 и связанные только с ним вопросы исключаются из активной обязательной приёмки, но сохраняются полностью в памяти и показываются как дополнительные материалы. Они не помечаются PASS. Проверка фактического роста дерева остаётся обязательной. Старое ожидание параметров записи снимается без сброса исходников.

Проекция не использует поиск слов «видео» в условии: это могло бы ошибочно убрать настоящую игровую проверку. Если смысл условия или версия ТЗ изменились, старое исключение не применяется автоматически. При исключении отдельной задачи записи сохраняются транзитивные функциональные зависимости её соседей.

## Когда меняется граф

Принятый граф стабилен при обычном выборе пакета. Планировщик может отдельно запросить изменение функционального разбиения или смысла зависимостей. Нельзя удалять настоящую предпосылку только потому, что она не выбрана в пакете.

Структурно корректный новый граф принимается отдельно. Если затем пакет не учитывает его зависимости, ошибка возвращается в `AgentPlan` с указанием отсутствующей предпосылки. Граф повторно не генерируется для исправления ошибки пакета. Кодер получает только пакет, прошедший актуальную проверку ID и зависимостей. Старые ошибочно направленные в граф сообщения об `actions` также перепроверяются на правильном этапе.

## Что проверяется

Сохраняются проверки схемы машинной части, существования ID, зависимостей, покрытия назначенных условий ревью, безопасных путей, текущих версий файлов, бюджета и изоляции. Итоговая готовность требует независимых проверок всех условий и полного заключительного ревью. Ни Markdown, ни согласие ревьюера не создают PASS.

Совпадение текстовой цитаты с результатами чтения больше не блокирует планирование или ревью. Старые цитаты могут дать информационное замечание для ревьюера. Контроллер не подменяет этой проверкой анализ смысла.

Отдельная LLM-классификация всех задач в `PreparationHandoff` не требуется. Контроллер маршрутизирует уже записанные вопросы: технический эксперимент, пользовательское уточнение, внешняя зависимость. Сам пакет работы выбирает планировщик. В `external_updates` он может явно записать внешнюю блокировку или её разрешение. Разрешение не считается прохождением теста; пользовательский вопрос нельзя закрыть таким обновлением. Если записаны зависимые внешние блокировки, нужно явно разрешить и их.

### Исследование и реализация в одном пакете

Статус `experiment` описывает неизвестный факт и не запрещает писать код. Планировщик может назначить исследование API и реализацию вместе. Кодер изучает реальные исходники/JAR, реализует решение по найденным фактам и готовит проверки. Для этого не требуется отдельное разрешение планировщика или ожидание часового порога.

Если фактов недостаточно, кодер сохраняет результаты исследования и открытый вопрос, откладывает только затронутую работу и продолжает независимые задачи пакета. Игровую проверку по-прежнему запускает независимый процесс. Кодер не может выдумать API, результаты Minecraft или PASS. Ревьюер проверяет обоснованность решения и достаточность сценариев.

Настоящее пользовательское уточнение или внешняя зависимость продолжают ограничивать соответствующие задачи и их зависимости. Проверки ID, порядка действий и графа остаются. Открытые технические вопросы сохраняются до обоснованного разрешения и не позволяют объявить готовность проекта автоматически.

## Совместимость и исправления

Принятые старые контрольные точки используются без новых вызовов модели. Старые точечные правки `SubmissionPatch` остаются исполнимыми в прежнем формате. Исходники, старые каталоги, графы, результаты и журналы не сбрасываются. Старое отклонение только по происхождению цитаты превращается в информационную запись.

Старое отклонение только из-за запрета реализации `experiment` также снимается. Если сохранённый ответ доступен по прежнему хешу и проходит текущие проверки схемы, области действия, исходников, ID и зависимостей, контроллер использует его без повторного планирования. При этом восстанавливаются исходные обновления внешних зависимостей из записи коррекции. При иных ошибках, изменении файлов или недостатке данных ответ не принимается автоматически. Устаревшая причина удаляется из активной коррекции, но полный отказ остаётся в памяти.

Новые адресуемые ошибки исправляются точечной правкой компактного документа с проверкой исходного хеша. После преобразования повторяется проверка полного внутреннего результата. Объяснения предыдущей попытки сохраняются и при исправлении JSON.

Обновление не возобновляет задания, не меняет модели, бюджет или `.env`. Реальное качество и скорость выбранной LLM проверяются после продолжения; автоматические тесты протокола не являются оценкой качества генерации модов.

## Файлы реализации

- `common/agent_protocol.py` — компактные форматы и преобразование.
- `worker/pipeline.py` — выбор формата, постоянная память, нормализация и маршрутизация.
- `common/preparation.py` — зависимости и состояния вопросов.
- `agent/dslab.py` — API-сдача, свободный Markdown и коррекции.
- `schemas/pipeline/Agent*.schema.json` и `examples/Agent*.json` — схемы и примеры.
- `schemas/pipeline/generate_agent_protocol.py` — воспроизводимая генерация компактных артефактов из внутренних контрактов.
- `tests/test_agent_protocol.py` — сквозные проверки, сохранение текста и продолжение старых проектов.
