# Доступ к файлам и запуск сборок

Из папок Windows к сервисам подключаются только рабочие подпапки `Codex-Development-Lab`.
Домашний каталог Windows, соседние проекты, Downloads и диски целиком не
подключаются. Весь корень лаборатории тоже не подключается: в нём есть `.env`
и служебный код. `.env` читает Compose на компьютере; контейнер `storage`
получает только перечисленные в Compose настройки S3.

| Компонент | Доступ к постоянным данным |
| --- | --- |
| `agent` / Codex | `projects/`, `agent-tasks/`, собственные Docker volumes авторизации и Gradle |
| `worker` | `projects/`, `data/`, `artifacts/`, `agent-tasks/`, `backup-requests/` |
| `dashboard` | `projects/`, `data/`; результаты, бэкапы и `agent-tasks/` только для чтения |
| `backup` | исходники и артефакты только для чтения; база, запросы и `backups/` для записи |
| `storage` | артефакты только для чтения, собственный volume индекса S3 |
| `runner` | Docker socket, закрытый volume временных копий и служебный Unix socket; без папок Windows и авторизации |
| `egress` | никаких папок хоста, Docker socket или авторизации; только сетевой прокси |
| Контейнер сборки | копия одного workspace, защищённый каталог экспорта и кэш этого проекта в закрытом volume |

Агент пока видит все проекты лаборатории, а не только текущий. У него нет
Docker socket, базы очереди или папки артефактов. Сгенерированный код может
выполняться при работе Codex с полномочиями этого контейнера. Авторизация Codex
остаётся доступна самому агенту, поскольку нужна для запросов модели.

## Как работает запуск

1. `worker` под блокировкой проекта упаковывает workspace в архив.
2. `runner` принимает идентификаторы проекта/задания, фиксированный режим проверки,
   её таймаут и флаг EULA. Отдельный интерфейс команд принимает argv, запись, CI
   и EULA. Поля Docker API, пути хоста, образ и настройки
   привилегий не принимаются. Прямого проксирования Docker API нет.
3. Архив распаковывается в отдельный каталог закрытого Docker volume. Каталоги
   заданий создаёт только `runner`; агент и worker не видят этот volume.
4. Для раунда создаётся контейнер с тремя подкаталогами этого volume:
   `/workspace`, `/output` и `/cache`. Кэш доступен только своему проекту;
   родительские каталоги принадлежат root и не подключены внутрь задания.
   Bind mounts хоста в конфигурации задания отсутствуют.
   Образ фиксируется по локальному image ID при старте `runner`.
5. После остановки контейнера исходники возвращаются в `projects/<id>/workspace`.
   Верхние `.lab-cache`, `.gradle` и `build` исключены из передачи. Кэш и build
   остаются в Linux-томе для следующего раунда; JAR, отчёты и запись экрана
   экспортируются в артефакты. Временный контейнер и его рабочая копия удаляются.
   Запросы одного проекта не выполняются одновременно.

Пути архивов проверяются при отправке и получении. Абсолютные пути, `..` в
именах, hard links, устройства, FIFO, выходящие наружу или циклические symlinks
не принимаются. Относительные ссылки внутри workspace, например npm `.bin`,
поддерживаются. Работа с файлами использует открытые дескрипторы каталогов и
`O_NOFOLLOW`, чтобы не перейти по подменённой ссылке. Возврат workspace использует
атомарный обмен каталогов Linux `renameat2`. В подключённых папках Windows,
где такой обмен не поддерживается, применяется журнал
`.lab-workspace-swap.json`: после прерывания восстановление завершает перенос
новой копии либо возвращает исходники, если новая копия отсутствует.

Все команды проекта выполняются как UID/GID 1000, без capabilities и дополнительных
групп. Доверенный supervisor проверки работает как root только с SETUID/SETGID,
чтобы отделить проект от защищённого `/output`; модель не выбирает его код или
аргументы. Корень read-only, включён `no-new-privileges`, пределы — 4 CPU, 6 GiB
RAM и 768 процессов. `/tmp` временный. Бюджет каждой стадии — 60–1800 секунд;
worker по умолчанию задаёт 900. Общий жёсткий предел runner — 7200 секунд.
Архив ограничен 20 GiB содержимого и 200 000 записей.

Агент и проверки подключены к разным `internal` bridge-сетям с режимом шлюза
`isolated` для IPv4/IPv6. У них нет маршрута к сервисам Windows, локальной сети
или прямому Интернету. Выход выполняется через rootless `egress`: HTTP на 80,
CONNECT на 443, без расшифровки TLS. Прокси проверяет все DNS-ответы и соединяется
с проверенным числовым IP; частные, loopback, link-local и переходные IPv6-адреса
запрещены. Java получает настройки прокси отдельно через `JAVA_TOOL_OPTIONS`.
`worker`, `runner`, `backup` и init-сервис работают с `network_mode: none`.

Для запуска используйте `START_WINDOWS.ps1`: он проверяет итоговую конфигурацию
Compose с учётом override-файлов, разрешённые подпапки, отсутствие junction/symlink
в путях подключений, права, доверенные команды и метаданные существующих volumes.
Папка лаборатории целиком, `.env`, домашний каталог и соседние проекты запрещены.
Проверка не заменяет доверие к исходникам самого runner и установленным образам.
HTML/XML отчёты скачиваются как вложения, с sandbox CSP и `nosniff`.

Только доверенный `runner` управляет Docker через настоящий socket. Поэтому
его код входит в границу доверия. Пользовательский код там не исполняется,
корневая файловая система read-only, сеть отключена, портов нет.
Защита не означает устойчивость к уязвимостям самого Docker/ядра или к
изменению конфигурации лаборатории владельцем компьютера.

## Обновление существующей установки

Дождись окончания текущей сборки или поставь задание на паузу и дождись
подтверждения в панели. Это позволяет старому worker остановить созданный им
контейнер и сохранить изменения до смены механизма запуска.

```powershell
docker compose stop
docker ps -a --filter label=codex-lab.role=project-test --format "{{.ID}} {{.Names}}"
```

Если остались контейнеры старого вида `codex-lab-test-<job-id>`, сначала проверь
каждый через `docker inspect <ID>`: имя, label проекта и подключённый workspace
должны относиться к этой лаборатории. Затем останови и удали именно этот
контейнер командой `docker rm -f <ID>`. Не удаляй чужие контейнеры или volumes.
Старый `.lab-runner.json` соответствующего проекта можно удалить только после
подтверждённого удаления указанного в нём контейнера. Обычная пауза со старым
worker выполняет эту очистку сама.

```powershell
powershell -ExecutionPolicy Bypass -File .\START_WINDOWS.ps1
```

`START_WINDOWS.ps1` строит четыре образа, включая `egress`. Существующие исходники, бэкапы,
`.env` и volume входа Codex сохраняются. Не используй `down -v` для обновления.

## После прерывания

Состояние запуска хранится в закрытом volume `runner_state`, а в проекте —
маркер `.lab-runner.json`. После перезапуска служба останавливает оставшиеся
свои контейнеры. Worker возвращает сохранённый workspace перед продолжением.
Если остановка или возврат файлов не подтверждены, проект остаётся заблокирован
для агента и бэкапов; причина находится в логах `worker` и `runner`.

Не удаляй `runner_state` и маркеры во время восстановления: там может находиться
результат последней проверки, ещё не перенесённый в `projects/`.
Журнал `.lab-workspace-swap.json` и каталоги `.lab-incoming-*`/`.lab-previous-*`
также принадлежат восстановлению; не удаляй их вручную при незавершённом переносе.

Результаты независимой проверки: [RUNNER_VALIDATION_RU.md](RUNNER_VALIDATION_RU.md).
