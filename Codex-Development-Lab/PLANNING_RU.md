# Планирование и ручная приёмка

> Историческое описание прежнего контроллера. Правила одной группы, квоты
> задач/проверок и остановки по числу исправлений ниже не являются текущими.
> Текущий процесс: [оптимизированные роли](docs/OPTIMIZED_RUNTIME_RU.md).

## Проверяемый результат каждого действия

После подтверждённых сборки и игрового запуска контроллер включает
`round_progress_policy`. Каждое действие, включая дополнительные задачи пакета,
обязано содержать `expected_progress` с видом работы и наблюдаемым результатом:

```json
"expected_progress": {
  "kind": "new_behavior",
  "observable_result": "Персонаж атакует ближайшего врага через UnionClef и освобождает управление после остановки"
}
```

Для реализации нужны незавершённые исходные `condition_ids`, `verification_kind`
и конкретный `verification_objective`. Новым результатом может быть функция или
содержательная исполняемая проверка существующей функции. Ремонт относится к
конкретному независимо наблюдавшемуся сбою. Отдельная проверка допустима для
непроверенного/устаревшего сценария, обзор — для сопоставленных условий с ожидающим
обзором. Ремонт сборки/схемы требует реального отказа; ручной ход — проверяемых
инструкций и обоснованного отсутствия автоматической возможности.

Виды: `new_behavior`, `repair`, `verification`, `coverage`, `infrastructure`,
`diagnosis`, `manual`. Вид соответствует действию, а не произвольному заявлению
модели. Документы, упаковка и повторение неизменённого успешного сценария не
подменяют назначенный функциональный результат. Технические требования самого ТЗ
не удаляются: им по-прежнему нужны уместные независимые проверки.

После проверки контроллер сохраняет `round-progress-outcome.json`: ожидаемый
результат и фактические исполнения связанных сценариев. `execution_observed`
означает наблюдавшуюся попытку, в том числе FAIL; это не подтверждение достижения
цели и не PASS требования. Для обзоров и других неигровых ходов это поле не является
оценкой успеха (`execution_applicable=false`). Диагностика известного сценария
также учитывает фактическое исполнение. Приёмка опирается на независимые результаты,
а не на планируемый прирост. Счётчик отсутствия новых успехов меняет стратегию;
сам по себе он больше не ставит задание на паузу.

## Рефлексия вместо паузы no_progress

Для выбора стратегии достаточно настоящего FAIL одной именованной проверки.
Если сценарий завершился раньше следующих проверок, их отсутствие не отменяет
уже наблюдавшуюся ошибку. Для PASS по-прежнему нужны все обязательные проверки.
Цель `diagnose_failure`, если это известный сценарий, обязательно резервирует
место в следующем независимом запуске и учитывается в `verification_limit`.

В `.lab-feedback/index.json` перечислен файл `scenario-N-checks.txt` с разбором:
успешные, ошибочные, явно пропущенные и не имеющие результата assertions.
Отсутствие результата не превращается в PASS или установленную причину сбоя.
Планировщик и кодер используют этот разбор вместе с исходным журналом и XML,
сохраняют успешные assertions и не закрывают весь пункт по частичному успеху.

После повторных неуспешных результатов контроллер назначает отдельный ход
`reflect_failure`: изучить существующие журналы и неудачные решения, отделить факты
от гипотез и получить недостающее наблюдение ограниченным экспериментом.
После исполненной диагностики следует `repair_after_reflection`: использовать её
результат для конкретного исправления с независимым повтором сценария.

Если исправление не помогает, контроллер может назначить один другой незавершённый
пункт текущей группы, затем обязательный возврат к ошибке. Выбор уже существующей
ветки переключения после двух ремонтов сохраняется. Отсутствие нового успеха не
стирает полезную диагностику, но и не превращает её в PASS. Если независимых
кандидатов в группе нет, диагностика и исправление продолжаются до пользовательского
лимита раундов; автоматического перехода в другую группу пока нет.

Решение и обязательство возврата сохраняются в `work-routing.json` вне рабочей
папки агента. Изменение списка assertions не стирает историю диагностики; текущий
FAIL всегда проверяется по актуальному определению. Каждый ход ограничен обычным
бюджетом, выбранная модель автоматически не меняется. Отклонённый обзор покрытия
получает ту же одну попытку исправления ответа, что невалидный план. Для API она
расходует только остаток первоначального резерва; повторная ошибка не обходит
валидатор и не запускает кодера с неподтверждённым планом.

| Причина остановки | Поведение |
| --- | --- |
| Нет новых успехов, повтор игрового FAIL | Рефлексия, ремонт, переключение с возвратом |
| Ошибка компиляции или схемы приёмки | Автоматический ремонт; новые функции ждут восстановления сборки |
| Невалидный ответ или отклонённое покрытие | Одна корректирующая попытка с точной причиной, затем явная ошибка |
| Устаревший checkpoint | Архив и перепланирование по текущим исходникам |
| Timeout | Существующее ограниченное продолжение частичного кода; бюджет не умножается |
| Авторизация, квота, API-бюджет, недоступная модель | Остановка с причиной; нет скрытого переключения или бесконечных повторов |
| Поломка verifier, неподтверждённая остановка runner | Остановка; новая запись не разрешается до восстановления изоляции |
| Пользовательская пауза, лимит раундов, итоговая приёмка | Сохраняются |

## Первый рабочий сценарий

После подтверждённых сборки и базового игрового запуска контроллер ищет в текущей
группе однозначное поведенческое условие раздела «Цель». Если это условие ещё не
имеет исполненного игрового сценария, назначается `implement_functional_goal`:
точный REQ, исходные `condition_ids`, `verification_kind=gameplay` и конкретный
`verification_objective`. Обзор покрытия и расширение упаковки не заменяют этот
ход. Для Auto Defense следующим шагом становится небольшой реальный бой через
UnionClef с остановкой, а не ещё одна проверка ZIP-поставки.

Правило использует консервативное распознавание явной формулировки цели; если цель
неоднозначна, оно ничего не угадывает. Ошибки схемы, сборки и текущие игровые
регрессии исправляются раньше. Достаточно реализовать и проверить небольшой срез,
не весь большой абзац за раз. Mapping без исполнения не снимает приоритет.
Результат исполнения освобождает обычную маршрутизацию для ремонта или обзора,
но не назначает PASS условию. Историческая загрузка здесь используется только для
выбора следующего шага, не для объявления актуальной работоспособности.

Приоритетные проверки выбираются по указанным condition IDs до других сценариев
того же широкого требования. После отклонения обзора завершённый транспорт
планировщика убирается с сохранением журнала, чтобы возобновление не повторяло
тот же отклонённый ответ.

## Связанный пакет на раунд

Планировщик выбирает от одной до четырёх связанных задач для одного вызова кодера:
основное `action` и до трёх `additional_actions`. Пакет ограничен текущей группой
ТЗ и наблюдаемыми регрессиями. `bundle_reason` объясняет общую реализацию или
проверку; `depends_on` может ссылаться только на предыдущие цели пакета.
Связность оценивает планировщик; контроллер проверяет область, типы целей,
зависимости, размер и доказательства каждого действия.

Число выбирается по сложности, без обязанности заполнять все четыре места.
Ремонт сценария ставится первым. Обзоры покрытия, ручная приёмка, глубокая
диагностика и обязательные директивы переключения остаются отдельными ходами.

`verification_limit` задаёт от одной до четырёх проверок за проход и не может быть
меньше числа действий. Сначала выбирается по одному актуальному сценарию каждого
участника пакета, затем остальные сценарии и регрессии. Явные
`verification_scenario_ids` должны уже существовать и относиться к действию.
Новые сценарии кодер добавляет в обычный acceptance-plan; контроллер находит их
по mappings после изменения. Успешные текущие проверки не повторяются без основания.

Один пункт может требовать нескольких сценариев. Отложенные приоритетные проверки
перечисляются в `omitted_priority_scenario_ids` и остаются в очереди; выбор пакета
не означает его завершение. Обязательная директива контроллера может резервировать
до двух мест для нового требования и возврата к старой ошибке.
Статусы приёмки и счётчик отсутствия успехов не подменяются количеством действий пакета.
Пакет отображается в окне планировщика и сохраняется в памяти каждого раунда.

Если контроллер экспортировал диагностические файлы, API-планировщик обязан
прочитать один из относящихся к сбою файлов до финального ответа. Исполнитель
принудительно выбирает инструмент чтения, пока не получит непустое содержимое
файла из индекса. Одного чтения индекса, поиска или цитирования памяти недостаточно.
План ремонта без `action.evidence_refs` получает одно напоминание внутри того же
задания и бюджета. После повторного отказа кодер не запускается. Контроллер не
создаёт цитаты за модель: соответствие файлу и фактическому чтению проверяется
независимо. Для Codex действуют тот же формат ссылок и контроллерная проверка.

`implement_and_map_requirement` принимает только ID требования `REQ-…`, а
`repair_scenario` и `implement_or_verify_scenario` — ID сценария. Текущие цели и
статусы передаются в `action_targets`. Уже успешный сценарий нельзя повторно
выбрать для реализации из-за ошибки другого сценария; при непроверенном покрытии
нужен обзор условий или реализация оставшихся условий.

После невалидного завершённого ответа контроллер допускает одну коррекцию той же
моделью. Исходные ответ и ошибка сохраняются, исправленный ответ проверяется
заново. При сбое провайдера, отмене или изменении исходников такая коррекция не
запускается. Для LiteLLM/DSLab используются только оставшиеся токены и запросы
первоначального резерва планировщика по данным шлюза; неизвестный расход или
исчерпание резерва запрещают дополнительный запрос. Лимит коррекции сохраняется
при восстановлении обработчика в пределах того же поколения запуска.

Контроль полноты исходных условий, независимый обзор покрытия и миграция старых
успехов описаны в [COVERAGE_RU.md](COVERAGE_RU.md). Успех одного среза не закрывает
составное требование. Планировщик получает `scenario_facts` и возраст handoff;
при диагностике доступного сбоя нужны проверяемые ссылки на прочитанные строки.

Перед каждым новым ходом кодера запускается отдельный планировщик. Он использует
выбранные для задания провайдер, модель и reasoning. Планировщик читает компактную
память, ошибки, индекс требований и нужные исходники. Полное ТЗ в каждый запрос
не вставляется. План содержит одно действие, причину выбора, диагностические
гипотезы и следующие шаги. Завершённый план сохраняется до запуска кодера и
переиспользуется при восстановлении этого раунда.

Планировщик назначает исполняемый шаг, а не обязан самостоятельно доказать
корневую причину ошибки. При противоречивых данных он передаёт кодеру
диагностическое задание: наблюдения, гипотезу, недостающее измерение, точные
файлы и способ независимой проверки. Неопределённость остаётся явной.
Это правило разделения работы, а не принудительное завершение по бюджету.

После двух оплаченных раундов с повторным подтверждённым падением одного сценария
контроллер назначает одно ещё не покрытое требование текущей группы. Следующий
раунд обязан вернуться к исходной ошибке. Сбой сборки или инфраструктуры имеет
приоритет; он не отменяет возврат. Если независимых требований нет, переключения
нет. План с другой целью отклоняется до запуска кодера.
Незакрытые ошибки остаются в памяти и
приёмке. Новая задача сама по себе не считается прогрессом: нужны независимые
результаты. При отсутствии новых успехов контроллер назначает рефлексию и
последующее исправление, а не паузу no_progress. Лимит раундов пользователя
продолжает действовать.

Для диагностики агент читает `.lab-feedback/index.json` и выбранные файлы по
ссылкам из индекса. Контроллер копирует фрагменты журналов и JUnit последних
падающих сценариев, включая многострочные стеки. Весь архив и папки компьютера
агенту не открываются. Общий размер копий ограничен 256 КиБ; сокращение явно
отмечается. Копии не служат доказательством PASS и не меняют хеш исходников.

Планировщик работает в контейнере `agent-planner`. Проекты подключены `:ro`.
Его очередь `planner-tasks` отделена от очереди кодера. Планировщик не имеет
Docker socket, базы контроллера или доступа к папкам игры. Профиль Codex отдельный;
исходная авторизация доступна через подключение только для чтения. Дополнительные
права Linux для вложенной песочницы не выдаются.

Для DSLab бюджет раунда делится между планировщиком и кодером. Планировщику
резервируется 20% бюджета без фиксированного потолка, с минимальным резервом
1 000. Кодер получает остаток. Максимальное число запросов также делится;
сумма лимитов двух стадий не превышает прежний лимит раунда. Планировщик получает
20% числа запросов (минимум один), без отдельного потолка в 12 шагов.
Достигнутый лимит остаётся явной ошибкой без автоматического повтора или
принудительного завершения исследования. Планирование требует
не менее 2 000 токенов и двух запросов в настройках раунда. При таком минимуме
объёмный контекст может не поместиться: ошибка лимита остаётся явной.

В окне расхода DSLab новые запросы учитываются отдельно для планировщика и
кодера. Старые записи без роли показаны отдельно; их расход не теряется.
Передача контекста и доступ к диагностическим файлам не изменены.

## Пункты, которые проверяет пользователь

Ручной пункт должен иметь конкретную причину, недоступную автоматизации
возможность, шаги и ожидаемый результат. Допустимые категории: субъективная
оценка внешнего вида, физическое устройство, внешний доступ и среда пользователя.

Ошибку сборки, падающий тест, отсутствие реализованного сценария и лимит
провайдера нельзя превращать в ручную проверку. Требование с исполняемым
сценарием также нельзя убрать из автоматической очереди этим способом.

Явные ручные пункты получают отметку `USER_TEST_REQUIRED`. Они остаются
непроверенными, не получают PASS и не подтверждают готовность проекта. Кодер
продолжает остальные требования. Когда автоматическая часть завершена, система
останавливается для приёмки пользователем; автоматическая работа не повторяет
ручной пункт бесконечно.

План и инструкции видны в панели **«Планировщик и ручные проверки»**. Исходные
запросы и ответы сохраняются в **«Истории агентов»**, с ролью «Планировщик».
Первый реальный план появляется после команды **«Продолжить»**. Просмотр панели
не запускает моделей. Реальные тесты и видео остаются отдельными доказательствами.
