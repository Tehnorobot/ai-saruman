## Подтверждённые проблемы

1. `worker/progress_guard.py`, ветка с task_id, учитывает успешные проверки и новые ID исполненных сценариев. Обзор с результатом missing и новые диагностические данные существующего FAIL не сбрасывают счётчик. Раунды 23–26 получили streak 1/2/3/4; после дополнительного deep_diagnosis контроллер остановился. Это отсутствие новых успешных результатов, но не отсутствие полезной работы.
2. `common/round_progress.py:outcome` не включает diagnose_failure в действия, привязанные к scenario target. Поэтому receipt раунда 26 содержит execution_observed=false, хотя acceptance_results.json и XML подтверждают исполненный FAIL. На сам вердикт теста это не влияет.
3. Реальный игровой отказ: в round-26/acceptance/search-32-nearest/test.log и экспортированном .lab-feedback/scenario-0-log.txt:309 есть playerAttack=true, attackerMatches=true, weapon=air, mainHand=air, slot=0. Причина выбора пустой руки пока не доказана. SearchRadiusTest.java:201 сбрасывает выбранный слот; необходимо проверить синхронизацию сервер/клиент и автоматическую экипировку UnionClef перед атакой. Ослаблять проверку меча нельзя.
4. Самозащита REQ-00010 открыта: закреплённый клиентский API не сообщает универсально UUID цели преследования обычного моба до первого удара. Документ: workspace/docs/REQ-00010-directed-aggression.md. Нужен явный выбор поддерживаемых сигналов и допустимого поведения при неопределённости; объявлять весь режим выполненным нельзя.
5. AutoCombat.java выбирает ближайшую цель при target == null. Переключение с живой текущей цели на нового ближайшего врага пока отсутствует. Это незавершённая функция, а не доказательство её поломки после готовности.
