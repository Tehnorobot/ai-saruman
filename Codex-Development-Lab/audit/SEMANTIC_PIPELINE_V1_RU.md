# Смысловой пайплайн v1

Дата: 26.10.2026. Этот файл описывает внедрение согласованной архитектуры.

Производственная точка входа `worker.engine.runner` использует
`worker.pipeline.run`. Старый цикл доступен только через явно вызываемый
`replay_legacy` для регрессионной проверки исторического протокола. Панель,
очередь и обычный запуск не переключаются на него при ошибке новой модели.

## Выполнение

1. Контроллер сохраняет снимок исходного ТЗ и настройки трёх ролей.
2. Планировщик выделяет смысловые требования и условия, затем компактные задачи
   с зависимостями. Ревьюер сверяет разбиение с исходником.
3. Контроллер проверяет схемы, ID, реальные цитаты, хеши, связи и DAG.
4. Планировщик выбирает связанный пакет из всего графа. Число задач и действий
   не фиксировано. Зависимости можно выполнить раньше в том же пакете.
5. Кодер вносит изменения и пишет исполняемые сценарии с именованными JUnit
   проверками для каждой контрольной точки.
6. Отдельный ревьюер читает код и тесты. Кодер отвечает на каждое замечание.
   Повтор обсуждения без новых данных передаётся в эксперимент и рефлексию.
7. Независимый исполнитель собирает код, запускает сценарии и регрессии,
   сохраняет оригинальные отчёты и медиа.
8. Факты возвращаются планировщику. Повтор одинакового результата вызывает
   пересмотр гипотезы, эксперимента или выбор независимой функции.
9. Перед готовностью нужны полный смысловой обзор покрытия и полный финальный
   независимый запуск. Ручные пункты остаются неподтверждёнными с инструкцией.

Ошибки JSON возвращаются автору с полем, типом, примером и меняющейся
инструкцией. Фиксированного отказа после одной коррекции нет. Действуют заданные
пользователем бюджеты, время выполнения и команды остановки. Ошибка доступа к
провайдеру не вызывает скрытую смену модели.

### Исправления после первого запуска MiniMax

- До первого ответа модель получает краткую форму и корректный вымышленный
  пример. Коррекция показывает конкретное поле и тип; полный отклонённый ответ
  остаётся в истории. Планировщик не должен перечитывать проект ради JSON.
- Каталог сохраняется сразу в `pipeline/draft.json`. Структурная валидность
  не означает принятие смысла: сначала ревью каталога, затем граф и ревью графа.
  Незавершённые этапы видны в панели. Канонические `catalog.json` и `graph.json`
  доступны рабочему циклу после семантического ревью.
- `RequirementsCatalog.question_resolutions` хранит точный вопрос, тип,
  статус, ответственного, связанные условия, ответ, основание и ссылки на ТЗ.
  `implementation_decision` — обоснованный выбор планировщика;
  `experiment` — проверка кодером; `user_clarification` — неоднозначность ТЗ.
  Старые вопросы без классификации остаются открытыми. Удалять их вместо
  решения нельзя. Ответ модели не подменяет уточнение пользователя.
- Открытый вопрос не требует заново строить неизменившийся граф. Эксперимент
  пересматривается по новым результатам. При отсутствии ответа пользователя
  продолжается независимая работа; финальная готовность остаётся запрещена.
  Изменение смысла условия по-прежнему обнуляет актуальность его доказательств.
- Обрыв потока API повторяет незавершённый этап в пределах того же бюджета
  токенов, запросов и времени. Частичные изменения кодера сохраняются; следующая
  попытка получает реальную версию файлов и исходную базу задания. Ключ, квота,
  конфигурация, недоступная модель и остановка пользователя не повторяются так.
- Счётчик памяти читается из актуального архива при каждом запросе панели.
  Рост индекса памяти сам по себе не отменяет уже принятый этап. Полная
  диагностика ошибки сохраняется, а в новый запрос идёт ссылка вместо большого
  повторного хвоста журнала.

### Восстановление API

Причина повтора берётся только из явной ошибки исполнителя или последнего
верхнеуровневого события `turn.failed`/`error`. Тексты исходников, результатов
инструментов и ответов модели не участвуют в классификации. Поэтому слова
`Budget`/`quota` и примеры HTTP-ошибок в коде не блокируют и не запускают retry.

Повторяются обрывы потока, временные HTTP 500/502/503/504 и отдельный исход
`stop_reason=error` (ошибка генерации, причина провайдером не раскрыта).
Повтор сохраняет этап, предыдущие принятые результаты, частичные файлы кодера
и выбранную модель. Задержки: 2, 4, 8, 16, 32, затем 60 секунд.
Пауза проверяется каждую секунду ожидания. Нового отдельного лимита числа
повторов нет: действуют общий бюджет запросов/токенов и лимит отдельного вызова.
Авторизация, квота, конфигурация и `max_tokens` так не повторяются.
HTTP 502, скрывающий отказ upstream HTTP 400/401/403/429, также не повторяется.
Причина и задержка показываются в окне пайплайна; исходная диагностика остаётся
в памяти и журнале попытки. Повтор не гарантирует восстановление самого сервиса.

## Реализация

Некорректный JSON аргументов инструмента обрабатывается внутри диалога:
парсер дочитывает поток для итогового usage, сохраняет публичные аргументы и
позицию ошибки, затем возвращает коррекцию модели. Весь пакет вызовов
отклоняется до выполнения, включая корректные соседние записи файлов.
Служебные метаданные исключаются из native-истории; thinking и подписи не
публикуются. Повреждённый JSON самого SSE-события или незакрытый блок инструмента
считается нарушением протокола и повторяется с контрольной точки.

| Файлы | Ответственность |
| --- | --- |
| `worker/pipeline.py`, `worker/engine.py` | Состояние фаз, вызовы ролей, восстановление и готовность |
| `common/pipeline_contracts.py`, `schemas/pipeline/` | 26 строгих контрактов v1, инструкции и примеры |
| `common/preparation.py` | Мягкий переход к работе и проверка зависимостей нерешённых задач |
| `common/catalog_patch.py` | Точечные изменения каталога и вычисление связанных условий |
| `common/task_graph.py` | Каталог, DAG, зависимости пакета и JUnit-привязки |
| `agent/daemon.py`, `agent/dslab.py` | CLI JSON Schema, native submit_result, отдельный read-only ревьюер |
| `worker/pipeline_verification.py` | Независимый разбор свежего XML и контрольных точек |
| `worker/acceptance_runner.py`, `worker/sandbox.py` | Запрос исполнителю v2 без квоты в четыре сценария |
| `common/pipeline_memory.py` | Полные неизменяемые записи, поиск и выдача страниц |
| `common/provider_settings.py`, `app/agent-models.js` | Провайдер, модель и reasoning по трём ролям |
| `app/pipeline.js`, `app/pipeline.css`, `app/main.py` | Окно пакета, задач, ревью и полной памяти |

Кодер — единственная роль, изменяющая рабочий код. Планировщик и ревьюер
используют существующий контейнер с проектами только для чтения. Вложенные LLM
делегации нового цикла отключены: ревью проходит через выбранную роль и учёт
расхода. Доступ к Docker, хостовым каталогам и секретам не расширяется.
Новых монтирований нет. `.env` не изменяется и не читается при внедрении.

## Память и восстановление

Канонические данные находятся в `artifacts/<project>/<job>/`:

```text
pipeline/catalog.json, graph.json, state.json, public.json
pipeline/manifest.json, latest-result.json
pipeline-memory/index.json
pipeline-memory/records/<id>.json
pipeline-memory/payloads/<id>.json
pipeline-memory/pages/<id>.json
round-N/pipeline/<phase>/attempt-N/
round-N/pipeline/session.json
round-N/pipeline/coding-state.json
round-N/pipeline/development-ready.json
round-N/pipeline-verification-result.json
round-N/full-verification/
```

Агенты получают диагностическое зеркало `.lab-memory/pipeline/` и текущие
документы `.lab-pipeline/`. Эти каталоги не входят в отпечаток исходного кода.
Иначе JSON с хешем самого проекта не мог бы иметь стабильный хеш.
Контроллер доверяет только своей канонической копии.

Входы, публичные выходы, ошибки формата, принятые планы, ревью и результаты
сохраняются целиком. Секретные и приватные поля провайдеров исключаются.
Пагинация выдачи не удаляет старые записи. При перезапуске контроллер продолжает
с сохранённой фазы; готовый код не создаётся повторно перед проверкой.
Хеш определения условия защищает от переноса старого PASS на новый смысл того
же ID. Исторические версии сохраняются.

У старого проекта новая декомпозиция выполняется при первом продолжении.
Существующие исходники, сценарии и история остаются на месте. Старые результаты
не объявляются автоматически доказательствами новых смысловых условий.

## Интерфейс и форматы

В «Моделях агентов» доступны планировщик, кодер и ревьюер. У старых заданий
ревьюер явно наследует модель кодера; можно задать отдельный выбор.

В разделе «Агенты и память» откройте «Пайплайн и решения». Там доступны пакет,
граф, статусы условий, ревью, рефлексия и полные JSON-записи с поиском.
История CLI и расход включают роль ревьюера.

API чтения:

```text
GET /api/jobs/<job>/pipeline
GET /api/jobs/<job>/pipeline/memory?task_id=T1&query=...&cursor=...
GET /api/jobs/<job>/pipeline/memory/<record_id>
```

Рабочие схемы — `schemas/pipeline/<Contract>.schema.json`; примеры —
`schemas/pipeline/examples/<Contract>.json`. Поля `Scenario.execution` задают
реальную задачу Gradle, ожидаемые JUnit cases и соответствия контрольным точкам.
`ReviewResult` содержит `reviewed_condition_ids` и цитаты реально прочитанных
исходников. Это уточняет демонстрационные форматы `proposal-v1` в HTML.

CLI и native API получают переносимую грамматику `*.submission.schema.json`:
точные поля, типы, обязательность и enum. Ограничения строк и путей полностью
проверяются контроллером по основной схеме. Так различия декодеров провайдеров
не превращаются в ошибку подключения и не ослабляют проверку результата.

В схеме **нового ответа** каждое объявленное свойство обязательно, в том числе
`question_resolutions` (для пустого списка — `[]`). Схема **хранения** продолжает
принимать старые каталоги без этого поля. Это разные задачи: обычная валидность
JSON Schema не подтверждает совместимость со строгим форматом API.
Перед запуском Codex исполнитель проверяет обязательность всех полей, закрытые
объекты и совпадение файла грамматики с текущим генератором. Native API,
`read_output_format`, начальная инструкция и коррекция используют одну грамматику.
Проверки охватывают все 26 контрактов и вложенные определения. Эти локальные
проверки не являются заявлением о выполненном платном вызове API.

### Точечная правка каталога

Полный `RequirementsCatalog` создаётся при первом разборе. Далее уточнение
вопросов и правки по замечаниям возвращают `CatalogPatch`:

```json
{
  "base_catalog_ref": {"path": ".lab-pipeline/catalog-base.json", "sha256": "<хеш точного файла>", "media_type": "application/json"},
  "conditions_upsert": [{"id": "C7", "requirement_id": "R3", "expected": "Уточнённое наблюдение", "verification": "automated"}],
  "requirements_upsert": [],
  "conditions_remove": []
}
```

Это сокращённый пример операций; полный обязательный формат и корректный
пример находятся в `schemas/pipeline/CatalogPatch.schema.json` и
`schemas/pipeline/examples/CatalogPatch.json`. Модель возвращает изменившиеся
записи целиком, а неизменённые не повторяет. Операции удаления используют ID;
произвольных путей и файловых операций нет. В запросе — ссылка на основу,
замечания и нужная диагностика. Полный каталог читается по ссылке при надобности.

Контроллер проверяет точную ссылку основы, применяет правку к копии, проверяет
все ID, владение условиями и цитаты. Ошибка оставляет исходный каталог прежним.
Полная новая версия и сама правка сохраняются в неизменяемой памяти.
При повторном ревью обязательны изменённые условия, условия затронутых
требований и вопросы из предыдущих замечаний. Если изменён граф, добавляются
затронутые зависимости. Финальное полное ревью и независимая приёмка сохранены.
Принятые полные правки предыдущей версии переиспользуются только при совпадении
их исходного задания; история не переписывается и не удаляется.

### Мягкая граница подготовки

`PREPARATION_SOFT_LIMIT_SECONDS=3600` задаёт момент завершения подготовки,
а не принудительную остановку. Значение передаётся обработчику через Compose.
`.env.example` содержит пример; реальный `.env` при внедрении не изменяется.
Счётчик `pipeline/state.json → preparation.elapsed_seconds` учитывает активную
подготовку и ожидания повторов, сохраняется между обычными паузами; время
простоя на паузе не прибавляется. При аварийном завершении между сохранениями
последний незаписанный интервал может быть потерян.

После границы новые циклы косметического ревью каталога прекращаются.
Планировщик выдаёт валидный граф и `PreparationHandoff`: рабочие решения,
готовые задачи, эксперименты, зависимости от пользователя и внешних систем.
Нерешённые замечания сохраняются как ссылки; они не объявляются исправленными.
Неизвестные вопросы получают точечную классификацию. Если подготовка ранее
остановилась именно по старому общему таймауту, при продолжении включается
переход с последнего исправленного черновика.

Контроллер распространяет пользовательские/внешние блокировки по графу.
Независимые задачи можно реализовывать; технические эксперименты сначала
передаются как `diagnose`. После независимого результата их решения обновляются
точечно, затем задача может перейти к реализации. Если доступной работы нет,
планировщик указывает реальную причину ожидания вместо пустого запуска кодера.

`AGENT_TIMEOUT_SECONDS` и настройки роли ограничивают один вызов исполнителя.
Суммарного часового обрыва всего цикла больше нет. Токены и число запросов
учитываются суммарно по прежнему бюджету. Ровно через час начало кодирования
не гарантируется: нужны валидные контракты, граф и доступный провайдер.
Окно пайплайна показывает время подготовки и рабочие решения. Переход к работе
не означает готовность: обязательны итоговое семантическое ревью и полный
независимый запуск; старые доказательства другой версии кода не закрывают вопросы.

`PlannerDecision.regression_condition_ids` задаёт затронутые ранее реализованные
условия для регрессии. Остальные независимые игровые сценарии не запускаются
автоматически в каждом раунде. Полный финальный запуск проверяет весь набор.
Не выбранные проверки сохраняют прошлые доказательства и их ревизии; при
изменении кода они требуют перепроверки. Доказательства ссылаются на неизменяемые
оригиналы памяти, а не на перезаписываемый файл последнего результата.

Интерактивная HTML-страница остаётся объяснением архитектуры. Её примеры —
проектные. Действующие схемы v1 находятся отдельно и загружаются из образа,
а не из файлов, изменяемых агентом.

## Границы проверки

Автоматические тесты используют синтетические ответы моделей и подставной
исполнитель, а проверка JUnit — настоящие XML-файлы с проверкой хешей. Они
проверяют контроллер, форматы, восстановление, отсутствие ложного PASS и UI.
Платные запросы к моделям и реальные игровые прогоны не запускаются при
установке. Качество конкретной модели и созданного мода оценивается реальными
последующими раундами, отдельно от исправности инфраструктуры.
