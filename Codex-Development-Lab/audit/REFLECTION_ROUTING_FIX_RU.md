# Автоматические остановки и смена стратегии

Проверены worker/engine.py, worker/planner.py, common/planning.py,
common/work_routing.py, common/task_assignment.py, timeout recovery и verifier.
Политика описана в PLANNING_RU.md, раздел «Рефлексия вместо паузы no_progress».

## Изменения

- Обе ветки автоматической паузы no_progress удалены: после проверки раунда
  и при восстановлении уже завершённого checkpoint. Сам счётчик независимых
  успехов сохранён; диагностика или новое имя ошибки не превращаются в PASS.
- Для повторного настоящего assertion FAIL добавлены обязательные директивы:
  reflect_failure — гипотезы и ограниченный эксперимент; repair_after_reflection —
  конкретное исправление с использованием результата диагностики. Планировщик
  не может заменить назначенный ход произвольным требованием или повторной
  диагностикой. Рефлексия не совмещается с дополнительными действиями пакета.
- После неуспешного ремонта можно переключиться на ещё не использованный
  независимый пункт текущей группы с обязательным возвратом. Граница текущей
  группы сохранена: автоматического перехода между группами здесь нет.
- История реальной диагностики используется для выбора стратегии даже после
  добавления assertions. Для текущего FAIL по-прежнему обязательны актуальное
  определение сценария и настоящее свидетельство исполнения.
- Отклонённый coverage review направлен в общий механизм одной коррекции ответа:
  точный отказ сохраняется и передаётся той же модели, все проверки повторяются.
  Коррекция запускается вне project lock. Для API она использует только оставшийся
  резерв исходной попытки. После повторного отказа или неизвестного остатка
  кодер не запускается; автоматических неограниченных исправлений формата нет.
- Receipt диагностики известного сценария учитывает фактическое исполнение,
  включая FAIL. Диагностика инфраструктуры не получает фиктивного исполнения.
- Обновлены инструкции планировщика/кодера, подписи UI и описание политики.

## Остановки, которые сохранены

Пользовательская пауза/стоп, авторизация, квота, API-бюджет, недоступная модель,
повторный невалидный план после коррекции, исчерпанное timeout-продолжение,
поломка verifier, неподтверждённая остановка/snapshot runner, итоговая приёмка
и общий предел раундов. Удаление этих ограничений создало бы повторные расходы,
разрешило бы неподтверждённый план или нарушило бы владение рабочей папкой.
Ошибки обычной сборки и игровых assertions уже возвращаются в автоматический
ремонт; их не нужно превращать в пользовательскую приёмку.

Если независимых кандидатов текущей группы нет, диагностика/ремонт продолжаются
в пределах пользовательского лимита; при режиме без лимита фиксированного числа
рефлексивных циклов нет. Требования и ошибки остаются открытыми.
