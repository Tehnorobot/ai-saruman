# Форматы планировщика — 26.10.2026

Формат плана хранится отдельно от описания задачи и выбранной модели:

- `schemas/planner_output.schema.json` — версия `planner_output_v1`, допустимые поля и типы.
- `schemas/examples/` — девять проверяемых примеров для всех восьми типов действий и пакета задач.
- `common/output_contracts.py` — загрузка доверенной схемы и проверка структуры.

Корневые `hypotheses`, `next_steps`, `manual_reviews`, `coverage_reviews`,
`additional_actions`, `bundle_reason`, `verification_limit` нельзя вложить в
`action`. Неизвестные поля и неверные типы отклоняются. Примеры содержат вымышленные
ID: их необходимо заменить ID и цитатами из реального проекта.

## Как передаётся план

API-планировщик MiniMax, DSLab или LiteLLM получает схему как описание аргументов
инструмента `submit_planner_plan`. Готовый план передаётся этому инструменту
одним объектом, отдельно от чтений. Итоговый JSON сериализует программа.
Инструмент не меняет файлы, не запускает кодера и не устанавливает PASS.

`read_planner_format` позволяет запросить один подходящий пример по имени;
все примеры не загружаются в каждый запрос. Планировщик Codex CLI может читать
те же доверенные файлы схемы/примеров из образа и возвращает JSON в финальном
сообщении. Контроллер проверяет структуру всех новых планов по одной схеме.

При неправильном вызове модель получает ограниченное сообщение с путями
ошибочных полей и может исправить форму в пределах бюджета текущей попытки.
Свободный текст вместо вызова получает одно напоминание. Автоматического
восстановления скобок, перемещения полей или смены модели нет. Незавершённый
из-за max_tokens ответ не исполняется.

## Формат не заменяет проверку смысла

После схемы остаются прежние проверки контроллера: допустимые ID, текущая задача,
порядок зависимостей, источник цитат и реальные строки, полнота покрытия,
обязательная диагностика и независимые результаты Minecraft. Правильно
оформленный выдуманный план не получает права обойти эти проверки.

Схема берётся из кода образа `/opt/lab/schemas`, а не из рабочего каталога агента.
Подмена файла `workspace/schemas/planner_output.schema.json` не меняет контракт.
Планировщик остаётся read-only. Старые задания и архивные форматы не переписываются.
Новые запросы получают явный признак версии контракта.

В образах закреплён валидатор [jsonschema 4.25.1](https://pypi.org/project/jsonschema/4.25.1/).
Оплачиваемые запросы к моделям для проверки интеграции не выполнялись.

Проверка: 950 тестов в Linux-контейнере, ошибок нет, 29 пропусков.
Изолированный Python исполнителя (`-I`) загрузил доверенную схему и все девять
примеров. Проверены коррекции формы, неверное вложение полей, невозможность
подменить схему из workspace, сохранение пар tool_use/tool_result и ограничений
бюджета, передача `$defs`/локальных `$ref` через шлюз LiteLLM. Проверки смысла и
происхождения доказательств остаются обязательными. Живые оплачиваемые вызовы
MiniMax/DSLab/LiteLLM не запускались; структура проверена на сохранённых сценариях
протокола и локальных тестах.
