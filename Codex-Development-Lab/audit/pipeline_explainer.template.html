02 / КАК РАБОТАЕТ КОНТРОЛЛЕР

Проверка — это набор алгоритмов

Скрипт не понимает текст как человек. Он проверяет явно заданные инварианты. Ни JSON Schema, ни Pydantic сами по себе не доказывают правильность решения.

Проверка графа

T1 → T2 → T3  → допустимый DAG
T1 → T2 → T1  → цикл: вернуть автору
T9 неизвестен → неверная ссылка

Алгоритм Кана:
1. Найти узлы без входящих рёбер.
2. Удалять их, уменьшая степени соседей.
3. Обработаны не все узлы → есть цикл.

Граф без циклов может быть плохим планом. Его смысл оценивает планировщик и ревьюер.

Почему не сделать контроллер LLM?

Он отвечает за воспроизводимое выполнение правил: одинаковые данные должны давать одинаковое решение по схеме, правам и версиям. Вызов LLM нужен для смысловой оценки. Контроллер вызывает планировщика или ревьюера и сохраняет их вывод, но не заменяет проверку прав мнением модели.

Контроллер не решает, что «воды достаточно для всего раздела передвижения». Он может установить лишь то, что условие о воде имеет результат. Остальные условия остаются открытыми.

03 / КОНКРЕТНЫЕ ФОРМАТЫ

Каждое сообщение имеет контракт

Все управляющие сообщения — JSON UTF-8. Исходный документ — Markdown UTF-8; код, логи, XML, MP4 и PNG остаются файлами. В JSON входят ссылки и SHA-256.

proposal-v1. Это конкретное предложение для согласованной новой архитектуры. Поля ниже ещё не являются действующим API. Текущая схема планировщика находится в schemas/planner_output.schema.json.

Сообщение

Путь относителен корню проекта. Хеши в примерах условные.

SourceRef

Строки с 1, обе границы включены.

Общие правила: обязательность, null, версии и доверие
  • Все перечисленные поля обязательны. Неизвестные поля запрещены. null допустим только там, где он указан в схеме. Пустой массив означает отсутствие элементов.
  • Строки с данными непустые, кроме поискового query. Значения enum регистрозависимы. Хеш — 64 строчных шестнадцатеричных символа.
  • Массивы задач не имеют фиксированной квоты. Для реализации требуется полезный непустой пакет. Для ожидания — конкретная внешняя причина. Эти межполевые правила проверяются отдельно от формы JSON.
  • spec_revision идентифицирует ТЗ вместе с уточнениями; source_revision — снимок исходников. В CoderReport поле base_source_revision указывает исходную версию, а scope.source_revision — полученную. Контроллер вычисляет хеши самостоятельно.
  • При первой проверке каталога и графа ссылки на ещё не принятые документы в ValidationRequest равны null. Текущий проверяемый документ указан в payload_ref.
  • replacement_graph_ref — ссылка на полный новый TaskGraph, а не произвольный patch. Контроллер проверяет его и принимает атомарно, сохраняя прежний граф. Для смысловых изменений сохраняются связи с ТЗ.
  • ReviewRequest.context_ref указывает DecompositionInput для разбора ТЗ, PlannerInput для плана или CoderAssignment для кода. При первом обзоре каталога catalog_ref может быть null; предлагаемый каталог находится в subject_refs.
  • Кодер может изменять файл сценариев. Он не может назначать доверенный runner_run_id, статус приёмки или теги подтверждённого успеха. Доверие определяется каналом исполнения, а не полем producer.
  • Пути проверяются после разрешения относительно разрешённого корня, включая переходы через символические ссылки. Выход за рабочую область отклоняется.
  • Контроллер отдельно проверяет согласованность полей: valid=true требует пустого issues; статус сценария должен совпадать с результатами его обязательных точек; принятые действия ссылаются на существующие условия. Смысловая достаточность теста остаётся предметом ревью.
  • Схемы доступны отдельно для каждого сообщения. Встроенный просмотр показывает его поля и общие определения. Это предлагаемые контракты, а не уже подключённый runtime-валидатор.
Как читать примеры по времени и версиям

VerificationResult показывает неуспех раунда 2 на снимке b…b. PlannerInput и PlannerDecision используют его для раунда 3. Reviewer смотрит промежуточный снимок d…d; ответ кодера и итоговый CoderReport ссылаются на исправленный e…e. VerificationRequest назначает новую проверку e…e; её результат в примерах ещё неизвестен.

Примеры форматов не являются реальными файлами мода. Хеши условные. Имена схем и ссылки на них — реальные файлы этой документации.

Как исправляется неверный JSON без потери работы

Контроллер сохраняет оригинал. Возвращает ValidationResult с точным путём, ожидаемым типом и примером. Автор исправляет представление. Для повторной ошибки система меняет подсказку или способ подачи схемы. Проект и память сохраняются.

Нет правила «одна коррекция, затем остановка». Действуют пользовательский бюджет и реальные ошибки доступа. Произвольный JSON не исполняется. Синтаксически оборванный ответ не дополняется догадками.

05 / СОХРАННОСТЬ И ДВИЖЕНИЕ
Полный архив. Краткий рабочий контекст.
Что хранится
Оригинальные публичные JSON, принятые версии, замечания, ответы, изменения и результаты. Каждая запись имеет ID, происхождение и ревизию.
Ошибка→Гипотеза→Эксперимент→Правка→Результат
Агенты получают индекс, нужные записи и ссылки на продолжение. Полная память не вставляется заново в каждый запрос.
Как избежать зацикливания
  1. Сравнить ошибку, гипотезу, изменения и наблюдения прошлых попыток.
  2. Если нового основания нет — назначить другой эксперимент.
  3. Либо выбрать независимую задачу по всему графу.
  4. Записать причину переноса и условие возврата.
Счётчик повторов — сигнал для анализа. Одинаковая формулировка не доказывает одинаковую причину. Бюджет, пользовательская пауза и внешние зависимости остаются реальными границами.

Пункт можно пропустить при автоматической разработке. В панели остаются шаги, ожидаемый результат и незакрытый статус.
NEEDS RETEST

Прошлый успех сохранён. Для текущего снимка нужна повторная проверка затронутых условий. Ничего не обнуляется в архиве.
Полное покрытие ID — необходимая формальная проверка. Она не доказывает, что само разбиение ТЗ было полным. Поэтому смысловой обзор исходника обязателен в целевой архитектуре.
