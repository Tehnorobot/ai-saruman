# Codex Development Lab — один `ТЗ.md` → автономная разработка и проверка

Внедрён смысловой пайплайн **v1**: граф задач от LLM, адаптивные пакеты,
отдельный ревьюер и полная память решений. Ответы моделей упрощены:
JSON для машинных действий, свободный Markdown для объяснений; служебные данные добавляет контроллер.
[Компактный обмен, сохранение истории и форматы](docs/COMPACT_AGENT_PROTOCOL_RU.md).
[Реализация и продолжение старых проектов](audit/SEMANTIC_PIPELINE_V1_RU.md).
В панели: «Модели агентов» → три роли; «Агенты и память» → «Пайплайн и решения».

Согласованная целевая архитектура и отличия от текущей реализации:
[PIPELINE_DESIGN_RU.md](PIPELINE_DESIGN_RU.md).

Новая архитектура с входами, выходами и примерами JSON:
[интерактивная HTML-схема](docs/pipeline/index.html). Открой файл в браузере.

Память раундов, ошибки и выборочное чтение ТЗ: [ROUND_MEMORY_RU.md](ROUND_MEMORY_RU.md).

Полнота требований и частичные результаты: [COVERAGE_RU.md](COVERAGE_RU.md).

В разделе «Материалы» результаты показаны от новых раундов к старым.
Можно выбрать конкретный раунд и догрузить файлы кнопкой «Загрузить ещё результаты».
Служебные JSON и история запросов не занимают страницы галереи.

Локальная универсальная Docker-платформа. **Это рабочая заготовка лаборатории, а не обещание, что любой мод будет создан правильно без проверки.** Присылаешь **один Markdown-файл** через браузер; агенты Codex создают проект, а независимый исполнитель собирает его и запускает доступные тесты. Скриншоты и видео появляются только после *реальных* графических тестов. Видео MP4 **не дольше 60 секунд** (запись теста до 58 секунд, последующая проверка перед загрузкой). Сервис Yandex Object Storage хранит приватные ролики; ключи поступают исключительно из `.env` в `storage`.

Интерактивная схема: [ARCHITECTURE.html](ARCHITECTURE.html). Открой файл в браузере.
Она показывает компоненты, раунд разработки, права доступа и замеры скорости.
Сервер для просмотра не нужен.

### MiniMax Explore / M Plan

Отдельный тест модели: [test_minimax.py](test_minimax.py), Python 3.10+, без
установки библиотек. Из корня проекта:

```powershell
python test_minimax.py --dry-run
python test_minimax.py --run --verify-code
```

Первый запуск только показывает задания. Второй отправляет 15 запросов:
планировщик, кодер и ревьюер × `low`, `medium`, `high`, `xhigh`, `max`.
Используются `MINIMAX_API_KEY` и `MINIMAX_BASE_URL` из `.env` или окружения;
ключ не передаётся через аргументы командной строки. `--verify-code` требует
запущенный Docker и существующий локальный `codex-lab-worker:local`:
Java-код проверяется без сети, секретов и подключённых папок хоста.
Ответы, время API, токены/кеш и таблица сравнения сохраняются в
`minimax-probe-results/<дата>/results.json` и `results.html` после каждого ответа.
Это отдельные прямые запросы: в счётчик панели Lab они не входят.
План и замечания ревьюера нужно оценить по смыслу; автоматические проверки
формата не доказывают их правильность. Minecraft этот скрипт не запускает.
Один пробный вариант: `python test_minimax.py --run --roles planner --efforts low high`.
Для повторов добавьте `--repeats 3`; лимит ответа задаётся `--max-tokens 16384`
(включает thinking), таймаут — `--timeout 900`. Усечённый ответ показан отдельно,
автоматических повторов нет. `--self-test` проверяет скрипт без сети и ключа.

В выборе провайдера проекта и моделей по ролям доступен **MiniMax / Explore**.
Документированная текстовая модель подписки — `MiniMax-M3.1-Flash`.
Reasoning: `low`, `medium`, `high`, `xhigh`, `max`; `default` означает `max`.
«Максимум ответа» в лимитах API применяется к обеим ролям, включая планировщика,
в пределах доступного бюджета стадии. В него входит thinking. При `max_tokens`
полный ответ не получен: увеличь этот предел либо снизь reasoning. Скрытого
потолка 4096 для планировщика нет; автоматического платного повтора тоже нет.
Thinking обязателен; `none`, `minimal` и `ultra` не отправляются.
Старый ID `MiniMax-M3.1-Flash-Preview` не предлагается: он выведен из эксплуатации.
Общая API-модель `MiniMax-M3` не включена в список Explore без подтверждения
доступа по подписке. Изображения и видео этот исполнитель пока не передаёт.

В локальном `.env` добавь:

```dotenv
MINIMAX_API_KEY=твой_Subscription_Key
MINIMAX_BASE_URL=https://api.minimax.io/anthropic
```

Нужен именно **Subscription Key** из MiniMax **Plan Details**, а не обычный
pay-as-you-go API Key. Ключи различаются способом оплаты; приложение не может
проверить тип ключа по его строке. Если `DSLAB_CONTROL_TOKEN` ещё не настроен,
создай отдельную случайную строку не короче 32 символов; существующее значение
сохрани. Это внутренний секрет шлюза, не ключ MiniMax.

После изменения `.env` обнови шлюз из папки проекта:

```powershell
docker compose up -d --no-deps --force-recreate provider-gateway
```

Затем обнови страницу → «Модели по ролям» → нужный агент → MiniMax / Explore →
модель и reasoning → сохранить. Настройки меняются на паузе; сохранение не
возобновляет задание. Можно оставить Codex у одной роли и MiniMax у другой.

Подключение использует Anthropic-совместимый протокол MiniMax с сохранением
thinking/tool-history. Ключ доступен только шлюзу; исходники и агенты его не
получают. В панели расхода учитываются вход, выход и кеш из usage; это не остаток
подписки и не точное денежное списание. При исчерпании подписки нет скрытого
перехода на pay-as-you-go или другую модель. Кредитные пакеты, если они уже есть
в аккаунте, MiniMax может использовать после квоты согласно своим правилам.

Проверено по официальным источникам 25.10.2026:
[модели Explore](https://platform.minimax.io/docs/m-plan/intro),
[уровни thinking и endpoint](https://platform.minimax.io/docs/guides/text-generation),
[ключи и квоты](https://platform.minimax.io/docs/m-plan/faq).

У сценариев в «Приёмке по ТЗ» есть разбор именованных проверок: что прошло,
что завершилось ошибкой, что явно пропущено и для чего нет результата.
Для ошибки показано сообщение JUnit; если причина не установлена, это отмечено.
Отсутствие последующих результатов не отменяет предыдущий FAIL и не доказывает,
что соответствующая функция не реализована. Такой же разбор доступен в памяти
выбранного раунда. Старые отчёты читаются из XML с проверкой контрольных сумм.

В разделе «Расход» вход включает обычные и кешированные токены. Кеш не
прибавляется к входу повторно. Экономия повторной обработки равна объёму чтения
кеша; её доля считается относительно всего входа. Это не уменьшение контекста
и не оценка денежной экономии. Стоимость Codex не определяется; стоимость API
показывается отдельно, когда для неё настроены тарифы.

Статистика Codex восстанавливается из сохранённых журналов завершённых ходов,
включая старые раунды. Текущий ход может быть ещё не учтён; попытки без usage
показаны отдельно. В окне истории есть дни UTC и среднее за активный день.
API обновляется по событиям usage, Codex — по завершении хода. Перезагрузка
страницы не сбрасывает счётчики. Эти показатели не служат измерителем остатка
квоты аккаунта.

## Продолжение после достижения лимита раундов

Пункты ТЗ и доказательства доступны в окне **«Приёмка по ТЗ»** выбранного проекта. Подробнее: [ACCEPTANCE_RU.md](ACCEPTANCE_RU.md).

Блок **«Сейчас выполняется»** показывает этап, текущий раунд и время с начала этапа. Он обновляется каждые пять секунд по состоянию обработчика и публичным действиям текущего агента. Время не сбрасывается от heartbeat. При недоступности данных последний статус помечается как устаревший. Сборка и независимые проверки пока отображаются общим этапом: без отдельного сигнала нельзя утверждать, что Minecraft уже запущен. Чтение ТЗ или работа с планом показываются только при соответствующей незавершённой команде в свежем журнале, а не по предположению о рассуждениях модели.

Выбери завершённое задание с надписью «Лимит раундов достигнут». Укажи, сколько раундов добавить, и нажми **«Добавить раунды и продолжить»**. Например, после 5/5 можно добавить 5: работа продолжится с раунда 6 до общего лимита 10. Сохраняются тот же проект, ТЗ, код, модель, отчёты и история. Завершённые раунды не перезапускаются.

Ограничения в 20 раундов больше нет. Количество дополнительных раундов задаёшь сам. Повторный запрос во время ожидания или работы не увеличивает лимит. Для паузы и ошибки используется обычная кнопка «Продолжить». Добавление раундов запускает работу агентов; само обновление панели ничего не запускает.

В новом проекте можно выбрать **«Без лимита»**. У существующего проекта задай **«Новый общий предел»** или включи **«Без лимита»**, затем нажми **«Сохранить лимит»**. Работающее задание сначала поставь на паузу. Конечный предел должен быть больше текущего номера раунда. После сохранения завершённое задание переходит на паузу; для запуска нажми **«Продолжить»**. Код и история сохраняются.

Безлимитный режим не останавливается по числу раундов. Пауза, стоп, ошибки, квоты и ограничения времени отдельных попыток сохраняются. Этот режим не подтверждает готовность мода автоматически: нужны проверки требований ТЗ. В API `max_rounds=0` означает отсутствие предела; положительное число задаёт общий предел. `POST /api/jobs/{jid}/round-limit` принимает это поле как Form; `extend-rounds` принимает положительное `additional_rounds` и продолжает задание после исчерпания конечного предела. Числа должны быть целыми и точно представимыми в интерфейсе (до `9007199254740991`); для работы без конечного предела используй режим без лимита.

## Требования

- Windows 10/11 с **Docker Desktop + WSL2**, включённый Linux container mode (или Linux с Compose v2).
- Лучше 16 ГБ ОЗУ, не меньше 20 ГБ свободного места (Minecraft/Gradle скачивают много данных).
- Интернет для первого построения Docker образов, библиотек и работы Codex.
- Доступный лимит Codex через вход ChatGPT в CLI; **без платного API по умолчанию**.
- Ключи S3 — *необязательны* для запуска лаборатории. Без них фото/видео остаются локально.

## Первый запуск в Windows PowerShell

1. Распакуй ZIP **в отдельную папку** и открой PowerShell внутри неё.
2. Выполни:

```powershell
powershell -ExecutionPolicy Bypass -File .\START_WINDOWS.ps1
```

Или вручную:

```powershell
Copy-Item .env.example .env
# В .env при необходимости заполните Yandex S3 ключи.
. .\Test-LabIsolation.ps1
$config = docker compose config --format json | ConvertFrom-Json
Assert-LabIsolation -Configuration $config -LabRoot $PWD.Path
Assert-LabVolumeMetadata -Configuration $config
docker compose build dashboard worker runner egress
docker compose up -d --no-build
```

3. **Один раз** войди в Codex (в том же Docker volume, что использует рабочий агент):

```powershell
docker compose run --rm agent codex login --device-auth
docker compose run --rm agent codex login status
```

Вход через устройство может требовать разрешения в настройках аккаунта ChatGPT. При входе не копируй логин/токены в `ТЗ.md`, `.env` или архив.

4. Открой **http://localhost:8080**. Загрузи единственный `.md` и выбери лимит раундов. Готовый пример — [ТЗ_Auto_Defense.md](examples/ТЗ_Auto_Defense.md): универсальный мод с отдельной интеграцией Saruman. В нём уже объединены требования, без обязательного чтения других входных Markdown. [Подготовка и дополнительные исходники](examples/AUTO_DEFENSE_PREPARATION_RU.md). Это задание на создание мода, а не уже включённый мод.

5. Просматривай этапы, Gradle-логи, отчёты, JAR, PNG, MP4 и резервные копии через веб-панель. Логи: `docker compose logs -f worker`.

## Выбор модели и reasoning в веб-панели

При создании проекта, рядом с загрузкой `ТЗ.md`, появились два новых параметра:

- **Модель** — введи ID модели, доступной твоей авторизованной сессии Codex, например `gpt-6-sol` или `gpt-5.3-codex`; пустое поле использует настройку по умолчанию Codex. Подсказки модели не гарантируют доступа в конкретном аккаунте.
- **Reasoning** — `По умолчанию`, `low`, `medium`, `high`, `xhigh`, а также `minimal` и `none` (последние поддерживаются не каждой моделью). Выбирай `medium` для обычных задач и `high`/`xhigh` для сложных требований, если нужная модель допускает уровень.

Для уже созданного проекта можно раскрыть **«Изменить модель / reasoning для следующих циклов»** на странице задания. Изменение разрешено, когда задача стоит в очереди либо приостановлена; во время активного вызова Codex сначала нажми «Пауза». Новая пара применяется к следующим раундам, уже завершённые раунды сохраняют прежние настройки.

Выбранные значения фиксируются в SQLite для **каждого проекта** и проходят по всей цепочке dashboard → worker → agent → `codex exec`. После Docker restart, quota pause и продолжения значение сохраняется; уже созданные проекты используют ранее выбранные настройки. Для существующих пользователей база обновляется автоматически с сохранением старых задач. Неверная модель/effort не заменяется системой молча: ошибка появится в логах, не будет считаться исчерпанием лимита.

Эквивалентный вызов Codex CLI:

```bash
codex exec --model gpt-6-sol -c 'model_reasoning_effort="high"' "..."
```

В отличие от API, выбор модели Codex CLI не означает автоматическую активацию платного API: по умолчанию используется уже настроенная авторизация через ChatGPT. Уровень reasoning **не гарантирует** определённый расход лимита; более высокий уровень может замедлить выполнение и увеличить использование ресурсов. Изменения настроек фиксируются в истории событий; при паузе и восстановлении действует последняя сохранённая пара. Во время выполняющегося запроса менять настройки запрещено.

## Yandex Cloud Object Storage

Приватный bucket, статический S3-ключ сервисного аккаунта с ограниченными разрешениями для объектов нужного префикса. В `.env`:

```dotenv
AWS_ACCESS_KEY_ID=...
AWS_SECRET_ACCESS_KEY=...
YC_S3_BUCKET=my-private-bucket
YC_S3_ENDPOINT=https://storage.yandexcloud.net
YC_S3_REGION=ru-central1
YC_S3_PREFIX=codex-development-lab
YC_VIDEO_MAX_SECONDS=60
```

Применить изменение `.env`: `docker compose up -d --force-recreate storage`. **Не публикуй `.env`** и не вводи ключи в веб-панель. Dashboard запрашивает временную подписанную ссылку через внутренний сервис `storage`, при этом у dashboard и Codex нет S3-ключей. Подтверждённая загрузка сверяется с HEAD/размером. Неудачная загрузка повторится; локальный оригинал сохраняется. Ролик длиннее минуты автоматически обрезается до ≤58 секунд, затем проверяется `ffprobe`.

## Minecraft Fabric 1.21.11 GameTests

Для выполнения клиентских игровых тестов **прочитай** [Minecraft EULA](https://www.minecraft.net/en-us/eula). Только если согласен, укажи в `.env` `MINECRAFT_EULA_ACCEPTED=true` и пересоздай контейнер worker:

```powershell
docker compose up -d --force-recreate worker
```

Агенты должны создать настоящие Fabric GameTests и задачу `runClientGameTest`. Пока у проекта её нет, статус `NOT_CONFIGURED`, видео не будет. Когда задача существует, тестовый клиент запускается внутри виртуального Xvfb экрана, а `ffmpeg` записывает до 58 секунд **именно экрана запуска тестов**. При очень медленной загрузке Minecraft видео может запечатлеть только загрузку, а не бой; сценарий остаётся `NOT_TESTED` без объективных проверок. Пример Fabric GameTests: https://github.com/FabricMC/fabric-docs/blob/main/versions/1.21.11/develop/automatic-testing.md

### Ограничения тестирования

- Успешный Gradle build **не равен** подтверждённому поведению в игре.
- Для PvP требуется отдельный подтверждённый тест с двумя игроками; обычный стартовый тест не подтверждает PvP.
- Псевдо-скриншоты, фиктивные метрики или заявленные агентом победы не являются доказательством.
- Система собирает `.jar`, но не гарантирует, что весь перечень требований завершён в установленное число раундов.
- Если нет подходящей тестовой среды для необычного приложения, dashboard показывает `NOT_CONFIGURED`/`NOT_TESTED`.

## Как работает ограничение Codex

При распознавании ошибки лимита Codex рабочий процесс переводит проект в `QUOTA_PAUSED`, отправляет запрос отдельному контейнеру `backup` и проверяет возможность возобновления после задержки (`QUOTA_RECHECK_SECONDS`, по умолчанию 900 с). **Никакого платного автоматического fallback**. Многократные попытки не выполняются чаще заданного интервала. При отсутствии достоверного времени сброса проверка выполняется одним новым запросом Codex в очередной цикл.

Все исходники, рабочая копия и артефакты сохраняются в папках `projects/`, `artifacts/` и `backups/` компьютера. Бэкап создаётся после каждого раунда и при паузе. В `backups/<job-id>/` появляются архив с датой, консистентная SQLite-копия очереди, manifest SHA-256 и контрольная сумма. Видеофайлы остаются локально и могут загружаться в S3; они не дублируются в каждый архив. После полного выключения компьютера сервисы запускаются снова при Docker Desktop, а очередь восстанавливается из SQLite.

Нельзя гарантировать сохранение **незавершённого** отдельного обращения к модели; после обрыва оно будет повторено с последней контрольной точки. При новой попытке Codex может использовать дополнительную часть лимита.

### Таймаут и продолжение сохранённого проекта

`AGENT_TIMEOUT_SECONDS` (по умолчанию 3600 с) теперь задаёт мягкий срок:
исполнитель не уничтожает процесс по времени. API-агент после текущего ответа
получает указание завершить исследование и выдать выводы; CLI получает целевое
время и инструкцию проверять часы. `PREPARATION_SOFT_LIMIT_SECONDS=3600`
переводит подготовку к рабочим решениям, а затянувшееся обсуждение кода —
к независимой проверке реальных сценариев. Нерешённые вопросы и замечания
сохраняются; истечение срока не устанавливает PASS.

Старые TIMEOUT продолжаются с текущими исходниками и контрольными точками
без фиксированного числа повторов. `MAX_AGENT_TIMEOUT_RETRIES` больше не действует.
Выбранные бюджеты токенов, запросов и раундов остаются обязательными.
Пауза пользователя сохраняет принятые этапы. Старое `FAILED` также можно
продолжить без загрузки ТЗ заново. [Изменения и настройки](docs/SOFT_HANDOFF_RU.md).
`STOPPED` и `FINISHED` остаются конечными состояниями.

Компиляция и unit-тесты могут выполняться в этапе разработки. Загрузку игровых
ассетов и запуск Minecraft промпт поручает независимому контроллеру после
завершения этапа Codex; их лимит — `TEST_TIMEOUT_SECONDS` (900 с по умолчанию).
Игровые проверки по-прежнему требуют явного согласия владельца на EULA.
Переменные передаются через Compose; изменение значений применяется при
пересоздании worker и agent. Авторизация хранится в прежнем томе.

Агент ограничен 768 процессами/потоками; JVM, Gradle workers и программный
рендеринг ограничены по параллелизму. После каждого этапа очищаются его процессы,
включая отделившиеся Java/Xvfb. Если очистка не подтверждена, агент завершается,
а результат передаётся контроллеру только после перезапуска контейнера.
Роли Codex передаются явно при запуске; их фактическое участие подтверждается
доступными событиями журнала, а не текстовым заявлением основного агента.

Бэкап сохраняет wrapper JAR, входные зависимости, ресурсы, итоговые JAR,
результаты тестов и crash reports. Кэши, игровые миры и видео не дублируются.
`backup_manifest.json` содержит причины исключения файлов и лимиты архива:
128 MiB для JAR/ZIP, 12 MiB для обычного файла и 512 MiB полезных данных
на снимок. Проверяй `exclusions`, если восстанавливаешь проект из архива.

## Управление

- В панели: `Пауза`, `Продолжить`, `Стоп`.
- Логи агента: `docker compose logs -f worker` и файлы в `artifacts/<project-id>/<job-id>/`.
- Логи S3: `docker compose logs -f storage`.
- Бэкапы: `backups/<job-id>/` и скачивание из панели.
- Перезапуск: `docker compose up -d` (не `down -v`, эта команда удаляет тома входа Codex и S3 index).
- Остановка без удаления данных: `docker compose stop`.

## Что встроено по умолчанию

Сборки и тесты выполняются в отдельных временных контейнерах. Они получают копию
workspace одного проекта, защищённый каталог экспорта и отдельный кэш проекта
в закрытом Docker volume, без подключения папок Windows. Один раунд проверки
использует один контейнер и один обмен исходниками. Кэши Gradle и каталог `build`
остаются в Linux-томе; JAR и отчёты возвращаются в `artifacts/.../builds` и соседние
каталоги результатов. В `projects/` возвращаются исходники без этих кэшей.
`worker` работает как обычный пользователь и не имеет Docker socket.
Небольшой служебный `runner` принимает через Unix socket только архив проекта и
команду. Образ, подключаемые тома, пользователь и ограничения ресурсов задаются
его кодом; передать путь хоста или включить privileged через этот интерфейс нельзя.
Только `runner` имеет Docker socket; папки проектов и учётные данные ему не
подключены. Это доверенная часть системы, которая управляет Docker.
Обновление, границы доступа и восстановление: [ISOLATION_RU.md](ISOLATION_RU.md).
Ускорение, сетевые ограничения и результаты замеров: [PERFORMANCE_SECURITY_RU.md](PERFORMANCE_SECURITY_RU.md).
История предыдущих исправлений: [FIXES_RU.md](FIXES_RU.md).

Codex выполняется в отдельном контейнере `agent`: он видит каталог проектов лаборатории, собственный task-mailbox, Codex login volume и кэш Gradle; `data/`, `artifacts/`, бэкапы и S3 credentials туда не монтируются. Агент и тесты используют изолированные сети без шлюза к хосту. Интернет доступен через фильтрующий HTTP/HTTPS-прокси, который запрещает локальные и частные адреса. Из-за ограничений вложенного sandbox внутри Docker Codex работает с `danger-full-access` **только внутри изолированного контейнера**, не на Windows-хосте. Не помещайте посторонние конфиденциальные файлы в каталог проектов лаборатории.

Skills и `AGENTS.md` копируются внутрь нового проекта автоматически. Агенты определяют тип проекта по содержанию ТЗ, создают исходники и конфигурацию без иных обязательных файлов. Для Fabric 1.21.11 встроено специальное техническое руководство. `architect`, `implementer`, `reviewer`, `tester` доступны как роли Codex; реальную стратегию делегирования определяет Codex.

Встроенный `code-quality` применяется при реализации и исправлении кода: существенные
предположения формулируются явно, изменения ограничиваются задачей, API проверяются,
а результат подтверждается наблюдаемыми проверками. Skill основан на предоставленных
рекомендациях `CLAUDE.md`; обычные решения агент принимает самостоятельно.
Его файл: [skills/code-quality/SKILL.md](skills/code-quality/SKILL.md).

Имя Fabric-skill — `fabric-minecraft-12111`: точки в имени skill недопустимы,
хотя номер версии в описании остаётся `1.21.11`. Перед запуском Codex обновляются
также skills существующего проекта. Старый каталог переименовывается с сохранением
содержимого; если новый каталог уже есть, старая копия сохраняется в
`workspace/.lab-legacy-skills/` вне каталога обнаружения skills. Пользовательские
правки существующих skills не перезаписываются. В новом задании worker явно
направляет реализацию к `code-quality`; ручной вызов — `$code-quality`.

Встроенные тестовые профили сейчас распознают Gradle, Maven, pytest и npm (если объявлен тестовый скрипт). Новые runner'ы можно добавлять в `worker/engine.py`. **Запуск произвольного недоверенного кода** происходит в изолированном контейнере, но Docker — не абсолютная песочница. Не храните в смонтированных папках конфиденциальные материалы. Веб-панель привязана исключительно к `127.0.0.1`; не открывайте её в интернет без отдельной авторизации.

## Проверка сборки и файлов

Результаты проверки нового ограниченного запуска находятся в
[RUNNER_VALIDATION_RU.md](RUNNER_VALIDATION_RU.md); предыдущего аудита — в
[FIX_VALIDATION_RU.md](FIX_VALIDATION_RU.md). `VALIDATION_REPORT.md` сохраняет
историю проверки исходной упаковки проекта.

`docker compose config` проверяет конфигурацию Compose (без запуска). Первый Docker build требует сети. В `VALIDATION_REPORT.md` указано, что реально удалось проверить в среде создания архива, а что остаётся непроверенным. Yandex S3 credentials и Docker Desktop пользователя недоступны в среде генерации ZIP, поэтому реальный облачный upload и запуск Minecraft будут проверены при твоём первом запуске.

## Исправление первого запуска Docker Compose (pull access denied)

Если появляется `pull access denied for codex-lab-service:local` или
`pull access denied for codex-lab-worker:local`, образ не был собран локально.
Сборка теперь выполняется до запуска сервисов, а для локальных образов задано
`pull_policy: never`. В PowerShell из каталога проекта:

```powershell
powershell -ExecutionPolicy Bypass -File .\START_WINDOWS.ps1
```

Никакого `docker login` или `docker pull codex-lab-service:local` не нужно.
При обычной перезагрузке ранее собранных образов достаточно `docker compose up -d`.
Если первая команда заканчивается ошибкой загрузки npm, Maven, Gradle или Java,
исправлять нужно ошибку из вывода сборки; второй шаг до её устранения не выполняется.
Существующий `.env` при обновлении не перезаписывается.
