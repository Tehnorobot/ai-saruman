# Приёмка по ТЗ

В панели выбери проект и нажми **«Приёмка по ТЗ»**. Окно показывает исходные пункты, строки и цитаты ТЗ, уточнённые агентом критерии, результат выполнения тестов и доказательства. Есть поиск, фильтры статусов и отсутствующих видео. Закрытие окна останавливает его плееры; обновление данных не сбрасывает просмотр.

## Откуда берутся пункты

Контроллер получает консервативный черновой каталог из абзацев, списков и блоков исходного `ТЗ.md`. Ни один выделенный пункт не исчезает из списка, если агент его не обработал. Информационные абзацы тоже могут попасть в черновик: их назначение требует проверки, они не получают автоматический PASS. Для ТЗ свыше 2000 исходных блоков окно явно предупреждает об ограничении каталога и не объявляет полный охват.

Агент читает `acceptance-catalog.json` и создаёт `acceptance-plan.json`: уточняет названия, ожидаемый наблюдаемый результат и тип проверки; связывает IDs требований с отдельными сценариями. Исходные цитаты и контрольную сумму ТЗ задаёт контроллер, а не агент. Неизвестные IDs, несогласованные ссылки и план другого ТЗ отклоняются. Агентские поля вроде `status: PASS` не учитываются.

## Проверка и видео

После успешной сборки контроллер запускает до четырёх сценариев за раунд в существующей изоляции. Ещё не запускавшиеся сценарии получают приоритет. Ограничение размера группы не ограничивает общее количество сценариев.

Каждый игровой сценарий получает отдельное окно записи. Тест должен загрузить мир, напечатать `LAB_ACCEPTANCE_BEGIN:<id>`, подождать не меньше секунды перед демонстрацией, выполнить действия и утверждения, затем напечатать `LAB_ACCEPTANCE_END:<id>` и оставить результат видимым ещё хотя бы полсекунды. Контроллер наблюдает маркеры и игровое окно, записывает настоящий дисплей и проверяет, что начало и конец уложились в запись. Длинную демонстрацию следует разделять: один ролик ограничен 58 секундами.

Перед каждой проверкой удаляются старые XML-результаты. Проектный адаптер должен сохранять честный свежий JUnit XML с точными `classname`/`name` после реальных утверждений, включая ошибки и пропуски. Fabric Client GameTest сам по себе такой отчёт не предоставляет: его нужно подключить к адаптеру. Просто вывести маркеры, создать MP4 или завершить процесс с кодом 0 недостаточно.

Для unit/API-пунктов доказательством служат выполненные утверждения и журналы; видео может быть неприменимо. Для игровых пунктов обязательны также проверенная непустая запись и подтверждённые границы демонстрации. Отсутствующие тесты, пропуски, ошибки, обрезанное видео и недоступные доказательства видны в окне.

## Версии и доверие

Результат связан с контрольными суммами ТЗ, кода и плана. При изменении кода прежние успешные доказательства становятся устаревшими; старые ролики сохраняются для просмотра. Сохранённые XML проверяются по хешам; ссылки ограничены файлами этого задания. Симлинки, обход каталогов, DTD/entities, неподдерживаемые XML и внешние URL не допускаются.

«Тесты пройдены» означает выполнение указанных тестовых утверждений. Оно не доказывает, что сами написанные агентом тесты достаточно полно и правильно выражают ТЗ. Даже если все строки проходят тесты, сводный статус — `TESTS_PASSED_REVIEW_REQUIRED`, а не автоматический `READY`. Семантическая полнота и качество тестов требуют независимого рассмотрения.

## Схема плана

```json
{
  "schema_version": 1,
  "spec_sha256": "контрольная сумма из acceptance-catalog.json",
  "requirements": [{
    "id": "ID из каталога",
    "title": "Обнаружение зомби",
    "expected": "Зомби обнаружен до контакта, сервер зарегистрировал удар",
    "kind": "gameplay",
    "scenario_ids": ["zombie-before-contact"]
  }],
  "scenarios": [{
    "id": "zombie-before-contact",
    "kind": "gameplay",
    "task": "labZombieAcceptance",
    "requirement_ids": ["тот же ID из каталога"],
    "description": "Один воспроизводимый сценарий",
    "expected_tests": [{"classname": "example.ZombieAcceptance", "name": "detectsBeforeContact"}]
  }]
}
```

Gradle-задача получает `-PlabAcceptanceScenario=<id>`. Проект обязан связать это свойство с выбором конкретного теста: свойство не фильтрует стандартный Fabric-набор автоматически. Пути команд, shell-фрагменты и произвольные аргументы в плане не принимаются.

Файлы доказательств: `round-NN/acceptance/<scenario-id>/`. Матрицы: `round-NN/acceptance.json`, `latest_acceptance.json`. API только для чтения: `GET /api/jobs/{jid}/acceptance`.

Ранее записанные общие ролики не распределяются задним числом между требованиями. Первые отдельные ролики появятся после подготовки плана и реального выполнения сценариев новым контроллером. Само открытие окна не вызывает LLM и не запускает Minecraft.
