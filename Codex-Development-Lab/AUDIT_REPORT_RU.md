## P1 — запуск, восстановление и независимость проверки

### 1. Команда исполнителя содержит неподдерживаемый аргумент Codex

Место: `agent/daemon.py:27–28`; закреплённая версия — `Dockerfile.worker:2`.

Исполнитель формирует `codex exec ... --ask-for-approval never ...`.
У закреплённого CLI 0.162.1 `exec` не объявляет этот аргумент: его нет ни в структуре
аргументов команды, ни в подключённых общих аргументах. Поэтому вызов завершается
ошибкой разбора аргументов до обращения к модели; задание получает `FAILED`.
Существующие тесты подменяют Codex скриптом, который принимает любые аргументы,
и эту ошибку не замечают.

Доказательства закреплённой версии: [exec/src/cli.rs](https://github.com/openai/codex/blob/rust-v0.162.1/codex-rs/exec/src/cli.rs),
[shared_options.rs](https://github.com/openai/codex/blob/rust-v0.162.1/codex-rs/utils/cli/src/shared_options.rs).
Локальный CLI `0.162.0-alpha.17.2` дополнительно воспроизводит `unexpected argument '--ask-for-approval'`
при безопасном вызове с `--help`. Это отдельная версия; настоящий бинарник 0.162.1
в контейнере не запускался. Подробности: [audit/cli_evidence.md](audit/cli_evidence.md).

Исправление: согласовать argv с закреплённой версией, задавая политику одобрения
поддерживаемым этой версией способом, и проверять реальный разбор argv без модельного вызова.

### 2. Возобновление после паузы получает CANCELLED от предыдущей попытки

Место: `worker/engine.py:227–259`, обработка результата — `worker/engine.py:288–308`.

`request_agent()` при паузе создаёт `cancel/<taskid>` и сразу возвращает `USER_PAUSED`.
Исполнитель позднее сохраняет `CANCELLED`. Номер раунда ещё не увеличен; после
возобновления используется тот же `taskid`. Контроллер читает старый результат,
новый запрос не создаёт, а `runner()` трактует `CANCELLED` как ошибку агента.

Воспроизведение: пауза во время первого раунда → результат исполнителя `CANCELLED`
→ возобновление. Получено `USER_PAUSED`, затем `CANCELLED`, новый запрос отсутствует.

Исправление: дождаться завершения отменяемой попытки и выделять каждой попытке
собственный ID; старые запросы/результаты/отмены не должны относиться к новому запуску.

### 3. Перезапуск может пропустить незавершённые проверки

Место: `worker/engine.py:280`, `worker/engine.py:309–312`.

`round=n` записывается до выполнения `checks()`, а восстановление начинается с
`round+1` без учёта сохранённой фазы `verifying`. Если worker остановлен между
этими действиями или во время тестов, проверка текущего раунда не повторяется.
На последнем раунде задача сразу становится `FINISHED`, хотя отчёта может не быть.
Пауза во время проверки также может оставить раунд без завершённой проверки.

Воспроизведение: `round=1`, `max_rounds=1`, `phase=verifying`, отчёта нет;
повторный `runner()` устанавливает `FINISHED`, `checks()` не вызывается.

Исправление: сохранять отдельно завершение разработки и завершение проверки;
восстанавливать незавершённую фазу без повторного обращения к модели.

### 4. Пауза/стоп плюс падение worker навсегда оставляют RUNNING

Место: `common/db.py:112–114`, `app/main.py:74–83`.

Для работающего задания API записывает флаг паузы/отмены, сохраняя `RUNNING`.
Если worker падает до подтверждения, новый worker не может забрать задание:
`claim()` исключает все строки с этими флагами даже при истёкшей аренде.
`resume` разрешён только для `USER_PAUSED`/`QUOTA_PAUSED`, поэтому возвращает 409.

Воспроизведение: `create_project → claim → pause → lease_until=0 → claim`.
Результат: `RUNNING`, `pause_requested=1`, повторный `claim=None`, `resume=409`.
Для `stop` аналогично.

Исправление: при восстановлении просроченных заданий сначала подтверждать
сохранённые запросы управления, затем решать вопрос повторного исполнения.

### 5. Проверяемый код может менять базу контроллера и доказательства

Место: `worker/engine.py:94–95`, `compose.yaml:69–75`.

Gradle/Maven/npm/pytest выполняются прямо в контейнере worker с его UID,
окружением `LAB_DB` и доступом на запись к `/data`, `/artifacts`, `/agent-tasks`.
Отделение контейнера Codex не отделяет сгенерированный им build/test-код от
проверяющего контроллера. Скрипт проекта может менять статусы очереди,
перезаписывать отчёты и воздействовать на другие задания.

Воспроизведение: синтетическая проектная команда, запущенная через настоящий
`engine.command()`, открыла SQLite по `LAB_DB`, изменила `jobs.phase` на
`changed_by_project_test` и завершилась с кодом 0. Изменение сохранилось.

Исправление: запускать build/test в отдельной среде без базы/почтового ящика
контроллера, с ограниченными выходными файлами. Доверенный процесс должен
сам формировать итоговые статусы из результатов запуска.

## P2 — проверки, управление, резервные копии и интерфейс

### 6. Документированная команда тестирования внутри dashboard не работает

Место: `Dockerfile.service:8–12`, `tests/test_lab.py:7–8`, `tests/test_codex_settings.py:10`.

В сервисный образ копируются тесты, но не `worker/` и `agent/`, которые они импортируют.
Команда из README `docker compose run --rm dashboard python3 -m unittest discover -s tests -v`
получает `ModuleNotFoundError`. В собранном сервисном образе воспроизведены две
ошибки импорта. С подключением полных исходников в Linux все 20 тестов проходят.

Исправление: отдельный полноценный тестовый образ либо включение необходимых
модулей в образ, на который ссылается инструкция.

### 7. Kotlin DSL пропускает Minecraft GameTests

Место: `worker/engine.py:152`.

Условное выражение вычисляет `is_minecraft=False`, когда отсутствует `build.gradle`.
Распознавание `build.gradle.kts` для обычной сборки есть, для Minecraft — отсутствует.
При `build.gradle.kts` и `gradle.properties` с Fabric сборка запускается, но
обнаружение клиентских GameTests и проверка EULA вообще пропускаются.

Воспроизведение: синтетический Kotlin DSL/Fabric проект, выполнение Gradle
подменено; проверяется только выбор ветви. Вызовов
`discover_game_test`/`minecraft_client_gametest` нет. Игра не запускалась,
пользовательское согласие не менялось.

Исправление: явно выбирать существующий Gradle-файл и проверять его содержимое;
избежать неоднозначного сочетания `and`/`or` с тернарным выражением.

### 8. Управляющий запрос может перезаписать уже завершённый статус

Место: `app/main.py:74–83`.

Чтение состояния и изменение выполняются раздельно. Если worker завершит работу
между SELECT и UPDATE, запрос `pause` запишет устаревшее `RUNNING` поверх `FINISHED`.
Другая последовательность — `QUEUED → claim → pause` — преждевременно объявляет
`USER_PAUSED`, пока worker ещё выполняет задачу, разрешая настройки/возобновление.

Воспроизведение с контролируемым завершением между SELECT и UPDATE:
`status=RUNNING`, `phase=max_rounds_reached`, `pause_requested=1`.

Исправление: выполнять переход атомарно с проверкой текущего состояния в SQL.

### 9. Manifest резервной копии может не совпадать с содержимым архива

Место: `backup/daemon.py:35–36`, асинхронный запуск копии — `worker/engine.py:263–266`.

Файл сначала добавляется в tar, затем повторно читается для SHA-256. Следующий раунд
может уже редактировать проект, поскольку запрос копии асинхронный. Manifest тогда
содержит хеш новой версии, а архив — старую версию. Разные файлы проекта также
могут относиться к разным моментам времени; online backup SQLite решает только
консистентность самой SQLite.

Воспроизведение: запись новой версии между `tar.add()` и чтением хеша.
Архив содержит `version = 1`, текущий файл — `version = 2`,
`manifest_matches_archive=false`.

Исправление: хешировать именно архивируемые байты и обеспечить неизменяемый
снимок исходников либо координацию записи проекта с резервным копированием.

### 10. Смена bucket/prefix не приводит к загрузке видео в новое место

Место: `storage/s3_cli.py:147–152`, подпись URL — `storage/api.py:43–48`.

Идентификатор дедупликации содержит только относительный путь и SHA исходника.
После изменения bucket/prefix существующая запись считается загруженной и
возвращает старые bucket/key. Повторной загрузки нет. Подписывающий сервис
использует новую конфигурацию: старый prefix отклоняется, либо подписывается
ключ в новом bucket, где объекта нет. Аналогично новая политика длительности
не применяется к уже индексированному исходнику.

Воспроизведение с fake S3: первая загрузка в `old-bucket/old-prefix`, затем смена
конфигурации. Ответ `ALREADY_UPLOADED` со старым bucket/key; всего один upload.

Исправление: учитывать назначение и параметры обработки в ключе дедупликации;
подписывать URL для подтверждённого назначения конкретной записи.

### 11. Журнал в веб-панели замирает после 500 сообщений

Место: `common/db.py:94–96`, `app/index.html:13`.

База возвращает первые 500 событий после `after`, а панель всегда запрашивает
`/events` без `after` и полностью заменяет отображение. После накопления 500
сообщений новые ошибки и сообщения завершения больше не видны.

Воспроизведение: 502 события в настоящей SQLite дают только первые 500 при запросе
без курсора. Дополнительно настоящий JS исполнен с подставленным DOM/fetch:
два обновления при 501 и 502 событиях оба показывают последним `event 500`.

Исправление: использовать имеющийся параметр `after` и догружать страницы либо
возвращать последние сообщения с явным ограничением истории.

## Воспроизведения и границы выводов

- [audit/reproduce_runtime.py](audit/reproduce_runtime.py): отмена/возобновление,
  восстановление фазы, Kotlin DSL, доступ теста к базе контроллера.
- [audit/reproduce_queue_ui.py](audit/reproduce_queue_ui.py): восстановление
  запросов управления, гонка статусов и ограничение истории событий.
- [audit/reproduce_storage_backup.py](audit/reproduce_storage_backup.py):
  несоответствие manifest и перенос назначения S3.

Воспроизведения используют временные синтетические проекты, заглушки внешних
команд/облака и настоящие функции контроллера. Они доказывают конкретные
ошибки, но не заменяют запуск Minecraft, реальную авторизацию Codex или S3.
Проверка Docker Compose выполнялась без рабочего `.env`. Полная сборка worker,
запуск всей платформы, модельные вызовы, реальный S3 и игровой клиент не проверялись.

Рекомендуемый порядок исправлений: совместимость CLI → жизненный цикл попыток
и восстановление фаз → атомарные переходы очереди → изоляция build/test →
тестовый образ и Kotlin DSL → резервные копии/S3/журнал.
