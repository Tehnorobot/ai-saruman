# Прогресс приёмки

Контроллер хранит очередь и историю сценариев отдельно от последнего отчёта:
`artifacts/<project>/<job>/acceptance-progress.json`. Старые отчёты раундов
сохраняются. При первом чтении контроллер восстанавливает из них историю.

- Новые сценарии получают приоритет. Затем выполняется самый давно проверявшийся
  сценарий, которому нужна проверка. Ошибка одного сценария не блокирует очередь.
- За один раунд выполняется до четырёх сценариев. Если сборка прошла и остаются
  непроверенные сценарии, контроллер может выполнить следующий раунд без вызова
  модели. При ошибке теста модель получает управление для исправления; ещё ни разу
  не запускавшиеся сценарии сначала получают по одной попытке проверки.
- Подтверждения на неизменном коде накапливаются. Для повторного использования
  должны совпадать ТЗ, исходники и определение сценария, включая имена assertions.
  После изменения кода прежний успех остаётся в истории и требует перепроверки.
- Старые отчёты без хеша определения сценария дают историческую информацию,
  но не становятся новым подтверждением для текущего определения теста.
- После трёх раундов модели без изменений исходников, новых результатов
  независимых проверок или впервые выполненных сценариев задание получает
  `USER_PAUSED`, этап `no_progress`. Проверочные раунды без вызова модели
  не увеличивают этот счётчик. Перезапуск worker его не сбрасывает.
  Явное возобновление пользователем даёт новую серию из трёх попыток.

В окне «Приёмка по ТЗ» отдельно показаны текущие подтверждения, результаты,
которым нужна перепроверка, исторические успехи и неподтверждённые пункты.
В окне памяти раунд без модели обозначен как независимая проверка кода.
Состояние RUNNING само по себе не обнуляет подтверждения неизменного кода.

Общее число пунктов ТЗ не равно числу реализованных сценариев. Контроллер
не может подтвердить пункт, для которого агент ещё не создал полный набор
проверяемых assertions и, если требуется, игровую видеозапись.

Регрессии контроллера: `tests/test_acceptance_progress.py`,
`tests/test_progress_guard.py`, `tests/test_acceptance_workflow.py` и
`tests/test_acceptance.py`. Они используют синтетические проверки и транспорт
без платных вызовов моделей. Их успех не означает готовность Minecraft-мода.
